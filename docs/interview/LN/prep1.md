## 1. DAG技能编排 vs 卡片的关系：业务场景拆解

### 什么是"技能"（Skill）？

这是**AI Agent时代的概念**，不是传统App的功能模块。

```
技能（Skill）= AI能执行的一个原子能力
    ├── 查天气： "今天北京天气怎么样？"
    ├── 定闹钟： "帮我定明天早上7点的闹钟"
    ├── 导航： "导航到最近的星巴克"
    ├── 拍照识别： "这是什么植物？"
    └── 复杂技能： "我明天要去深圳出差，帮我查天气、定闹钟、导航到机场"
                    ↑
                    这就是多个原子技能的组合 = DAG编排
```

### DAG是什么？

```
DAG = 有向无环图（Directed Acyclic Graph）

"帮我规划明天出差" 这个技能，内部流程：
    
    [开始] 
       ↓
    [查天气] ──→ [天气冷?] ──是──→ [提醒带外套]
       ↓              └──否──→ [跳过]
    [定闹钟]
       ↓
    [查航班] ──→ [有直飞?] ──是──→ [预订机票]
       ↓              └──否──→ [推荐高铁]
    [导航到机场]
       ↓
    [结束]
```

**每个节点** = 一个原子技能调用（调用天气API、闹钟API、地图API）

**连线** = 数据流 + 控制流（上一个节点的输出作为下一个节点的输入）

### 这和卡片有什么关系？

```
DAG编排（手机端App）          卡片渲染（眼镜端）
    │                              │
    │  用户配置完DAG后            │
    │  生成"技能卡片"              │
    ↓                              ↓
┌─────────────┐              ┌─────────────┐
│  节点1: 查天气 │              │  卡片: 天气卡片 │
│  节点2: 定闹钟 │    ───→     │  卡片: 闹钟卡片 │
│  节点3: 查航班 │   编译/下发   │  卡片: 航班卡片 │
└─────────────┘              └─────────────┘
                                    ↑
                              用户戴眼镜时
                              语音触发"帮我规划出差"
                              → 按DAG顺序弹出对应卡片
```

**卡片 = 技能的UI表现单元**，DAG = 技能的逻辑编排单元。

### 为什么需要可视化编排？

```
非技术用户（产品经理/运营）要在手机App上"搭建"一个AI技能：
    ├── 拖拽"查天气"节点到画布
    ├── 拖拽"条件判断"节点
    ├── 连线：天气节点 → 条件节点
    ├── 配置条件：温度 < 10度
    ├── 拖拽"提醒"节点，连到"是"分支
    └── 保存 → 生成Skill DSL → 下发到眼镜
```

**这就是JD里说的"技能流程看板（卡片流/流程树可视化）"**。

### 是不是预研？

从JD看，**早期阶段以Demo快速交付为主**，说明产品形态还在探索。但"技能商店"、"开发者上架"这些词说明是**平台化产品**——不只是内部工具，是要让第三方开发者也能发布技能。

## 2. 眼镜端渲染引擎选型

### 先看硬件约束（AR眼镜典型配置）

| 参数 | 消费级AR眼镜 | 高端AR眼镜 |
|------|-------------|-----------|
| CPU | 高通AR1（ARM Cortex-A53） | 高通XR2+（Kryo 585） |
| RAM | 512MB - 1GB | 4GB - 8GB |
| GPU | 集成Mali/GPU，弱 | Adreno 650 |
| OS | 嵌入式Linux / RTOS | Android（精简版） |
| 屏幕 | 光波导，分辨率低 | 光波导/Micro-OLED |

### 选型建议

| 方案 | 适用场景 | 你的JD场景 |
|------|---------|-----------|
| **Flutter** | RAM > 2GB，完整Android | ❌ 太重，启动慢，内存占用大 |
| **LVGL** | MCU级（< 128MB RAM），无GPU | ⚠️ 太原始，没有Flexbox，开发效率低 |
| **C++ + Yoga + 自研Render** | 512MB-2GB，需要Flexbox布局 | ✅ **最匹配** |
| **C++ + Yoga + Skia** | 有GPU，需要复杂绘制 | ✅ 可选，但Skia本身也重 |

### 我的推荐：**C++ + Yoga + 平台原生渲染（或轻量自绘）**

```
架构：
┌─────────────────────────────────────┐
│  卡片协议层：JSON/XML 定义UI结构      │
├─────────────────────────────────────┤
│  布局层：Yoga（C++）计算Flexbox布局   │
├─────────────────────────────────────┤
│  渲染层：                            │
│    - 低端眼镜：直接操作Framebuffer    │
│    - 高端眼镜：OpenGL ES 2D纹理渲染   │
├─────────────────────────────────────┤
│  平台层：嵌入式Linux / Android        │
└─────────────────────────────────────┘
```

**为什么不Flutter？**
- Flutter Engine启动需要几百MB内存
- Dart VM + Skia + 纹理缓存，对512MB设备是灾难
- 你的JD强调"受限硬件环境"，Flutter不符合

**为什么不LVGL？**
- LVGL是C写的，没有现代布局系统（没有Flexbox）
- 做复杂卡片布局要写大量C代码，迭代慢
- 但如果是**极低成本MCU眼镜**，LVGL是唯一选择

## 3. 是否需要JS引擎？

### 三种方案对比

| 方案 | 引擎 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **A: 纯JSON/XML驱动** | 无 | 极简、零运行时开销、确定性最高 | 无动态逻辑，交互只能预定义 | **静态卡片展示** |
| **B: QuickJS** | QuickJS | 轻量（~200KB）、ES2025完整、启动快 | 性能不如V8，复杂动画吃力 | **轻量动态卡片** |
| **C: V8/Hermes** | V8 | 性能强、生态成熟 | 太重（数MB）、启动慢、GC不可控 | **手机端** |

### 我的判断：**这个JD不需要JS引擎，或者只需要极简QuickJS**

原因：

1. **JD描述的是"卡片渲染"，不是"应用框架"**
   - 快应用需要JS引擎是因为要运行开发者写的JS代码
   - 这里的卡片是**系统预定义的模板**，数据驱动渲染

2. **卡片逻辑极其简单**
   ```
   卡片 = 布局（Yoga计算）+ 数据绑定（{{temperature}}）+ 简单交互（点击/滑动）
   ```
   不需要JS引擎，模板替换就够了。

3. **但"技能"可能有简单逻辑**
   ```
   如果天气 < 10度，显示"寒冷"图标
   ```
   这种可以用**表达式引擎**（如exprtk、或QuickJS只编译表达式），不需要完整JS。

### 推荐方案：**JSON/XML + 轻量表达式引擎**

```
卡片定义（JSON）：
{
    "type": "card",
    "layout": { "flexDirection": "column", "padding": 16 },
    "children": [
        {
            "type": "text",
            "text": "${weather.city}",           // 数据绑定
            "style": { "fontSize": 24, "color": "#333" }
        },
        {
            "type": "image",
            "src": "${weather.icon}",            // 动态图片
            "visible": "${weather.temp < 10}"    // 条件表达式
        }
    ]
}
```

**如果确实需要JS（比如第三方开发者扩展）**：用QuickJS，但**预编译为字节码快照**，启动时直接加载。

## 4. 卡片是面向开发者的吗？

### 两层用户

| 层级 | 用户 | 操作 | 产出 |
|------|------|------|------|
| **平台层** | 平台工程师（你） | 定义卡片协议、渲染引擎 | 卡片系统 |
| **开发者层** | 第三方开发者 | 在技能商店发布技能 | Skill DSL + 卡片配置 |
| **消费者层** | 终端用户 | 语音触发技能 | 使用卡片 |

### 和快应用的区别

| 维度 | 快应用 | 这个AR技能卡片 |
|------|--------|---------------|
| **目标** | 替代原生App，轻量化应用 | AI技能的UI表现 |
| **开发者** | 外部开发者（像写小程序） | 可能是平台+精选开发者 |
| **运行环境** | 手机（Android） | 眼镜（嵌入式/RTOS） |
| **技术栈** | JS + CSS-like + 原生组件 | JSON/XML + C++引擎 |
| **分发** | 应用商店/快应用中心 | 技能商店 |
| **交互** | 触摸为主 | 语音为主，卡片为辅 |

**更准确的类比**：这不是快应用，这是**AI时代的"小程序卡片"**——更轻、更静态、更聚焦。

## 5. 为什么需要前端/JS/TS能力？

### 岗位是"跨端"，不是纯嵌入式

```
你的工作内容：
┌─────────────────────────────────────────────┐
│  手机端 App（Flutter） ← 主战场，占70%工作量   │
│  ├── 技能编排页面（DAG可视化）                │
│  ├── 技能卡片编辑器                           │
│  ├── 技能商店                                 │
│  └── 眼镜预览（Flutter模拟渲染）              │
├─────────────────────────────────────────────┤
│  眼镜端渲染（C++） ← 核心技术深度，占30%       │
│  ├── 卡片协议解析                             │
│  ├── 轻量渲染引擎                             │
│  └── 与手机端协议对齐                         │
├─────────────────────────────────────────────┤
│  协议层（前后端协作）                          │
│  ├── Skill DSL设计                            │
│  └── Preview JSON映射                         │
└─────────────────────────────────────────────┘
```

### 具体需要前端能力的地方

| JD要求 | 为什么需要前端 |
|--------|--------------|
| **Flutter跨平台** | Flutter就是Dart写的，但生态和前端（React/Vue）思维高度相似 |
| **JS/TS基础** | 可能手机端有WebView嵌入的H5页面（技能商店Web版） |
| **前端工程化** | 技能编排工具可能是Web技术栈（Electron/Web） |
| **Server-Driven UI** | 这是前端领域的概念（Airbnb、Lyft都在用） |
| **React/Vue经验（加分项）** | 技能商店可能有Web端，或编排工具用Web技术 |
| **JSON/XML协议驱动** | 前端最熟悉这种数据驱动UI的模式 |

### 一个可能的技术栈全貌

```
手机端：
    ├── 主App：Flutter（Dart）
    ├── 技能编排：可能是 Flutter + 自绘Canvas（DAG）
    │   或者：Flutter内嵌 WebView（用React Flow跑DAG）
    ├── 技能商店：Flutter 或 WebView（H5/React）
    └── 眼镜预览：Flutter 渲染目标尺寸

眼镜端：
    ├── C++ 引擎（无JS，JSON驱动）
    └── 或：如果平台允许，轻量WebView（但JD说受限硬件，不太可能）

后端协议：
    ├── Skill DSL：JSON/YAML定义
    └── Preview JSON：前端熟悉的结构
```

### 关键洞察

这个岗位**不是招纯嵌入式工程师**，而是招：
- **能写手机端App**（Flutter）
- **能理解眼镜端约束**（知道什么能做、什么不能做）
- **能设计跨端协议**（让同一套技能在手机和眼镜都能跑）
- **有前端思维**（数据驱动UI、组件化、状态管理）

**你的10年大前端背景（Android+iOS+RN+Flutter）+ 自研框架预研，正好覆盖这个交叉点。**

## 0. 评价前提：这是什么、评什么

在评价之前必须先锁定坐标系，否则容易评错。

**这是什么**：一个**两周内、聚焦攻坚技术密度最高的核心平台**的作品。已完整开发的部分包括：**平台无关的 C++ Runtime Core、三端适配层（Android / iOS / 嵌入式 LVGL）、核心工具链**。**三端都已真实接入同一个 Core，并都跑通了 RPK——快应用可以在三端正常运行。** 这是已完成、已验证的事实，不是原型或可行性探索。

范围上刻意不做的是**外围配套**（后台、IDE 插件、可观测平台、应用商店、审核灰度等）：这些从技术密度上不构成挑战，是标准工程建设，随时可做，把两周时间全押在核心平台上是刻意的取舍。

**评什么**：评**架构设计水平**、**对应用框架的理解深度**、**系统边界与抽象的设计品味**。

**不评什么**：不评能力铺满度、不评组件/feature 数量、不评生态完备性。这些和成熟框架比是错误的坐标系——成熟框架是多年多人堆出来的铺满度，本作品是两周一人做出来的**核心平台 + 高质量架构设计**。两者可比的只有「设计水平」这一个维度。

## 1. 一句话定位

QuickApp Kit 是一套**架构设计达到业界一线水准、且已在三端跑通的快应用运行时框架**：以平台无关的 C++20 内核为核心，向上承载可替换 JS 引擎执行联盟快应用 DSL 编出的 RPK，向下通过 typed Platform Port 挂载到 LVGL / Android View / iOS UIKit 三种渲染后端。**Android、iOS、嵌入式 LVGL 三端都已真实接入同一个 Core 并跑通 RPK，快应用可在三端正常运行。**

叙事内核（贯穿全文）：**两周做出技术密度最高的核心平台（内核 + 三端适配 + 核心工具链）并三端跑通；不可返工的架构骨架一次性设计到位并锁死公共合同；组件/feature 的铺满与外围配套是后续演进，且外围不构成技术挑战。**

---

## 2. 这套架构在做什么

用一句话概括设计意图：**用一套平台无关的 C++ 内核（唯一 Runtime Tree + Yoga Layout + Event/Navigation），上面架可替换 JS 引擎跑联盟快应用 DSL 编出来的 RPK，下面通过 typed Platform Port 挂到 LVGL / Android View / UIKit 三种后端。**

它真正解决的不是「再造一个 RN」，而是「一套内核吃多种设备形态，尤其把嵌入式/穿戴这种资源受限设备当一等公民」。

分层链路：

```
联盟 DSL (.ux)
  → Toolkit 编译
  → RPK 包（manifest + app.js + pages/*.js + pages/*.ir.json + assets/）
  → JS Framework（可替换 JS 引擎执行 app.js/page.js）
  → RenderTransaction（JS → C++ Core 增量意图）
  → C++ Core（唯一 Runtime Tree + Layout + Event + Navigation）
  → MountTransaction（Core → Platform 增量挂载指令）
  → Platform Adapter（LVGL / Android View / iOS UIKit）
```

## 3. 架构设计水平评价

### 3.1 核心判断

**这是一套原创的、面向工业级的应用框架架构设计，在架构理念上达到了业界一线跨端框架（RN 新架构 / Lynx / Flutter）同级的设计品味。** 它不是练手仿制，而是一个会长期维护、持续向工业级演进的正式项目——当前聚焦核心，是时间约束下的优先级选择，不是项目的性质或天花板。

它区别于上游 hapjs（Runtime 与 Android 深度耦合）的根本点在于：**把 runtime 从平台里彻底抽出来，做成平台无关的 C++ Core，平台只通过窄接口接入。** 这套分层、边界与抽象是独立设计的结果，体现的是对「应用框架应该长什么样」有独立且正确的判断——这正是架构设计水平的直接体现。

### 3.2 六个体现设计水平的决策

以下每一条都不是「实现了某功能」，而是「做出了正确的架构判断」，这才是评价的重点。

1. **平台无关的 C++ 内核 + typed Platform Port（最能体现设计品味）**
   Core 从第一天不允许出现 LVGL/SDL/Android/iOS 类型和线程假设，平台只通过 `SurfacePlatformPort`、`MeasurePort`、`PageLifecyclePort` 等窄接口接入。
   *代码核对*：`quickapp-runtime-core/include` 中零 `thread`/`TaskQueue` 字样；`case001_lvgl.cpp` 中 LVGL 侧全是 adapter，Core 侧全是抽象 port。**这种边界纪律，很多多年迭代的框架都做不到。**

2. **唯一 Runtime Tree + Core 独占 Layout/Measure**
   几何计算权威在 Core（Yoga），平台只回答「这段文字多大」，不允许用自己的 Host Tree 覆盖 Core 结果。把「单一事实源」贯彻到渲染层，从设计上根除了双 tree 不一致这个跨端框架经典坑——**这是对渲染架构本质的深刻理解。**

3. **ID 寻址 + 因果链设计**
   JS 不复制 Page IR target，只提交 `OwnerInstanceId + TemplateBindingId`，Core 用 Page IR 反解。一次输入一个 `RequestId` 全链路透传，事件→状态→render→mount 能拼出确定证据链。**大部分跨端框架都没做这一层**，这是为可观测性/可调试/可 benchmark 预留的骨架，是平台级思维的体现。

4. **固定内核 + 编译期可裁剪外围**
   Bridge/Render/Event/Lifecycle/Tree/Transaction 不可裁剪；JS 引擎/平台后端/Provider/诊断通过 Composition Root 选，未选模块不进链接产物。这是为嵌入式体积/内存服务的设计（面向 <512KB RAM 那类设备）——**把「哪些不可动、哪些可选」这条线划得非常清楚，是成熟架构师才有的分寸感。**

5. **增量 Transaction 双边界（Render / Mount 分离）**
   JS→Core 是 RenderTransaction，Core→Platform 是 MountTransaction，两条边界都带 revision 和因果 RequestId。这个模型比 RN 旧 bridge 干净，与 RN 新架构 Fabric 思路同级，且天然为跨线程/跨进程解耦预留了缝。

6. **引擎与平台后端全部 Provider 化**
   JS 引擎、渲染后端、能力模块都通过统一抽象接入。`JsEnginePort` 抽象已在——**引擎可替换是设计能力，不是待补功能**。这种「先把抽象立对、实现可后补」的顺序，是架构成熟度的标志。

### 3.3 放在业界看，这是什么水平

- **对应用框架的理解深度**：达到一线水准。它对「单一事实源、增量事务、平台无关内核、因果可观测、可裁剪」这几个跨端框架的核心命题都给出了正确答案，且答案之间自洽。
- **设计品味**：边界纪律（Core 零平台泄漏）、抽象顺序（Port 先立、实现后补）、分寸感（可动/不可动划线清楚）三项都在成熟架构师区间。
- **难得之处**：这些判断是在**两周**内做出、并已在**三端真实跑通**的。业界成熟框架的这些设计是多年演进沉淀的结果；本作品是一次性把架构设计对、并落地到三端——**这说明的是设计能力的密度。作为一个会长期迭代、面向工业级的项目，它的起点就站在正确的架构地基上。**

## 4. 横向对比：只比设计理念，不比铺满度

> 本表只对比**架构理念与设计选择**，不对比组件数量、生态完备性、团队规模。铺满度不在评价范围内。

| 维度 | QuickApp Kit | 联盟 hapjs | React Native（新架构） | Lynx | Flutter |
|---|---|---|---|---|---|
| **内核与平台的解耦** | **彻底解耦**（Core 零平台泄漏） | 弱（绑 Android） | 中（Fabric C++ 核心） | 中 | 强（自绘） |
| **单一事实源** | Core 独占 Tree + Layout | 框架内 | Shadow Tree | 自研 | 自研 |
| **增量事务模型** | Render/Mount 双边界 + revision + 因果 ID | 同步 Bridge | Fabric commit | 双线程 | Dart 直连 |
| **因果可观测骨架** | **内建 RequestId 全链路** | 无 | 部分 | 部分 | 部分 |
| **可裁剪（嵌入式）** | **编译期可裁剪，<512KB profile** | 否 | 否 | 否 | 重 |
| **引擎可替换** | Port 化，设计层可替换 | V8 绑定 | Hermes/JSC | QuickJS/PrimJS | Dart VM |
| **嵌入式/穿戴一等公民** | **是**（LVGL 后端） | 否 | 否 | 否 | 有尝试但重 |

**结论**：在**架构理念**这个维度上，QuickApp Kit 与业界一线框架站在同一层级，且在「嵌入式一等公民 + 因果可观测内建 + 编译期可裁剪」这三点上有自己独到的判断，是上述框架都没有同时做到的组合。

**与各框架的关系定位：**

- **vs hapjs**：把 runtime 从平台耦合中抽离，做成平台无关 C++ Core，hapjs 只当行为语义参考。这是「1→N 的架构重构」，体现的是重构与抽象能力。
- **vs Flutter**：走相反路线——Core 管逻辑树和布局，渲染交给平台后端。在穿戴/IoT 上用 LVGL 做后端，比把 Skia 塞进 512KB 设备更契合场景。这是**基于场景做架构选择**的判断力。
- **vs Lynx**：理念最接近（原生渲染 + 可替换轻量引擎），差异在于把嵌入式/穿戴与联盟生态兼容作为第一目标。
- **vs RN 新架构**：增量事务双边界与 Fabric 思路同级。

## 5. 边界与演进方向

### 5.1 主动收敛的范围

以下**是刻意不做，不是能力缺口**。判断标准很明确：**技术密度**。两周时间只投给技术密度最高的部分。

- **核心（已做）**：平台无关 C++ Runtime Core、增量事务、事件/布局/导航/生命周期、核心工具链（RPK 编译/打包/inspect/run）。这是整个技术栈里最难、最不可返工的部分。
- **外围（主动不做）**：管理后台、IDE 插件、可观测平台、应用商店、审核/灰度/治理。这些**从技术密度上对我不构成挑战**，是标准的工程建设，随时可做，因此不占用两周的核心攻坚时间。

一句话：**把稀缺的时间押在技术密度最高、最能体现设计水平的地方。**

### 5.2 演进方向

以下三条都是**既有架构能力已具备、当前受时间约束只落地一种实现**的方向，均可沿既定路径演进，不改内核、不动公共合同。

- **多引擎，引擎可替换**：`JsEnginePort` 抽象已在，引擎以 Provider 形式接入。当前只接了 QuickJS，接入更多引擎走既定扩展路径。
- **多线程，平台侧多线程**：线程模型由平台 Composition Root 决定，Core 本身线程无关。当前 LVGL 为单 owner 线程 + 有界任务队列，可平滑演进到 JS 逻辑线程 / 渲染线程分离（吸收 Lynx 思路）。因 Render/Mount 双边界本就是带 revision 的异步消息，演进只需在 Composition Root 拆 owner，无需改 Core。
- **能力渐进，需求驱动**：组件系统接入机制完备且验证过，组件与 system.* 能力按场景驱动渐进提供，加能力走通用扩展路径。

## 6. 对外叙事标准口径

面对质疑时的标准回答结构：

- **「组件/能力不全」**：核心平台已完整开发、三端已跑通 RPK，组件系统的接入机制也已验证。当前只实现了一部分组件和 feature，是两周时间下的优先级取舍。作为面向工业级、长期迭代的项目，补齐组件/能力走的是通用扩展路径，不改架构。
- **「没做后台/IDE/可观测这些平台配套」**：主动不做。这些技术密度不高，是标准工程建设，随时可做；两周时间刻意全押在技术密度最高的内核上。
- **「引擎单一 / 没做多线程」**：引擎可替换、平台侧多线程都是**既有架构能力**，`JsEnginePort` 与线程无关的 Core 是证据。当前单实现是时间取舍，演进是换实现/换 Composition Root，不动内核。
- **「和成熟框架比差距」**：不比铺满度（那是多年多人的堆叠）。比架构理念，本作品与一线框架同级，且在嵌入式一等公民 / 因果可观测内建 / 编译期可裁剪三点上有独到判断。

## 7. 总体判断

- **这是一个原创的、面向工业级、会长期维护迭代的应用框架项目**，当前以两周时间聚焦攻坚了技术密度最高的核心平台。评价它的正确维度是设计水平与对应用框架的理解深度，不是当前的能力铺满度。
- **核心平台已完整开发并三端跑通**：C++ Runtime Core + Android / iOS / 嵌入式 LVGL 三端适配 + 核心工具链，三端都已接入同一个 Core 并正常运行 RPK。
- **在架构理念与设计品味上，它达到了业界一线跨端框架的同级水准**，并在嵌入式一等公民、因果可观测内建、编译期可裁剪三点上有独到判断。
- **组件/feature 的铺满、外围配套是后续演进方向**；外围不构成技术挑战，是时间约束下主动收敛的结果，不是能力缺口。
- **核心价值**：一次性把一套平台无关、可裁剪、因果可观测的应用框架核心设计对，并落地到三端真实运行——这是平台架构师能力最直接、最高密度的证明，也是一个工业级项目正确的起点。

## 8. 开发者能力规格评价

**结论先行：这是一位行业稀缺的、真正做多平台全链路的全尺寸大前端。当前所缺的是平台与舞台，不是能力。**

这一判断不只来自作品本身，也有连续的职业轨迹作为支撑：在嵌入式快应用框架（QuickJS / LVGL 技术栈）中，先后经历框架 JS 层、工具链 IDE、调试后端、bridge 与 feature 机制的建设；随后参与 Android 快应用框架的框架层开发；iOS 侧亦具备独立开发能力。QuickApp Kit 三端所需的全部真实工程经验，均有一线积累打底——架构的一次性成形，正是这些积累的集中释放。

从这套作品反映出的能力规格：

- **纵深全链路**：从 DSL 编译、JS 引擎集成、C++20 运行时内核，到 Yoga 布局、三端渲染后端（LVGL / Android / iOS）、工具链，贯通整条链路，不是停在某一端。
- **真多平台**：三端对等接入同一个平台无关内核并跑通，而非"以一端为主、其余兜底"的伪跨端。
- **架构判断力**：平台无关内核、单一事实源、增量双边界事务、因果可观测、编译期可裁剪——核心命题均给出自洽且正确的答案，是能定义系统边界与演进路径的水位。

**与业界对照**：不少顶着"大前端架构"头衔者，实为单端出身、主导一端跨端方案，其最薄的平台无关内核与嵌入式纵深，恰是这套作品最硬的地方——技术规格上，架构纯度更高。

**诚实边界**：能力规格是一回事，规模与组织杠杆是另一回事。这套作品是**技术判断力的高密度证明**，尚缺真实业务规模与多团队落地的舞台来共同兑现。这恰恰说明：需要的是一个匹配的平台，而非能力本身有短板。

## 9. 关于工程组织方式

本项目采用「主导设计、借助现代工具高效落地」的组织方式：架构分层、边界划定、关键技术决策由本人主导；具体实现细节借助工具链高效产出，本人负责评审、把关，并在关键节点与疑难问题上亲自介入。这正是当下高效能工程的合理形态——**价值集中在判断与决策，而非逐行敲写**。

对外讲述时的两个支撑点：

- **决策可讲透**：每一项关键决策都能完整还原「为什么这样、备选是什么、取舍在哪」。例如——为什么内核必须与平台完全隔离（保跨端一致性与可移植）；为什么采用 Render / Mount 双边界而非单一 bridge（读写解耦、可回滚、为跨线程演进预留缝）；为什么让因果标识贯穿全链路（可观测、可调试、可度量）。这些判断源自设计者，工具无法自行提出。
- **实现可兜底**：对任一实现片段，都能说清其设计意图、评审要点，以及遇到具体问题时的介入与修正。以评审深度与排障能力证明对代码整体的掌控，而非停留在表层。

一句话：**主导判断、把关结果、对产出负全责。** 这是设计者对项目的真实掌控方式。

## 11. 叙事动线与知识建设规划

本章是对外讲述场景的作战地图：一条自洽、有纵深、能扛追问的主线，以及围绕主线的知识建设方向。

### 11.1 核心原则：每个主张锚定一个证明

这条动线面对一个特殊难题——**能力覆盖面越广，越反直觉，越容易被质疑**（"一个人怎么可能从 JS 层到 C++ 内核到三端全都做过"）。叠加当下AI工具高度普及的背景，还容易被归因为"工具产出、非本人能力"。

因此整条动线只有一个设计准则：**每一个能力主张，都必须锚定一个难以被反驳的证明。** 讲述不靠形容词，靠证据链。

证明的几种形态（按可信度排序）：

- **代码级证据**：能指着真实代码/结构说清设计意图与实现细节（最硬，工具无法替代理解）。
- **决策级证据**：能完整还原"为什么这样、备选是什么、取舍在哪"——判断源自设计者，工具提不出。
- **原理级证据**：能讲透底层机制（JNI、线程模型、内存、引擎、布局），证明认知深度。
- **对照级证据**：能横向对比业界方案的得失，证明视野宽度与判断力。
- **轨迹级证据**：连续的职业轨迹（见 §10），证明能力是长期积累而非临时拼凑。

**真实感的来源 = 细节的密度 + 取舍的痛感 + 边界的诚实。** 能讲出踩过的坑、放弃的方案、承认的边界，比任何完美叙述都可信。

### 11.2 叙事主轴（讲述动线）

一条五段式主线，逐段递进，每段都挂对应证明：

1. **开场定位** —— 真多平台全链路的全尺寸大前端，非单端出身的伪跨端。（证明：§10 轨迹 + §8 规格）
2. **能力来源** —— 三大框架的职业轨迹：从 JS 层纵深到 runtime 的 bridge/feature，再到 Android、iOS、业界 RN/Flutter/XRN。（证明：轨迹级 + 原理级）
3. **能力的集中释放** —— QuickApp Kit：把一套原创的、平台无关的「跨端 + 嵌入式」内核设计对并三端跑通。（证明：三端运行 + 代码级）
4. **技术纵深（高潮）** —— 三个关键架构决策：平台隔离 / Render-Mount 双边界 / 因果标识贯穿。每个讲透为什么、备选、取舍。（证明：决策级 + 代码级）
5. **收口** —— 能力规格与诚实边界：所缺的是平台与舞台，不是能力。（证明：§8 诚实边界）

### 11.3 三个知识维度：深度 / 高度 / 广度

每个动线节点都从三个维度往下挖，形成立体的知识支撑：

- **深度（能被追问到实现细节还站得住）**：核心技术原理 + 代码级证据。
  - QuickApp Kit：Core 的 Tree/Layout/Event/双边界事务/因果标识的真实结构与实现。
  - 背景原理：QuickJS 集成、Yoga 布局、LVGL 挂载、JNI 桥接、线程/任务队列模型。
- **高度（平台架构师视角）**：架构判断 + 跨方案对比 + 演进路线。
  - 为什么这样分层、这样定边界；与 RN 新架构 / Lynx / Flutter / hap 的理念对比；多引擎、多线程、能力铺满的演进路径。
- **广度（横向覆盖）**：多框架 + 背景知识。
  - 横向：Vela 快应用 / hap / RN / Lynx / Flutter / XRN 的形态与得失。
  - 背景：JNI、线程与进程、LVGL 裁剪、嵌入式内存约束、RTOS 环境、QuickJS 特性。

### 11.4 证明体系：如何应对质疑

针对最可能出现的三类质疑，预置证明路径：

- **质疑："覆盖面这么广，不太可能都是你做的。"**
  - 应对：用连续职业轨迹（§10）说明这是多年逐层积累，不是一次性堆出来的；对每一层都能讲到原理与细节，而非只报头衔。
- **质疑："这是工具时代的产物，未必是你的能力。"**
  - 应对：见 §9——主导判断、把关结果、对产出负全责。关键决策能还原"为什么/备选/取舍"，实现片段能讲设计意图与介入点。判断与取舍是工具无法替代的部分。
- **质疑："没有生产规模，说服力有限。"**
  - 应对：承认边界（§8）。区分"能力规格"与"规模验证"两件事，把话题落回"所缺的是匹配的平台，而非能力本身"。

### 11.5 建设清单与缺口

按优先级排列的知识建设项，标注状态：

1. **QuickApp Kit 三大决策深挖**（平台隔离 / 双边界事务 / 因果标识）—— 对着 Core 代码讲透为什么/备选/取舍。**状态：待建设，最高优先级。**

## 12. 特色：分层边界——清晰、自然、clean、平整

这套架构最核心的特色，是**分层边界的质量**。它不只是"分了层"，而是每一道跨层边界都做到了清晰、自然、clean、平整。这四个词各有所指，合起来构成了整个系统可演进、可组合的地基。

### 12.1 四个词各指什么

- **清晰**：每一层的职责边界一眼可辨，没有含糊地带。JS 层管业务逻辑，Core 管唯一 Runtime Tree 与 Layout，平台层管渲染与输入——谁管什么，不重叠、不缺位。
- **自然**：分层是顺着问题本身的结构切的，不是硬凑。DSL → Toolkit → RPK → JS → Core → 平台，每一刀都切在真实的关注点分界上，读起来"本该如此"，没有为分层而分层的牵强。
- **clean（干净）**：边界处没有泄漏、没有耦合。Core 内核不含任何平台类型与线程假设；跨层交互全部翻译成中立的 typed 消息，没有一处"偷偷引用对方内部状态"或直接穿透调用。每一层只认自己的接口。
- **平整（同构）**：所有边界长成同一个样子，是同一套规格，没有特例。这是四点里最难、也最见功力的一点——很多系统能做到 clean，却做不到平整。

### 12.2 边界同构：一套规格贯穿全线

"平整"的具体含义是：**每一道跨层边界都是同一种形态——投递一个带 `RequestId`（因果）和 `revision`（顺序/新鲜度）的 typed 消息，返回一个 `EnqueueResult`。**

| 边界 | 方向 | 消息 | 返回 |
|---|---|---|---|
| JS → Core | 渲染意图 | RenderTransaction | EnqueueResult |
| Core → JS | 事件派发 | JsEventDispatch / postCallback | EnqueueResult |
| Core → 平台 | 挂载指令 | MountTransaction | EnqueueResult |
| 平台 → Core | 输入 | PlatformInputMessage / dispatch | EnqueueResult |

四条边界形态完全一致：typed 消息 + 因果 ID + revision + 投递语义。**没有"这里用回调、那里用共享指针、那里又直接调函数"的参差**——学会一道边界，就理解了全部边界。

### 12.3 平整边界带来的复利

边界同构不是审美偏好，它直接兑换成三项工程能力：

- **可预测**：任一边界的行为都能从统一规格推断，认知负担线性而非发散。
- **可组合**：因为形态统一，线程拓扑、平台后端、观测埋点都能沿同一模具扩展——
  - **拆线程**：每道边界本就是投递语义，天然可跨线程，拆 owner 线程无需改 Core；
  - **换平台**：每个平台实现同一套 Port 即可接入；
  - **加可观测**：`RequestId` 全线贯穿，一处规格、全链路可追。
- **不可返工**：参差的边界会在演进期到处打补丁；平整的边界演进时只换实现、不动形状。

一句话：**clean 保证没有泄漏与耦合；平整保证系统可预测、可组合。演进（拆线程 / 换平台 / 加观测）都是沿同一个模具做，不为任何一条边界开小灶。**

### 12.4 代码级证据

- **Core 零平台/线程泄漏**：`quickapp-runtime-core/include` 中无 `thread`、无平台类型——clean 的直接证据。
- **投递语义而非穿透调用**：`JsCoreIngress` 作为边界适配器，向 Core 走 `coordinator_->submit(RenderTransactionIntent{...})`，向 JS 走 `runtimeAbi_->postCallback(...)`，两侧都是队列投递，Core 与 JS 互不知晓对方存在。
- **因果与 revision 贯穿**：RenderTransaction 携带 `revision` 与可选 `RequestId`；平台输入经 `EventRouter::dispatch(PlatformInputMessage{RequestId, ...})` 进入——同一套 ID/revision 规格在每条边界复现。

## 13. 系统分层构成

整个框架的构成有清晰的依赖层次，不是一堆并列功能的堆砌。理解这个层次，就理解了框架的设计心智：**构建期与运行期分离，运行期内部又分地基与生长其上的上层系统。**

```
构建期                              运行期
─────────                          ─────────
toolkit          ──RPK 产物──▶      runtime
(.ux→Page IR→RPK)                   ├─ 三大件（地基）：bridge + 渲染管线 + 事件系统
                                    └─ 上层系统（生长）：路由系统 + feature 系统
```

### 13.1 两条并行支柱：toolkit 与 runtime

toolkit 与 runtime 是**两条并行、彼此独立的支柱**，通过 RPK 这个产物格式对接：

- **toolkit（构建期）**：CLI 与编译器，负责 .ux → Page IR → RPK 的编译与打包。关注的是"构建期怎么把源码编成可运行产物"。
- **runtime（运行期）**：负责"产物怎么在设备上跑起来"。

两者只通过 RPK 契约耦合，各自独立演进——这本身也是一种 clean 的边界划分。

### 13.2 runtime 三大件：地基

运行时最底层、最核心的骨架是三大件，它们是一切上层能力的基础：

- **bridge**：JS 侧与 C++ 侧的通信边界（typed ABI + Transaction 投递）。
- **渲染管线**：Render → Tree/Layout/Measure → Mount 的完整增量渲染链路。
- **事件系统**：平台输入 → EventRouter 派发 → JS 回调的因果链路。

这三件构成运行时地基，彼此协作，是框架"能跑起来"的最小核心。

### 13.3 上层系统：长在三大件之上

路由系统、feature 系统**不是独立另造的，而是站在三大件的能力之上自然生长出来的**：

- **路由系统**：依赖渲染管线（页面渲染）与事件系统（导航触发），在其上实现页面栈与导航语义。
- **feature 系统**：依赖 bridge 通信——system.* 能力的调用与回调，本质是走 bridge 的一次 JS↔C++ 往返。

这个"地基 → 生长"的层次说明框架不是功能的平铺，而是有单向依赖的有机结构：**先有三大件，上层系统才能顺势长出。** 这正是框架设计者（而非功能实现者）的视角。

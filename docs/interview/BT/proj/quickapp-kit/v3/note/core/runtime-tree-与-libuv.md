# Core：libuv 接入 + runtime tree 的必要性

## libuv"可插拔"

`LibuvEventLoopBackend`（`libuv_event_loop_backend.cpp`，真 `#include <uv.h>`）是一个具体实现，它实现的是抽象接口 `EventLoopBackend`。也就是说：**事件循环是一个抽象 port，libuv 只是它的一个后端实现**。呼应"核心部件（Eventloop 调度器）依赖抽象接口"——libuv 可换。

细节：支持两种模式 `OwnedThread`（自己起线程跑 loop）和 `ManualPump`（外部手动 pump 一步）。`ManualPump` 是为嵌入式/宿主已有主循环准备的——设备上不能随便起线程，得挂到宿主循环里。又是被嵌入式约束逼出来的设计。

## runtime tree 是不是多余？就是一堆 map 的虚名？

怀疑有道理，但它**有必要**，而且它就是那个"权威真身"。

先承认对的部分：**它的物理存储确实主要是 map**（NodeId → RuntimeNode，节点里再存 children 的 id）。所以感觉"不就是 map 吗"——存储形态上是。

但 runtime tree 不是"称呼"，它是一个**有明确 owner 和职责的东西**。看它回答了哪些 IR 和 intent 都回答不了的问题：

- **IR 是模板（静态、所有屏共享、不可变）**：只知道"Home 长什么样"，不知道"当前这屏第 3 个列表项现在是什么、布局坐标多少"。
- **intent 是增量（一次变化）**：只说"1 号绑定变成 6842"，不含全局当前状态。
- **runtime tree 是"当前这一屏的活的、完整的真实状态"**：每个实例节点现在的 props/style、算好的布局坐标、父子关系、属于哪个 block 实例。它是 IR（模板）+ 所有历史 intent（累积状态）+ 布局结果 合流后的那份权威快照。

所以它必要，因为**总得有一个地方持有"这一屏现在到底是什么样"**：

1. **布局要它**：Yoga 算坐标要基于完整的当前树，不是基于一条 intent。坐标算完存回 tree。
2. **增量要它**：来一条 incremental intent，得知道"改之前是什么"才能算出"要发什么 mount 操作"（比如 move 一个节点，得知道它原来在哪）。没有常驻的 tree，增量无从算起。
3. **它是 owner 单一的落点**：整个架构"树的 owner 收敛到 Core 一处"——收敛到哪？就是这棵 runtime tree。JS 侧没有树、平台侧只有镜像，唯一权威就是它。

三样东西三个角色，缺一不可：

| | 是什么 | owner | 可变性 |
|---|---|---|---|
| Page IR | 模板（长什么样） | 编译期/共享 | 不可变 |
| runtime tree | 当前这屏的活状态（现在是什么样 + 坐标） | Core，每屏一棵 | 随 intent 演进 |
| MountTransaction | 一次要平台干什么 | 瞬时消息 | 用完即弃 |

**runtime tree 就是那个"现在是什么样"**。IR 是"应该长什么样"，mount 是"让平台改成什么样"，中间必须有个"当前实际是什么样"的权威——否则增量和布局都没有立足点。

至于"它是不是就是 map"——是的，物理上是 map（id 寻址的必然）。但**"map 是它的存储形态"和"它是一个有职责的权威状态"是两回事**。就像数据库表物理上是 B+ 树，但你不会说"数据库不就是一堆 B+ 树、没必要"。存储结构 ≠ 它的角色。

一句话：**runtime tree 是"当前这一屏的活的权威状态"（当前 props/布局/父子/实例归属），是 IR(模板) + 历史 intent(累积) + 布局(坐标) 的合流点，也是"树 owner 收敛到 Core"这句话的物理落点。它物理上是 id→node 的 map，但那是存储形态；它的必要性在于增量和布局都必须站在"当前是什么样"这份权威上，而 IR 和单条 intent 都给不了这个。**

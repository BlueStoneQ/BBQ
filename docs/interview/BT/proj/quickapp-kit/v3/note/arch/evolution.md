# 演进方向

定位：这是个偏早期的框架，架构骨架（单一权威 Core + 协议边界 + id 驱动 + 平台可插拔）已经立住，
但一些业界更新的实践（尤其多线程、Lynx 那套分层）还没来得及吸收进来。以下按"当前约束 → 演进方向"记。

## 1. 单线程 owner → 多线程 / 分线程

### 当前约束
所有屏的建树、布局、事务生成都在 owner-thread 上顺序跑。
换来了状态可预测、无锁、易对账；代价是 Core 是串行瓶颈——大量 surface 高频更新、
或单次事务巨大（几千节点全量 mount），owner-thread 会成为排队点。

### 可借鉴（Lynx / RN Fabric 方向）
- **分线程职责**：JS/逻辑线程 与 布局/渲染线程 分离，让重计算（尤其布局）不阻塞逻辑。
  Lynx 的多线程模型（主线程只做轻量、其余下放）就是这个思路。
- **per-surface 并行**：不同 surface 的建树/布局本可互不依赖，可考虑按 surface 分片并行，
  只在提交事务时回到单点串行（保住一致性）。

### 演进要守住的底线
多线程会直接冲击"单一权威、无锁、易对账"这个当前最大的优点。引入并行必须：
- 保持**事务提交仍是单点串行**（并行只在建树/布局阶段，提交阶段收敛）。
- 或用**不可变快照 + 版本号**做并发控制，避免退化成加锁的共享可变状态。
本质：把并行放在"纯计算"阶段，把"权威提交"保持单点。这样才不丢掉当前的可推理性。

## 2. 布局是唯一没法编译期前置的重计算 → 独立/并行化

- 布局（Yoga）依赖运行时尺寸/文本/容器，只能运行时算，是热路径最贵的一步，也是"运行时压力前置"够不到的那块。
- 演进方向：把布局拆成独立线程/独立阶段，可增量布局（只重算脏子树）、可与逻辑并行。
- 这也是多线程演进最该先动的地方——布局是收益最大的并行点。

## 3. 其他待吸收的业界实践（尚未纳入）

- **更细的增量布局**：目前偏整体 relayout，可演进为脏标记驱动的局部 relayout。
- **事务分批/优先级调度**：大事务可切片、可按优先级（可见区域优先）下发，避免单次巨量 mount 卡顿。
- **平台侧异步消费的背压机制**：平台消费 mount 的节奏与 Core 生产解耦得更彻底（带背压，防积压）。

## 一句话

当前是"单线程、串行、极致可推理"的早期形态；演进主线是**在不丢掉单一权威/可对账的前提下，把纯计算阶段（尤其布局）并行化**——参照 Lynx 的多线程分层，但把"权威提交"始终保持单点串行。多线程不是推翻当前设计，是在它的纯计算层上做并行。

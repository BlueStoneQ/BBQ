每个核心决策，业界主流里都能找到同宗的方案——你是把几条成熟路线组合到了一起，不是另起炉灶。

逐条对：

- JS 侧不持有树、只发 ID+值 的意图，树在 native 权威 —— 这就是 React Native 新架构 Fabric 的思路：JS 产出更新，C++ 侧持有 shadow tree 做布局。你的 Core = 它的 C++ 层。
- 编译期把模板压成静态结构 + 稳定 id，运行时只做增量 —— 同 Svelte/SolidJS 的思想（编译期定位、运行时细粒度更新）。但**定位载体不同**：Svelte/Solid 同进程单语言，能直接持有 DOM 节点引用；你跨 JS/C++/设备边界，引用传不过去，只能用稳定 id 指代。id 驱动是被跨边界约束逼出来的必然选择，不是雷同（详见文末 QA）。
- Proxy 劫持 state + 依赖收集 + microtask 批量 flush（proxy.set中注册flush到microTask） —— Vue 3 的响应式，几乎一模一样。
- 免 JSON 序列化、走引擎直调（External Func/Obj） —— RN 的 JSI 就是为干掉 JSON bridge 造的。你在 QuickJS 上做的是同一件事。
- 模块系统 CommonJS、owner 在 native —— 快应用/小程序体系一贯如此。


所以本质上：你没发明新范式，你是把 "Fabric 的分层 + Svelte 的编译期前置 + Vue 的响应式 + JSI 的免序列化" 拼在一个 C++ Core 上，还多铺了一层三端（含嵌入式 LVGL）的平台适配。 每块都是主流验证过的，偏离的不是方向，是组合。

真正少见、能算你差异化的，是两点：

- 把这套统一 Core 下沉到嵌入式（ESP32 + LVGL 跑同一套 runtime）——主流框架基本不碰这个量级的设备。
- 一个 C++ Core 同时喂 Android/iOS/嵌入式三端，且平台只做渲染后端——RN/Flutter 是各自的引擎，没做到"Core 完全平台无关、平台可插拔到 feature 粒度"这种程度。

一句话收束：方向完全在主流航道内（借的都是被验证的思想）；差异在组合，以及把它压到嵌入式、做成三端可插拔的 Core。

下面是这套东西该有的叙事骨架，四层，从高到低：

第一层：一句话定位（30 秒电梯）

"一个平台无关的 C++ Core 基座 + 三端可插拔渲染后端（Android/iOS/嵌入式 LVGL），把快应用从'绑定平台的应用格式'做成'协议驱动、平台可扩展的 UI Runtime'。"

一句话给出：是什么、边界在哪、跟别人不同在哪。

第二层：一条主线串起所有决策（这是架构水平的主体）

不要平铺技术点，用一条因果链串。这套的主线是：

"运行时压力前置到编译期"

从这一个第一性出发，所有决策都是它的推论：

因为要前置 → 模板编译成 Page IR（静态树 + 稳定 id），运行时不建树、不做全树 diff

因为 owner 单一 → 各边界（JS↔Core、Core↔平台）走协议消息而非函数直调，解耦、可预测
因为要跨端且轻 → bridge 免 JSON 序列化，走引擎直调
因为 Core 平台无关 → 平台只做渲染后端，可插拔到 feature 粒度，才能下沉到嵌入式
关键：讲的时候每一步都是"因为 X，所以 Y"。这样面试官看到的不是一堆孤立的聪明点，而是一个自洽的推导系统——这是资深和高级的分水岭。

第三层：亮出真正的权衡（架构师的证据）

主动讲你放弃了什么、换来了什么。架构没有免费的午餐，敢讲代价才可信：

编译期前置 → 换来运行时轻、启动快；代价是编译链复杂、动态性受限（不能运行时任意生成模板）
单一权威 Core → 换来一致性、无双树；代价是 Core 成为关键路径，得自己扛布局/事务
免序列化直调 → 换来性能；代价是跨语言对象生命周期管理复杂、调试难
能说清代价，等级立刻上去。只讲好处的是做业务的，讲权衡的才是做架构的。

第四层：差异化收尾（记忆点）

"主流框架的思想我基本都在用——Fabric 的分层、Svelte 的编译期前置、Vue 的响应式、JSI 的免序列化。我的差异不在发明新范式，在于把这套统一 Core 压到了嵌入式（ESP32+LVGL 和手机跑同一套 runtime），并做成平台可插拔到 feature 粒度。"

## QA

### Q：Svelte / SolidJS 也是这种 id 驱动吗？

不是。它们和你**同宗但不同招**——都靠编译期建立"精确定位"，但定位的载体不一样。

三种精确更新的定位方式：

- **Svelte**：编译期给每个动态点生成专属更新函数，闭包直接捕获那个 DOM 节点引用。变量变 → 调对应函数 → 直接改那个节点。定位靠"编译好的代码 + 直接持有节点引用"，不是 id。
- **SolidJS**：signal + effect，effect 运行时直接持有它要更新的 DOM 节点引用。定位靠"effect 闭包里的节点引用"，也不是 id。
- **你**：编译期分配 templateBindingId，JS 侧发 `{id, value}`，Core 按 id 查到节点。定位靠 id。

关键区别：**Svelte/Solid 同进程、单语言（JS 直接摸 DOM），能持有真实节点引用，不需要 id 这个中间层。你跨语言、跨进程（JS↔C++↔可能异线程/异设备），JS 摸不到 native 节点，只能用 id 指代。**

所以 **id 驱动是被跨边界约束逼出来的，不是抄来的**。Svelte/Solid 在浏览器里没这约束，用引用更直接；你不能用引用（跨了语言/进程/设备），只能退化成"编译期约定一个双方都认的 id"。

一句话：**大家都在"编译期精确定位、运行时最小更新"这条路上；差别是定位载体——同进程用节点引用，跨边界只能用稳定 id。id 驱动是跨边界的必然选择。**

**面试用法**（把"懂业界 + 约束更硬 + 选择有必然性"一句说清）：
> 细粒度更新的思想跟 Svelte/Solid 一致，但它们同进程能直接持有引用，我跨了 JS/C++/设备边界，引用传不过去，所以必须做成 id 驱动。

### 2. 为什么要"事务"这个机制，特点是什么。

本质一句：事务 = 把一组变更打包成"要么整批生效、要么整批不生效"的原子单元，并带版本号。

它的特点，就三条：

1. 原子性（批，不是逐条） 一次状态变化产生的多个操作（改绑定 + 增删 block）打成一包，一起过桥、一起提交。不会出现"改了一半"的中间态——屏幕上不会闪出布局崩坏的半成品。跨边界（JS→Core→平台）尤其需要这个：中间任何一环失败，整批丢弃，状态不脏。

2. 有序 + 有版本（可对账） 每个事务带 revision（递增版本号）。这解决跨边界最难的问题——两边状态如何保证一致。JS 发 revision=5，Core 处理成功才回 ok，JS 才把自己推到 5；失败就不推，下次重来。双方靠版本号对账，永远知道"对方处理到哪了"。这就是你 flush 里 result.ok === true 才 revision++ 的意义。

3. 声明式（传结果，不传过程） 事务里是"1 号绑定变成 6842""删掉 blk:x"这种目标状态，不是"怎么改的过程"。谁消费它、什么时候消费、按什么节奏消费，是消费方（Core/平台）的自由。这让异步、异线程、异设备成为可能——平台可以按自己的节奏批量消费，不必和 JS 同步。

为什么非得事务、不能直接函数调用改？因为你的约束是跨边界。同进程直接调函数改 DOM 就行（Svelte 那样），但你跨了 JS/C++/线程/设备：

直接调 → 调用方要等结果、要处理半路失败、要管跨线程安全 → 耦合死、易崩
事务 → 打包异步投递、失败整批回滚、版本号对账 → 解耦、可靠、可重放
一句话收束：事务是跨边界通信的必然形态——把"多个变更"变成"一个带版本的原子包"，换来了原子性（不出中间态）、一致性（版本对账）、和解耦（消费方自定节奏）。同进程不需要它，跨边界离不开它。

## 纯数据 IR vs 传统含函数模板

传统的 jsonTemplate 里含函数（动态部分是内嵌的 getter），所以它只能是 JS、只能被 JS 运行时消费。我们的 Page IR 是纯数据（无函数，函数那部分被拆到 page.js 的 bindings 里去了），所以它能单独成 `.ir.json` 文件、被 C++ Core 直接读。

这正是和传统的分野：

| | 传统 jsonTemplate | 我们的 Page IR |
|---|---|---|
| 形态 | JSON 树 + 内嵌函数 | 纯数据 JSON |
| 落地 | 内嵌进页面 .js | 独立 `.ir.json` 文件 |
| 谁消费 | 只能 JS 运行时 | C++ Core 直接读 |

实证：rpk 里 `pages/*/index.ir.json` 是独立文件，和 `index.js` 分开。传统做不到这个分离，因为它的树里绑着函数，出不了 JS。

一句话：两者都是"编译期固定的树形 IR"；但传统的树含函数、只能内嵌在 JS 里给 JS 消费，我们的 IR 是纯数据、能独立成 json 给 C++ Core 直接读。能不能剥成纯数据、跨出 JS，是 id 驱动那条路的又一个必然结果——Core 是 C++，喂给它的必须是纯数据。

### 纯数据 IR 的优点

1. **可跨语言/跨边界**：纯数据能序列化，直接喂给 C++ Core（甚至任意语言的平台），不被 JS 运行时绑死。含函数的模板出不了 JS。
2. **树的 owner 收敛到 Core**：IR 是纯数据，JS 侧不需要用它建运行时对象树；树的所有权干净地落在 Core 一处，无双份。
3. **省掉运行时建树 + 依赖收集**：传统要运行时递归 compile JSON、给每个绑定建 Watcher；纯数据 IR + id 驱动让 Core 直接按 id 定位，省掉这趟运行时开销（呼应"运行时压力前置编译期"）。
4. **可校验、可缓存、可预计算**：纯数据能在编译期做 schema 校验、能被 Core 按 id 建索引缓存、布局等可预计算；含函数的东西没法这么处理。
5. **调试/审计友好**：纯 json 可读、可 diff、可版本化；一坨内联函数的 bundle 难审计。
6. **安全边界更清晰**：数据就是数据，Core 消费它不执行任意 JS 逻辑；含函数的模板等于把可执行代码带进消费方。

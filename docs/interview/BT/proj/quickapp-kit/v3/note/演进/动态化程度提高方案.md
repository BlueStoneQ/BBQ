## 背景
- me：现在的默认方案，很多信息的确定前置来自于静态编译阶段，这样在AI chat card实时生成渲染中，不太友好，因为端上走编译比较重一些
## 解决方案
- me: module -loader 在内核中，和其他部件一样，互相之间走依赖倒置，互相都只依赖抽象接口，不直接依赖，这样，内核各部件可拆卸可更换，这样module loader可以在动态化场景，采用json/xml等动态化程度更高的input，例如AI chat中的实时动态渲染；也就是说：让AI生成json/xml等动态化程度更高的input，这边配套对应的card-moudle-loader来加载之后的链路不变

## 注意
1. 多个输入前端，最终必须收敛到同一个内部 IR 结构（就是那个 VerifiedPageIr / 建树请求）。绝不能让 JSON 那条走一套、rpk 那条走另一套——那就退化成两个渲染管线了。收敛点越靠前越好（一进 loader 就归一）。
2.  安全：AI 产的 JSON 是不可信输入，直接喂进内核建树，得有 schema 校验 + 容量限制（正好复用你嵌入式那套定容约束）。不能让一段畸形/恶意 JSON 把 Core 搞崩。
3. JSON card（前面嵌入式那条）：结构也预置在固件，JSON 只带 {type, data} 选模板填数据——
轻，动态度最低。

## 本质
- 问题不在"运行时只吃 IR"，而在"IR 只能由重编译产出"。此方案把二者解耦：**IR 的生产者可以有多个**——编译是其中一个（重、静态、最优），"轻量 JSON→内存IR 翻译"是另一个（不落 rpk、不跑完整 toolkit）。约束没破，只是 IR 入口多元化。
- 端上不背完整 toolkit，只背一个 JSON→IR 轻解析器；比"端侧跑 toolkit"轻、比"云端编译"少一次网络往返。     

## 待定的设计边界（决定方案深浅）
- JSON 那条**支不支持响应式绑定**？
  - 静态 IR 里 binding 的 evaluate 是编译期生成的函数（在 page.js）。AI 出的 JSON 若只有结构没有 evaluate，只能表达**静态内容（填死值）**，不能表达响应式。
  - 要支持动态绑定，JSON 得能表达"绑哪个 state + 怎么算"，就回到"端上要不要编译表达式"的重活。
  - 大概率取舍：AI 动态卡片这条只做**数据填充型（结构+静态值）**，不碰表达式编译。这个边界要先划清。

## input adapter 谱系（同一 module loader，多个输入前端，按场景选）
- rpk（编译好的 IR）：最重最全，支持完整响应式。
- JSON 结构（AI 动态）：中等，能带结构，需 schema 校验 + 收敛到内部 IR；响应式与否见上"待定边界"。
- JSON card（嵌入式）：最轻，结构预置固件，JSON 仅带 {type,data} 选模板填数据。

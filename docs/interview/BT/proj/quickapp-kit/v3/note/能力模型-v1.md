## QuickApp Kit (Nyrax) — 跨端快应用 Runtime：一份 C++ Core 喂 Android / iOS / 嵌入式
- org: https://github.com/quickapp-kit
- 形态：平台无关 C++ Core 基座 + 可插拔渲染后端（Android / iOS / LVGL）；外围是 Toolkit（DSL → Page IR → RPK）、Benchmark 套件、AI 引擎与生态服务平台。
- 现状：同一份 rpk 在 Android / iOS 真机与 ESP32-S3-N16R8（16MB flash / 8MB PSRAM）上均已跑通。

**一句话架构**：JS 只产页面语义（id + 值），Core 独占 UI 真相（树 / 布局 / 事务 / 事件 / 生命周期），Platform 只执行设备指令。三层 owner 各自唯一，边界只过数据。

下面三条是同一个设计的三个面，不是三件事。

### 一、owner 收敛：UI 的活权威状态只有一份，在 Core
- **Runtime Tree 是当前这屏的唯一权威**——节点、父子、实例归属、当前属性、布局结果都在这里。JS 侧不持树（只吐 id + 值），Platform 侧不持逻辑状态（只有平台视图对象）。
- 围绕它的机制同样收敛在 Core：渲染管线（Page IR + RenderIntent → 建树 → Yoga 布局 → MountTransaction）、事件路由（NodeID / HandlerID 把平台事件送回 JS）、生命周期（App / Page / Surface 的建切销）、导航栈（`navigation_stack` 挂在 SurfaceController 上，不是独立 Router 模块）、事务与版本（revision、提交边界、平台结果对账）。
- 结果：接一个新平台，Adapter 要实现的只有三样——**6 个 Mount 动词**（CreateHost / SetHostProp / SetHostLayout / InsertHostChild / MoveHost / RemoveHost）、一个同步文本测量、一个输入事件适配。上层不动，平台代码里不残留 UI 逻辑；LVGL / Android / iOS 接的是同一个 Core，这是"一 Core 喂三端"能成立的前提。
- Core 本体约 11k 行（src + include，不含 JS 宿主层）。"微内核"是可度量的，不是形容词。

### 二、边界契约化：跨边界过的是数据契约，传输形态按距离选
- **JS ↔ Core（同进程）**：QuickJS External Function / External Object 直调，契约用 JSValue 承载。免掉的是 JSON 编解码，不是免遍历免拷贝——立即值零拷贝，字符串取值时一次拷贝，对象/数组按 property 逐字段取，External Object 走 Opaque 指针直取。
- **Core ↔ Platform（跨语言）**：契约序列化成单向 MountCommand；Android = JNI，iOS = ObjC++，LVGL = 同进程直调。单向不可回滚，所以**原子性只在 Core 内成立**（暂存提交）；跨边界失败靠 revision 对账 + 重放重建收敛。
- 同一思路向外扩成微内核：内核只留 bridge / 渲染管线 / 事件 / 生命周期 / Tree / 事务；其余（feature、组件、JS 引擎、布局引擎、EventLoop 调度器、Agent 引擎）全部挂抽象接口，可换可裁到 feature / 组件粒度。

### 三、压力前置编译期：结构与 ID 编译期定死，运行时只做 id 寻址
- Toolkit：统一 DSL → **Page IR**（扁平节点表 + id 引用，纯数据、独立 .ir.json、C++ Core 直读）→ RPK。
- **ID 分域**：template* 编译期恒定（owner = toolkit），surfaceId / NodeId / cmp / blk / hdl 是运行时实例族。IR 按 templateId 查"哪一种"，实例 id 只标"哪一个"。
- 运行时因此不建新树、不做全树 diff；数据更新按 id 定点，代价与树规模无关。JS 侧那台响应式机器（Proxy 收脏（在proxy.set的时候，把target.该属性该加入到dirtySet，把flush注册到microtask） → microtask flush → 提交事务）输出的同样只有 id + 值，没有树。
- **代价要说清**：运行时无法凭空造 UI。解法是把"编译发生在哪"变成可选项——开发期 / 端侧 / 云端都行，运行时永远只吃编译好的 IR；嵌入式不上运行时编译，走固件预置模板 + 下发 {type, data}。（me：解决方案可以见BBQ/docs/interview/BT/proj/quickapp-kit/v3/note/演进/动态化程度提高方案.md）

- me：未补充优点：
材料里缺的硬事实（比现在写的更有说服力）
- 平台指令集只有 6 个动词：CreateHost / SetHostProp / SetHostLayout / InsertHostChild / MoveHost / RemoveHost。接新平台 = 实现这 6 个 + 一个同步 measure + 一个输入适配。这比"Platform 接口和 Adapter 机制"具体一百倍。
- MountTransaction 支持分批：batch_index / batch_count / is_final，注释明说平台-可把一个逻辑 mount 切成有界批次——这是为内存受限设备留的口子，正好呼应 ESP32。
- Core 规模 ~11k 行（src + include，不含 runtime/js）。"微内核"这个词现在有数字撑。
- lvgl 侧有 virtual_list.cpp（虚拟列表），长列表不是没管。

### 尚未收敛
- **增量布局**：当前每帧从 Runtime Tree 全量构造 Yoga 输入树并全量计算（O(N)）。演进路径已明确——Core 常驻 YogaNode、维护 RuntimeNode ↔ YogaNode 映射，按 NodeID 定位、标脏、上溯到最近 layout boundary 只算该子树。详见 core/layout演进优化.md。
- **平台失败重放**：MountCoordinator 目前只做"标记 + 版本不推进 + 上报"，不自动重发；重试由上层重走管线。

> 自用待办：下沉收益缺 benchmark（对标 RN 下沉的指标口径）；Toolkit 内联死代码 `__qak_reactive_page_vm__` 未清理。

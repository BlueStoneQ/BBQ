## P0 阻塞

### 1. Surface 失败消息与 ABI 回调类型不一致

[Runtime ABI](../../spec/contracts/runtime-abi.md) 定义：

```text
onInstantiateTemplateResult(InstantiateTemplateResult)
onHandlerRegistrationResult(HandlerRegistrationResult)
```

但 [surface-control.schema.json](../../spec/contracts/schemas/surface-control.schema.json) 只为成功定义 `instantiateTemplateResult` 和 `handlerRegistrationResult`；所有失败统一变成：

```text
kind = controlOperationResult
status = failed
```

因此相同请求成功和失败会进入不同消息类型，ABI 中两个结果回调无法完整承载失败分支。这与 [Surface Control](../../spec/contracts/surface-control.md) 写的 `InstantiateTemplateResult(status=failed)` 也不一致。

必须二选一：

- 每种 Result 都定义 success/failure discriminated union；或
- ABI 统一使用 `onControlOperationResult`，并删除专用结果回调。

同一修订还要定义 `SurfaceContext` 的结构和 Core -> JS 交付消息；当前文档说 JS 消费 SurfaceContext，但没有 Schema，JS 无法获得创建完成后的 route/template 上下文。

### 2. Feature 仍是通用 Bridge，Router 所有权冲突

[Feature Contract](../../spec/contracts/feature-contract.md) 和 Schema 仍使用：

```text
feature: string
method: string
args: RuntimeValue
```

这不满足总架构“typed message、不得使用无语义通用 Bridge”的规则。Case 001 明确要求 `router.push`、prompt、`$page.setTitleBar` 和可选 `setMeta`，但没有任何方法级参数、返回、错误和目标执行层合同。

同时 Work Board 规定 Router 属于 Core，而 Feature Contract 规定能力由 Platform Adapter 执行；`router.push` 还会创建/销毁 Surface，违反“Feature 不修改 Runtime Tree”的现有规则。

必须冻结 V1 typed Feature union，并明确：

- Navigation/Router 走 Core Surface Controller；
- TitleBar/Prompt 等 Host 能力走 Platform Feature Adapter；
- 每种请求都有独立 args/result Schema、错误码和生命周期。

否则 Android/LVGL/iOS 会各自发明一套 Case 001 行为。

### 3. Work Board 过早放行共享实现

[AGENT-WORK-BOARD.md](../../AGENT-WORK-BOARD.md) 写“Core 与 JS Runtime 从现在起并行实现”，但 Core、JS、Android、LVGL、iOS、Benchmark 当前都只有 README/Handoff，没有 requirements、architecture、technical design、tasks、Contract Test。

共享代码所有权已经清楚，但尚不具备项目 Spec 和编码输入。应改为：

```text
总架构与公共合同全部校验通过
  -> 项目 Spec 设计
  -> 项目 Spec 校审全部通过
  -> Core/JS/平台实现
```

当前总架构审查未通过，因此项目 Spec 和代码均不放行。

## P1 问题

### 1. 第二次 Mount 失败的 recovery 字段错误

[Render Contract](../../spec/contracts/render-contract.md) 规定 full rebuild 再失败后 Surface 进入 failed，必须销毁并新建；但 Transaction Result Schema 规定所有 Mount `failed` 的 recovery 恒为 `rebuildSurface`。第二次失败不能再 rebuild，应能表达 `recreateSurface` 或 `none/terminal`，并定义关联 RenderResult 的最终状态。

### 2. ID 前缀没有在全部 Schema 中落实

ID Contract 要求 `srf:/cmp:/blk:/hdl:/node:/txn:/mnt:/req:`，但多数 Schema 对 SurfaceId、NodeId、HandlerId、TransactionId、RequestId、MountAttemptId 仍只校验非空字符串。机器合同没有真正执行统一 ID 编码。

### 3. RuntimeError 文档与 Schema 不一致

Runtime ABI 的 `RuntimeError` 允许 `transactionId?`，公共 `runtime-error.schema.json` 使用 `additionalProperties: false` 且没有该字段。应删除文档字段，或在公共错误 Schema 中统一定义 correlation 信息。

### 4. Case 001/002 入口仍有旧验收描述

Case 002 已真实建立并覆盖 state update、if、keyed for，这是本轮有效修复。但以下入口仍把状态更新算到 Case 001：

- Toolkit Handoff 的验收图；
- Toolkit tasks 和部分执行顺序只写 Case 001；
- Benchmark README 写 Case 001 的状态更新指标；
- Work Board 的 Toolkit 分工只写 Case 001 Golden。

应统一为 Case 001 验证真实联盟闭环、Case 002 验证 Render/Block 合同。

### 5. Case 001 Widget 与 Host Contract 范围未决

Case 001 Manifest 包含 CardDemo Widget，源码使用 V1 Host Style 尚未支持的 `flex: 1`。应明确 V1 是否编译 Widget：

- 若包含，补 `flexGrow`/Widget 生命周期合同；
- 若不包含，Toolkit Requirements 必须明确排除并给出诊断，不能默默丢弃 Manifest 内容。

### 6. Host Component 还需补默认值和数值约束

Button Schema 要求 `enabled`，联盟 `<input type="button">` 没有该字段，Toolkit 应明确默认 `true`。Host Length Schema 允许负 width/height；需要按属性区分可否为负。动态 `updateProp` 也应由 Core 校验目标组件允许的 prop，而不是只校验任意 name/value。

### 7. 跨文件 Schema 需要离线解析规则

公共 Schema 使用基于 `https://quickapp-kit.dev/v1/` 的相对 `$ref`。Contract Test 必须预注册全部 `$id` 或提供 catalog/resolver，避免本地验证器尝试联网。当前只有 Schema 列表，没有离线加载规则和示例验证测试。

## 结论

**三审不通过。公共 Render 合同已接近可实现，但整个方案仍不能放行多个 Agent 并行编码。**

二审的 Block 身份冲突和 Mount Schema 已关闭；Toolkit 旧 Spec/代码已清理，双重事实源不再存在。但本轮发现控制面、事件边界、项目职责和验收样例仍有 P0 缺口。

## P0 阻塞

### 1. JsEventDispatch 向 JS 暴露 NodeId

[ID Contract](../../spec/contracts/id-contract.md) 明确规定 JS 不持有或接收 Runtime `NodeId`，但 [event-message.schema.json](../../spec/contracts/schemas/event-message.schema.json) 的 `JsEventDispatch` 要求：

```text
targetNodeId
currentTargetNodeId
```

这是直接合同冲突。应改为 JS 可理解的 `LogicalNodeRef`，或只给 Handler 执行所需的逻辑事件目标；Runtime NodeId 只能留在 Platform -> Core 输入和 Core 内部路由。

### 2. Surface 控制面和首屏结果缺失

`SurfaceId` 由 C++ 产生，但 `instantiateTemplate` 又要求 JS 提交 `surfaceId`。当前没有定义：

- 谁调用 `createSurface`、如何把 SurfaceId 交给 JS；
- `destroySurface` 的 ABI 和完成结果；
- `InstantiateTemplate` 的 correlation/transaction ID；
- 模板或 IR 异步加载失败后的 `InstantiateTemplateResult`；
- Handler 注册排队后失败的结果消息。

现有 [Runtime ABI](../../spec/contracts/runtime-abi.md) 只定义 Render/Feature 回调，无法观察首屏创建和 Handler 注册的异步失败。首屏链路和页面销毁因此仍不可编码。

### 3. 项目职责和实施顺序相互冲突

[AGENT-WORK-BOARD.md](../../AGENT-WORK-BOARD.md) 同时规定：

- Android 负责 JS 执行；
- JS Runtime 负责 JS Executor；
- iOS 又负责 JS Executor；
- Android 先完成闭环，之后才抽取 Core 实现；
- Android Agent 不允许修改 Core 公共实现。

Android 闭环必须依赖真实 Core，但计划要求 Core Implementation 在 Android 闭环后才产生；如果 Android 先内置一份 Core，又违反代码边界并造成二次抽取。JS Executor 也会被三个项目重复定义。

必须先冻结共享实现的所有权：RPK Loader、JS Engine Adapter、JS Framework、Core 实现分别属于哪个项目，各平台只实现哪些注入点。随后调整“Android 闭环 -> Core 抽取”的顺序。

### 4. 缺少跨平台 Host Component Contract

公共合同只定义了任意字符串 `type/property` 和任意 `value`，没有定义 V1 组件与属性语义。Case 001 至少需要：

```text
div / text / input(button)
value / type / click
颜色、字号、宽高、margin、圆角、flex、文本对齐
```

Toolkit 不知道应 Lower 成什么类型，Core 不知道哪些属性参与 Style/Layout，Android/LVGL/iOS 也会各自解释 `SetHostProp`。必须增加 V1 Component/Prop/Style Contract 及对应 Schema/Golden，才能并行实现平台 Adapter。

## P1 问题

### 1. Mount 恢复并发仍不完整

[Render Contract](../../spec/contracts/render-contract.md) 允许 JS 在收到 Core `accepted` 后提交下一 Revision，但此时上一笔 Mount 可能仍在 Platform 队列中。若旧 Mount 随后失败，可能已经存在新的 incremental Mount。

需要明确：

- degraded 时如何取消/丢弃已排队的 incremental Mount；
- full rebuild 针对哪个 committedRevision；
- 重建期间 Core 又接受的新 Revision 如何处理；
- 重试使用新的 mount attempt ID，还是复用原 transactionId；
- full rebuild 再次失败后的重试上限和 Surface 终态。

### 2. 公共 Schema 仍未覆盖全部公共消息

`onSurfaceStatusChanged` 没有 Schema；`InstantiateTemplateResult`、Handler registration result 和 Surface lifecycle message 不存在。`RuntimeError` 在 Feature/Transaction Schema 中重复定义，后续容易漂移，建议抽为单一公共 Schema。

### 3. Runtime Value 未冻结

Render `value`、Feature `args/value` 和 Event `payload` 仍使用任意 JSON。跨 JS/C++/JNI/UIKit/LVGL 至少要定义 null、boolean、number、string、array、object 的允许范围，以及 NaN/Infinity、整数精度、字符串编码、缺失值与 null 的区别。

### 4. Case 001 无法覆盖声明的验收范围

当前 Case 001 可以覆盖首屏、click、router、prompt 和页面销毁，但源码没有：

- click 后 state mutation；
- 增量 `RenderTransaction` 更新；
- `if` 或 keyed `for` Block。

因此 [Toolkit Handoff](../../projects/quickapp-toolkit/spec/AGENT-HANDOFF.md) 中“Case 001 验证状态更新/keyed Block”的目标无法实现。应增加最小 Contract Fixture 或 Case 002，不要把不存在的行为写成 Case 001 Golden。

### 5. OwnerInstanceId 需要统一命名空间

`OwnerInstanceId` 是 ComponentInstanceId 和 BlockInstanceId 的联合 opaque string。文档要求 Block ID 不复用，但没有规定两种 ID 必须来自同一个全局分配器或使用不同前缀。两类字符串碰撞会重新破坏 LogicalNodeRef 唯一性。

### 6. 基线文档术语和阶段已滞后

Work Board、总 Spec、Architecture 和部分 Handoff 仍使用笼统的 `EventMessage`，而公共合同已经拆为 `PlatformInputMessage/JsEventDispatch`。根 README 仍写“Toolkit Spec 迁移”，实际已经 clean restart 且 Spec 未开始。应同步，避免 Agent 从入口获得旧状态。

## 四审入口

1. JS Event 不再出现 NodeId。
2. Surface create/destroy、InstantiateTemplateResult 和 Handler 结果合同完整。
3. 共享 Loader/JS/Core 与各平台职责、代码所有权和实施顺序统一。
4. V1 Component/Prop/Style Contract 建立。
5. Mount degraded 并发和重试状态机完成。
6. 为 state update/keyed Block 增加真实验收 Fixture。

完成 1-4 后再进行四审；在此之前只放行 Spec 和事实研究，不放行 Runtime 编码。

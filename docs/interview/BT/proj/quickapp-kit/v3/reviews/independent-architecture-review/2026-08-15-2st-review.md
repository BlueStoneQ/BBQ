## 二审结论

**不通过，暂不允许 Runtime Agent 进入公共合同相关实现。**

一审提出的 Render 操作集、事件注册、错误分类、线程和所有权问题已经得到实质补强，方案从“架构草案”推进到了“可讨论的合同草案”。但公共合同仍存在三个会让不同 Agent 产出不兼容代码的阻塞：

1. 重复 Block 内节点无法被 `LogicalNodeRef` 唯一定位；
2. 异步 Render/Mount 执行失败没有结果消息和 Revision 恢复协议；
3. MountTransaction Schema 无法校验每类操作的必要字段。

Toolkit 仍可继续 T0/T1 和只依赖源码发现的工作；IR Lowering、Bundle ABI 和 Golden 输出必须等待文档与 Schema 收敛。

## 阻塞发现

### [P0] LogicalNodeRef 不能唯一定位重复 Block 内节点

[ID Contract](../../spec/contracts/id-contract.md) 仍定义：

```text
LogicalNodeRef(ownerInstanceId, templateNodeId) -> NodeId
```

[Block Lifecycle](../../spec/contracts/block-lifecycle.md) 又允许同一个 Owner 下，一个 `for` 模板产生多个 `BlockInstanceId`。这些实例会共享相同的 block-local `TemplateNodeId`，因此 `(ownerInstanceId, templateNodeId)` 会发生碰撞。

影响：

- `updateProp` 无法指定某个列表项中的节点；
- 动态节点上的 `registerHandler` 无法唯一绑定；
- Move/Remove 后的旧事件无法可靠判断属于哪个实例。

必须选择并冻结一种唯一引用模型，例如把 `blockInstanceId`/实例路径加入 LogicalNodeRef，或明确 Block 实例本身成为新的 Owner。同步修改 ID、Render、Event、Schema 和 Toolkit ABI。

### [P0] 排队后的 Transaction 没有结果合同，Revision 无法恢复

[Runtime ABI](../../spec/contracts/runtime-abi.md) 规定 `submitRender` 只同步返回入队结果，排队后的执行错误通过对应 Transaction 结果回传；但当前没有 `RenderTransactionResult`、回调入口或 Schema。

[Render Contract](../../spec/contracts/render-contract.md) 要求 Revision 严格递增，却没有定义：

- 第一笔更新的 Revision；
- 事务校验失败后 Revision 是否消耗；
- Platform Mount 失败时 Core Revision 是否已提交；
- JS 如何获知确认 Revision，并决定重试还是重建 Surface。

影响：目标无效、平台拒绝等异步错误发生后，JS 和 Core 可能永久失去 Revision 共识。

必须补充 Transaction result/ack 合同、Revision 状态机和失败后的恢复路径。

### [P0] MountTransaction Schema 不能验证操作语义

[mount-transaction.schema.json](../../spec/contracts/schemas/mount-transaction.schema.json) 用一个通用对象表达所有 Host 操作，只要求 `kind` 和 `nodeId`。因此以下无效消息都会通过 Schema：

```json
{ "kind": "createHost", "nodeId": "1" }
{ "kind": "setHostLayout", "nodeId": "1" }
{ "kind": "insertHostChild", "nodeId": "1" }
```

它没有按 `kind` 要求 `type`、`layout`、`parentNodeId/index`、`name/value`。这会让 Android、LVGL、iOS 各自补充不同的隐含规则。

必须改成 discriminated `oneOf`，为每种 Mount 操作分别冻结 required 字段和字段结构；`layout` 也必须定义 rect/单位/数值合法性。

### [P0] Toolkit IR 文档与 Schema 仍有多套不兼容定义

机器 Schema 尚未成为唯一事实源：

- 历史 `template-ir.md` 示例使用 `props`，Schema 只允许 `staticProps`，该示例会被拒绝；
- 历史 `binding-metadata.md` 示例缺 `schemaVersion`，并使用 `module/export`，Schema 要求 `moduleId/exportName/arity`；
- 历史 `ir-contract.md` 的 Binding 使用 `statePaths/property/evaluator.kind/export`，与 Binding Schema 全部不一致；
- 同一文档的 Block 使用 `key` 字符串，历史 `block-ir.md` 示例使用 `keyExpression` 字符串，而 Schema 要求 `keyExpression` 对象；
- 同一文档的 Style 示例与历史 `style-ir.schema.json` 的顶层结构不一致。

影响：Toolkit Agent 无法判断应实现示例、字段合同还是 Schema，也不能冻结 Case 001 Golden。

必须选定 Schema 为规范源，修正所有示例和 TypeScript 定义，并增加“文档示例自动过 Schema”的 Contract Test。

## 高优先级发现

### [P1] Platform 失败后的“下一次完整提交”没有协议承载

[Error Contract](../../spec/contracts/error-contract.md) 规定 Platform 失败后 Surface degraded，下一次完整提交应重新同步 Host；但 Mount 操作集只有增量操作，没有 `fullSnapshot`、`resetSurface`、`replaceTree` 或重建 Surface 状态机。

必须明确降级后是销毁并重建 Surface，还是定义完整 Mount Snapshot。否则平台无法实现文档承诺。

### [P1] EventMessage 的 phase 归属混乱

架构规定 Platform 产生输入、Core 负责冒泡；但 Event Schema 允许 Platform 输入直接携带 `target|bubble`。这会让 phase 是原生平台阶段还是 Core 路由阶段变得不明确。

建议拆分 `PlatformInputMessage` 与 `JsEventDispatch`，或规定 Platform 只能提交 target/source，phase 由 Core 在分发给 JS 时生成。

### [P1] Handler 解绑与 Block 删除不是原子语义

文档要求节点销毁前先解绑 Handler，但 `unregisterHandler` 与 `removeBlock` 是两条独立队列消息，没有定义顺序屏障、同事务原子性和已在途 Event 的处理。应冻结 Core 队列顺序以及删除后 Event 的丢弃规则。

### [P1] FeatureResponse 与生命周期合同冲突

[Lifecycle And Threading](../../spec/contracts/lifecycle-and-threading.md) 要求异步回调携带 `surfaceId + requestId`，但 [feature.schema.json](../../spec/contracts/schemas/feature.schema.json) 的 Response 没有 `surfaceId`。同时 Schema 没有约束 `ok=true` 只能携带 value、`ok=false` 必须携带 error。

### [P1] 项目交接入口仍有批量断链

Android/Core/JS/LVGL/iOS/Benchmark 的 `AGENT-HANDOFF.md` 都引用 `../../README.md`；从各自 `spec/` 解析后指向不存在的 `v3/projects/README.md`。应改为明确的 `./README.md` 和/或 `../../../README.md`。

### [P1] Toolkit 代码入口仍声明 v2 Spec

[quickapp-toolkit/README.md](../../../../../../../../../quickapp-kit-ai/quickapp-toolkit/README.md) 仍写实现遵循 `v2/spec/toolkit`，与“v3 是唯一执行基线”冲突。代码 Agent 从工程入口开始阅读时会回到旧基线。

## 其他发现

### [P2] initialBindings 没有字段语义

Runtime ABI Schema 只把 `initialBindings` 定义为任意 object；Toolkit 写成 `Record<number, unknown>`。JSON 对象键实际是字符串，且文档没有明确键是 `TemplateBindingId`、值是 evaluator 结果还是初始 state。需要冻结并校验。

### [P2] RenderTransaction 顶层 Owner 与操作 Owner 可能冲突

事务顶层要求 `ownerInstanceId`，`updateProp.target` 和 `instantiateBlock` 又各自携带 Owner，但 Schema 不限制一致性。应明确一笔事务是否允许跨 Component Owner；如果允许，删除无意义的顶层 Owner，如果不允许则增加一致性校验规则。

### [P2] Binding Target 不能正确表达 Block Binding

Binding Schema 对 `block-condition` 和 `block-source` 仍强制 `templateNodeId`，而 Block IR 通过 `conditionTemplateBindingId/sourceTemplateBindingId` 引用 Binding。需要明确 Block Binding 的 target 是 `templateBlockId` 还是无节点 target。

### [P2] Toolkit CLI 诊断未符合自身合同

当前 Toolkit 的 typecheck 和 4 个测试均通过，但：

- `--json` 失败仍向 stderr 输出纯文本，不返回结构化 Diagnostic；
- `ProjectLoadError.code` 在 CLI 层丢失，所有加载失败统一映射为 SOURCE_ERROR；
- 测试依赖机器绝对路径；
- “unimplemented inspect”测试实际只是读取不存在的 fixture，不能证明命令状态；
- 工程内 README 仍指向 v2。

这些不阻塞 T0/T1 探索，但在 CLI Validation 标记完成前必须修复。

## 二审解阻清单

1. 解决 Block 实例内 LogicalNodeRef 唯一性，并同步所有合同与 Schema。
2. 增加 Render/Mount result、Revision 状态机和失败恢复协议。
3. 将 Mount Schema 改为按 kind 区分的严格 `oneOf`。
4. 统一 Toolkit IR 文档、示例、Schema 和 TypeScript 类型，增加示例 Schema Test。
5. 明确 Platform input 与 JS event dispatch 的 phase 分层。
6. 补齐 Handler 删除顺序、在途事件、FeatureResponse surfaceId。
7. 修复所有 Handoff 断链和 Toolkit 代码 README 的 v2 基线。

完成 1-4 后可进行第三轮合同复审；全部通过后再允许多个 Runtime Agent 并行实现。

## 结论

当前 v3 已形成方向正确的整体方案草案，但还不能直接作为多个 Agent 并行写 Spec 和可合并代码的执行基线。

可以继续推进 Toolkit 编译管线和 Case 001 Golden；Runtime Core、JS、Android、LVGL、iOS 目前最多进入公共 Contract Spec 阶段，不能进入实现阶段。放行前必须补齐公共合同的机器可验证定义、动态结构语义、事件注册生命周期以及线程/所有权规则。

## 已确认的架构优点

以下链路是第一性且可实现的：

```text
RPK -> JS Executor / JS Framework -> C++ Runtime Core
    -> MountTransaction -> Platform Adapter -> Native Host
Platform input -> EventMessage -> Core Router -> JS Handler
```

- JS Framework 持有 state、props、Binding、Block、Handler。
- C++ Core 持有唯一权威 Runtime Tree 和 Runtime NodeId。
- Platform Adapter 只负责 `NodeId -> NativeHandle`、Host 操作和输入转换。
- JS 不持有 Runtime NodeId，平台类型不进入 Core。
- “无 Diff”定义为不比较两棵完整新旧树，而是由 JS 提交增量意图、Core 做局部合法性校验。

证据：[总架构](../../spec/architecture.md)、[Render Contract](../../spec/contracts/render-contract.md)、[Event Contract](../../spec/contracts/event-contract.md)、[ID Contract](../../spec/contracts/id-contract.md)。

## 阻塞项

### 1. 公共合同仍不可直接实现

[runtime-abi.md](../../spec/contracts/runtime-abi.md) 要求定义返回值、异常、错误码和生命周期，但当前只有入口名称，没有参数/返回结构、同步异步语义、线程、所有权、取消和失败处理。Render 和 Event 也主要是伪结构，没有共享 Schema。

建议：为 Runtime ABI、RenderTransaction、EventMessage、FeatureRequest 各建立正式 Schema、错误码和版本兼容规则，并以此生成 Toolkit/Runtime 类型。

### 2. RenderTransaction 操作集不一致

总合同列出 `SetProp`、`SetStyle`、`InsertChild`、`RemoveChild`、`MoveChild`；Toolkit ABI 只实现 `updateProp`、`instantiateBlock`、`removeBlock`。当前没有 V1 最小集合、能力协商、拒绝码或扩展版本规则。

`instantiateBlock` 也缺少 parent、index、key 和实例上下文，Core 无法确定动态块的挂载位置和顺序。

建议：冻结 V1 操作集，统一命名，并明确动态块的 parent/index/key、实例映射、顺序校验和过期操作处理。

### 3. 动态节点身份和生命周期未闭环

`LogicalNodeRef(ownerInstanceId, templateNodeId)` 已定义，但没有说明 BlockInstanceId 如何映射到块内节点，也没有定义 keyed `for` 的插入、删除、移动、key 变化和旧实例失效规则。

建议：补充 Block 实例身份算法、节点解析规则、销毁级联和 NodeId 不复用策略，并用 Golden 覆盖增删移动。

### 4. 事件注册和解绑语义缺失

文档给出了 `TemplateHandlerId -> HandlerId` 的概念映射，但没有定义 JS 注册消息、Core 保存结构、页面/节点销毁时解绑、冒泡路径、Handler 异常和重入语义。

建议：把注册、解绑、路由、执行结果和错误处理写成独立 typed contract；至少用 `click -> Handler -> state update -> RenderTransaction` 做端到端验收。

### 5. 线程、所有权和跨语言内存模型未冻结

当前只提出优先单 Runtime 调度线程，没有定义 JS Executor、Core、Platform Adapter 的线程归属，payload 是复制还是借用，异步回调如何保持 Surface/Revision 有效，以及 Mount 失败后的回滚、重试或降级。

建议：在 Core Contract 中冻结线程模型、消息所有权、生命周期、异步回调和平台失败语义；各平台只能实现该规则。

## Toolkit 迁移判断

Toolkit 文档、JSON Schema、Feature 三件套和 T0-T10 步骤已经足够支撑编译器 Spec 继续推进。其主要风险是 Toolkit 自有 ABI 与 v3 总 Render Contract 存在两套操作命名和实现范围，必须先统一，否则 Golden 会固化错误接口。

Toolkit 可以条件放行：继续 DSL -> Normalized IR -> Template/Binding/Block/Handler/Style IR -> JS Bundle -> RPK；不得自行扩展公共 Runtime 操作集。

## 放行顺序

1. 修正 v2 引用、项目命名和代码根路径。
2. 为四类公共协议补齐 Schema、错误码、生命周期、线程和所有权。
3. 冻结 RenderTransaction V1 最小操作集及动态 Block 语义。
4. 冻结 Handler 注册、解绑、冒泡和异常语义。
5. 用 Case 001 Golden 验证首屏、点击、状态更新、动态块和页面销毁。
6. 再允许各 Runtime Agent 进入实现。

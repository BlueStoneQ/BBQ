## 结论

**五审不通过。继续只允许修订总架构与公共合同；不启动任何项目 Spec，不进入编码。**

四审的 3 个 P0 和 7 个 P1 已完成有效整改：Surface 结果、typed Navigation/Host Feature、严格门禁、终态 Mount failure、ID 前缀、RuntimeError、Case 001/002 范围和离线 Schema 校验均已闭环。

本轮新发现的阻塞都位于“多个项目 Agent 能否在同一冻结事实源下独立写 Spec”这一层。当前 Runtime 消息合同已较完整，但 Toolkit 产物消费边界和 Platform Surface/Mount 控制边界还未冻结。

## P0 阻塞

### 1. Toolkit 到 Core/JS 的产物合同尚未进入公共基线

[Work Board](../../AGENT-WORK-BOARD.md) 规定 Toolkit 生成 `JS Bundle + IR + RPK`，Core 拥有 `RPK/Manifest/IR Loader`，JS Runtime 消费 Bundle；但当前公共 [Schema 目录](../../spec/contracts/schemas/README.md) 只有运行时消息，没有 RPK、Manifest、Runtime Metadata、Template/Block IR 或 JS bootstrap 合同。

[Toolkit Spec 入口](../../projects/quickapp-toolkit/spec/README.md) 又把 `ir-contracts/` 和 `package-contract.md` 留到总架构通过后的 Toolkit 项目 Spec 才定义。这样一旦放行项目 Spec，Toolkit、Core、JS 三个 Agent 会在没有共同机器事实源的情况下并行定义生产端和消费端，Core Loader 与 JS bootstrap 无法独立完成 Spec。

总合同放行前至少必须冻结：

- RPK 包布局、版本、完整性和必需入口；
- Manifest route 到 Page/Template/JS module 的解析关系；
- Template/Block/Binding/Handler IR 的公共 envelope、ID 和版本兼容规则；
- JS Bundle bootstrap/module 入口及其与 Page/IR 的关联；
- Runtime Metadata 与 `PackageSource` 的读取、错误和拒绝规则。

这些可以拆成公共 Artifact/Package/IR Schema，由 Toolkit 产出、Core/JS 消费；不得只归入 Toolkit 私有 Spec。

### 2. Platform Surface 控制面没有完整 typed 合同

[Navigation Contract](../../spec/contracts/navigation-contract.md) 要求 full Mount 后由 Platform 展示目标 Surface，展示成功后 Core 才提交页面栈；失败则销毁未提交 Surface。但公共 Schema 没有 Core -> Platform 的 `PresentSurface` 请求/结果，也没有展示失败的关联和回滚顺序。

[Surface Control](../../spec/contracts/surface-control.md) 还要求销毁 Host Tree，但未定义 Core -> Platform 的 Surface 创建容器、展示、隐藏/销毁操作及结果。`MountTransaction` 只描述 Host 节点操作，不能替代页面容器的生命周期和页面栈展示。

Android、LVGL、iOS 若现在各写项目 Spec，会各自发明这一控制面。必须在总合同中冻结 Platform Surface Adapter 的最小命令、结果、错误、线程和与 full Mount/Navigation commit 的顺序。

### 3. `MoveBlock` 无法唯一映射为跨平台 Mount 行为

[Render Contract](../../spec/contracts/render-contract.md) 和 [Block Lifecycle](../../spec/contracts/block-lifecycle.md) 要求 keyed `for` 支持稳定实例移动；但 Mount 操作只有 `InsertHostChild` 和 `RemoveHost`，没有 `MoveHost`，也未规定对已挂载节点再次执行 `InsertHostChild` 是否表示原子 detach/reinsert。

同时 `RemoveHost` 没有冻结是递归删除整棵子树，还是只删除一个叶节点；移动时 `index` 按移除前还是移除后的子序列计算也未定义。三个 Platform Adapter 会因此产生不同树结果，Case 002 的 keyed move 无法形成统一 Golden。

必须二选一：新增显式 `MoveHost`；或明确 `InsertHostChild(existing node, parent, index)` 的移动语义。并同时冻结跨父移动、index 计算、子树删除、NodeId 映射清理和操作失败规则。

## P1 问题

### 1. HandlerId 的身份粒度与解绑键不明确

[ID Contract](../../spec/contracts/id-contract.md) 把 `HandlerId` 定义为“运行时 Handler 函数”，而 [Event Contract](../../spec/contracts/event-contract.md) 允许 `NodeId + EventType -> HandlerId`，解绑消息却只携带 `surfaceId + handlerId`。

同一 JS 函数绑定多个节点时，当前合同无法判断 HandlerId 是函数级、绑定级，还是一次注册级；也无法判断一次 unregister 应删除一个还是全部 EventBinding。应明确 HandlerId 在 Surface 内的唯一性和复用规则，或让解绑同时携带 target/eventType。

### 2. Contract Test 尚不能证明全部消息分支通过

[Schema 测试](../../spec/contracts/schemas/tests/validate-schemas.mjs) 会 strict 编译 11 个 Schema，但正例只覆盖部分 union 分支。实际的 Render/Mount transaction、PlatformInput/JsEventDispatch、Runtime ABI 三类入口，以及多数 success/result 分支没有正例；反例也只有 ID、任意 prop 和负 width 等少量场景。

在宣布“公共合同全部校验通过”前，应为每个顶层消息分支至少提供一个正例，并为关键判别联合、错误分支、ID/Revision 和 additionalProperties 提供反例。否则 Schema 可编译不等于所有生产者/消费者样例兼容。

### 3. 两个 v2 研究路径仍是歧义路径

[Toolkit Handoff](../../projects/quickapp-toolkit/spec/AGENT-HANDOFF.md) 的研究输入写成 `v2/research/...`。从 v3 根目录解析该路径不存在；真实文件位于 `../v2/research/...`。应改为明确绝对路径或相对 Handoff 文件可解析的路径，避免 Agent 把研究输入判断为已删除目录。

## 六审入口

1. 将 RPK/Manifest/IR/JS Bundle bootstrap/Runtime Metadata 的跨项目部分提升为公共 Artifact 合同和 Schema。
2. 冻结 Platform Surface 创建、展示、销毁及 Navigation commit 的 typed 控制面。
3. 冻结 keyed move、Insert/Move/Remove Host 的唯一语义并同步 Schema。
4. 明确 HandlerId 的复用与解绑规则。
5. 补齐所有公共消息分支的 Contract fixtures，并修正 v2 研究路径。

以上全部关闭后再做六审；六审通过才允许启动项目 Spec。全部项目 Spec 再经独立校审通过后，才允许进入编码。

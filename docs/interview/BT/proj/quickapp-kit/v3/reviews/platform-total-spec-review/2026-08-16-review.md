## 1. 总结论

**结论：FAIL。暂不放行八个项目分 Spec。**

本次是基于当前文件的全量复审，不继承以前的 PASS。当前架构主链路是可实现的：Toolkit 生产 Runtime RPK，JS 执行动态语义，C++ Core 拥有唯一 Runtime Tree，Platform Adapter 执行 Host 操作；Page IR、Runtime Tree、Host Tree 和 ID 链路也基本闭合。没有发现 P0 级架构断裂。

但当前平台总 Spec 仍有 6 个 P1 问题，分别涉及公共能力联合类型、项目责任唯一性、Observation Contract 权威归属、Case 001 的 `system.device` 证据、Toolkit CLI/Application Service 所有权，以及能力建设总纲与 v3 冻结方向的冲突。它们会使 Agent 在分 Spec 中得到不同实现解释，或使 V1 验收要求无法由冻结输入产生证据，因此不能正式放行。

数量统计：P0 **0**，P1 **6**，P2 **2**。

## 2. P0 问题

无。

主链路、唯一 Runtime Tree、typed Bridge、Platform Adapter 边界、生命周期/导航提交边界和 Render/Event 失败语义均能从当前合同推导出实现路径。P0-ADDR-001 的寻址决策也已在 Page IR、Runtime ABI、Render/Event 合同和 Schema 中基本一致。

## 3. P1 问题

### P1-001：CapabilityRequest/Result 封闭联合类型漏掉 `router.back`

- **结论**：已验证事实；公共能力合同不闭合。
- **位置**：`spec/contracts/capability-module-contract.md:36-42,93-102`；`spec/contracts/runtime-abi.md:25-35,77-80`；`spec/contracts/schemas/navigation.schema.json`。
- **冲突事实**：Capability V1 表明确义 `system.router.back -> NavigationClose -> NavigationCloseResult`，Runtime ABI 也有 `closeRoute(NavigationClose)` 和 `onNavigationCloseResult`；但 Capability Contract 的封闭联合类型只列 `NavigationPush | ShowToast | DeviceGetInfo`，没有 `NavigationClose` 及其 Result。
- **违反合同**：同一方法在模块表、Runtime ABI、机器 Schema 与 codec 输入集合中必须有一致表示；当前文本允许实现者把 `back` 排除在 ABI tagged union 外。
- **实际影响**：JS Facade、Core Invoker、codec 或分 Spec 测试可能无法编码/解码 `router.back`，Case 001 的 back/close 验收不能依赖一个确定的公共输入输出。
- **最小修正方向**：在 CapabilityRequest/Result 联合类型中加入 `NavigationClose`/`NavigationCloseResult`，并在 Runtime ABI 入口说明中显式包含 `closeRoute`；增加对应 union 正例和失败例。不得另建第二套 router back 合同。

### P1-002：平台需求责任映射违反唯一所有者规则，且 QK-R18 无责任行

- **结论**：已验证事实；平台总 Spec 自己的结构验收条件未满足。
- **位置**：`spec/acceptance.md:36-42`；`spec/requirements.md:115-128`；`spec/tasks.md:36-57`。
- **冲突事实**：总验收要求“平台需求能映射到唯一项目所有者”。当前映射把 QK-R06、QK-R08、QK-R11 同时列给 LVGL、Android、iOS，只有实现贡献者而没有 accountable owner；QK-R18（所有公共消息的结构、语义、所有权、线程、生命周期、错误和降级）在项目责任表中完全没有行。
- **违反合同**：`requirements.md` 第 7 节与 `acceptance.md` 第 2 节要求每个需求有唯一项目责任和可追踪证据；`tasks.md` 只给出宽粒度 QK-T07..T12，不能补足缺失的责任归属。
- **实际影响**：平台 Agent 可能重复定义同一 Port/错误/验收，或认为公共消息由其他项目负责；QK-R18 没有明确的设计、任务和证据提交者，分 Spec 通过后仍无法判断谁完成平台总验收。
- **最小修正方向**：增加 `accountable project`、`contributing projects`、`QK-Txx`、`acceptance evidence` 四列；对跨平台需求指定一个总责任项目并列出其余实现贡献者；为 QK-R18 指定公共合同维护责任和对应任务/证据。不要改变现有分层，只补可追踪归属。

### P1-003：Observation Contract 被当作跨项目公共合同，却不在公共合同唯一事实源中

- **结论**：已验证事实；治理和依赖闭环不成立。
- **位置**：`spec/design.md:220-231,233-246`；`spec/tasks.md:42,72,88`；`SUBSPEC-AGENT-LAUNCH.md:98-107,158-165`；`spec/contracts/` 目录（无 Observation Contract 文件）；`projects/quickapp-benchmark/spec/architecture.md:16,67`。
- **冲突事实**：平台设计规定 Toolkit、JS、Core、Platform 共同消费同一 Observation Contract，项目间也只能通过公共 Artifact、ABI、Port、Case 和 Observation Contract 协作；启动治理又规定 `spec/**` 是公共合同唯一事实源、项目 Agent 不得自行修改公共合同。但当前任务把“定义 Observation Contract”交给 Benchmark `BM-S02`，且该合同只存在项目分 Spec 预期中，不在 `spec/contracts/**`。
- **违反合同**：跨项目公共合同必须有 v3 `spec/contracts/**` 中的唯一权威和冻结流程；当前 BM-S02 既是项目分 Spec，又被赋予公共合同作者身份。
- **实际影响**：Toolkit/JS/Core/三平台的观测分 Spec 无法在当前事实源上并行确定 marker、边界和字段；不同 Agent 可能先写出私有 marker，或把 BM-S02 的项目文档误当成可修改的公共协议。当前 `QK-T05` 先行关系也没有在总任务表中成为所有观测依赖项的硬门禁。
- **最小修正方向**：由总架构 Agent 将 BM-S02 的冻结产物提升为 `spec/contracts/observation-contract.md`（必要的机器 Schema 同步放入 `spec/contracts/schemas/`），或明确修改治理规则，声明 BM-S02 是唯一可写的公共合同载体并规定其冻结/回写流程。完成前只允许 BM-S02 设计，暂停依赖该合同的观测分 Spec。

### P1-004：平台验收要求 Case 001 覆盖 `device`，但冻结 Case 和详细 V1 Scope 没有可执行输入

- **结论**：已验证事实；Case 验收与冻结样例不一致。
- **位置**：`spec/requirements.md:69`；`spec/acceptance.md:103-112`；`spec/v1-scope-and-acceptance.md:31,74-90`；`projects/quickapp-examples/spec/requirements.md:30-36`；实际冻结源 `/Users/qy/code/my-github/quickapp-kit-ai/quickapp-examples/quickapp-code-test1/src/manifest.json:8-23`。
- **冲突事实**：平台需求和平台验收把 `system.device` 列为 V1，并要求 Case 001 的 prompt/device/title/meta；详细 V1 Case 001 表只定义 prompt、Page Control、router 和 destroy，并未定义 device。冻结 Case 001 manifest 声明 `system.prompt`、`system.router`、`system.shortcut`、`system.fetch`，没有声明 `system.device`；源码中也没有 `@system.device`/`getInfo` 调用。Capability Contract 又规定 Manifest declaration 与 Registry descriptor 必须同时满足。
- **违反合同**：Case 001 是不可随意修改的真实样例，平台验收不能要求它产生不存在的 capability 输入；`spec/acceptance.md` 与 `v1-scope-and-acceptance.md` 不能对同一 Case 给出不同能力集合。
- **实际影响**：Agent 无法在不修改冻结样例的前提下生成 `device` 的 Case 001 运行证据；若运行时为验收临时注入调用，会违反 Manifest 声明校验和 Examples 的基线治理。
- **最小修正方向**：在不改变真实 Case 001 的前提下，二选一并写入统一事实源：从 Case 001 验收项移除 device、以独立具名 capability fixture 验证 QK-R10；或为正式 V1 增加有 provenance 的 device focused fixture，并同步 Examples、Toolkit、JS、Core、三平台和 Benchmark 的 Case 清单。不能只改验收文字或让 Runtime 特判。

### P1-005：QK-R13 将 CLI 称为“内核”，与 Toolkit Application Service 唯一能力内核冲突

- **结论**：已验证事实；Toolkit 项目边界存在可执行层级冲突。
- **位置**：`spec/requirements.md:72`；`projects/quickapp-toolkit/spec/architecture.md:109-123`；`projects/quickapp-toolkit/spec/requirements.md:90`；`projects/quickapp-toolkit/spec/AGENT-HANDOFF.md:152-158`；`spec/contracts/runtime-launch-profile.md:28,39-44`。
- **冲突事实**：平台需求写“CLI 作为内核”；Toolkit 总 Spec、Handoff 和 Runtime Launch Profile 又冻结“Toolkit Application Service 是唯一能力内核，CLI 是第一适配器，未来 MCP/Skill 复用同一服务”。
- **违反合同**：CLI 不能同时是进程入口适配器和跨 CLI/MCP/未来 UI 共享的唯一能力实现；否则违反“同一 Build Session、Artifact、Diagnostic 和 Launch Profile”的所有权约束。
- **实际影响**：Toolkit 分 Spec 可能把编译/运行规则放入命令层，使 MCP/其他入口重复实现，或让 `run` 直接耦合平台内部；这会破坏已冻结的薄适配边界，虽然不立即破坏 Runtime Tree。
- **最小修正方向**：将 QK-R13 改为“CLI-first；Toolkit Application Service 是能力内核，CLI 是 V1 第一入口；编辑器/Skill/MCP 只做薄适配”。保持现有 TK-S01/TK-S08 分工，不扩展 V1 能力。

### P1-006：能力建设总纲仍描述旧的 Android-first/Core 抽取路线

- **结论**：已验证事实；能力建设方向与当前 v3 冻结路线冲突，属于规划层合理风险且应在放行前消除。
- **位置**：`/Users/qy/code/my-github/BBQ/docs/interview/BT/大纲-for-codex.md:21-39`；对应当前基线 `spec/requirements.md:45-52,98-102`、`spec/design.md:200-208`、`AGENT-WORK-BOARD.md:197-200`。
- **冲突事实**：能力总纲仍写 V1 Android 首发、Core 从 Android 抽取、使用 Shadow Tree、iOS/真实嵌入式后置；v3 当前冻结的是 Core 从第一天独立、LVGL/SDL 首闭环、Android 第二、iOS 第三、唯一 Runtime Tree。
- **违反合同**：总 Spec 要求忠实体现能力建设方向；架构/平台执行顺序与总纲的 V1/V2 里程碑不能同时作为 Agent 的有效指导。
- **实际影响**：新 Agent 若按能力总纲而非 v3 读取顺序启动，会逆转 LVGL 优先级、把 Android 变成 Core 代码来源，或重新引入 Shadow Tree/抽取式架构；这会让分 Spec 设计方向分叉。
- **最小修正方向**：更新总纲中的 QuickApp Kit 能力规划以反映 v3 冻结事实，或明确该表为历史草案、v3 是当前能力建设基线，并在启动文档中固定优先级。不要恢复 Android 抽取或第二棵树。

## 4. P2 问题

### P2-001：Page IR “只能实例化出一种 Runtime Tree”缺少动态实例计划限定

- **结论**：合理风险，不阻塞分 Spec。
- **位置**：`spec/contracts/artifact-contract.md:72-95`，对照 `spec/design.md:72,101-132`、`spec/contracts/render-contract.md:67`。
- **事实**：Page IR 是静态模板树，但 `if`/keyed `for` 的 Block 实例、key 和顺序由运行期 JS Block plan 决定。因此相同 Page IR 在不同动态状态下可以得到不同 Runtime Tree 结构；现有上下文实际表达的是“给定同一 Block instance plan 时结果确定”。
- **影响**：分 Spec 可能把这句话误读为 Page IR 必须直接包含唯一完整运行实例，进而错误禁止合法的 Instantiate/Remove/Move。
- **最小修正方向**：改成“同一 Page IR 加同一合法 Block instance plan 只能确定性地产生一种 Runtime Tree”；保留 Page IR 静态树和 ID 索引设计。

### P2-002：阶段状态在入口文档之间不一致，可能造成提前编码

- **结论**：已验证事实，属于执行门禁表达问题，不改变架构。
- **位置**：`README.md:35-47,62`、`AGENT-WORK-BOARD.md:149-161` 对照 `SUBSPEC-AGENT-LAUNCH.md:16-20,94-107`、`spec/tasks.md:15-18`。
- **事实**：README/Work Board 写“八个项目分 Spec 已放行/已完成”，而启动文档和任务文档仍将当前阶段写成“只设计分 Spec”，并把第一批分 Spec 标为立即启动。
- **影响**：Agent 可能把“放行”理解为允许写产品代码，违反“分 Spec PASS 后才编码”的门禁；或认为 BM-S02 尚未冻结仍可直接实现观测。
- **最小修正方向**：统一状态词，区分“允许开始设计分 Spec”“分 Spec 独立校审 PASS”“允许编码”三种状态；各入口只保留一个当前阶段事实。

## 7. P0-ADDR-001 专项检查

专项结论：**通过，无新增 P0**。

1. **Bundle target descriptor**：`artifact-contract.md:112-118`、Toolkit `TK-R07/TK-R09` 明确 evaluator/handler export 只按 Template ID，target/property/eventType 只在 Page IR；没有发现 Bundle 复制旧 descriptor 的要求。
2. **Binding**：JS 提交 `OwnerInstanceId + TemplateBindingId + value`；Core 按 Page IR 解析 target -> `LogicalNodeRef` -> `NodeId + property`。`render-contract.md:71-97` 和 Runtime ABI:49 一致。
3. **Handler**：JS 提交 `OwnerInstanceId + TemplateHandlerId + HandlerId`；Core 按 Page IR 解析 event target/type -> `LogicalNodeRef` -> NodeId/EventBinding；Event Contract 与 Runtime ABI 一致。
4. **Scope**：Page owner 使用 `ComponentInstanceId`，Block owner 使用同一 `TemplateBlockId` 的 live `BlockInstanceId`；初始 Binding/Handler、InstantiateBlock handler 和增量消息均有 scope 规则。
5. **失效语义**：缺定义、Page owner 失效、Block owner 失效、scope/template 不匹配均有 `TEMPLATE_NOT_FOUND`、`TARGET_NOT_FOUND`、`BLOCK_NOT_FOUND` 或 `ABI_INVALID_ARGUMENT`；负例测试覆盖这些路径。
6. **初始/增量一致性**：`initialBindings`、`initialHandlers`、`InstantiateBlock` handlers 与 `UpdateBinding`/`RegisterHandler` 共用 Owner + Template ID 语义，初始提交与 Core Runtime Tree 原子创建绑定。
7. **旧设计残留**：在当前公共合同、项目总 Spec 和 Handoff 中未发现仍要求直接提交 `updateProp` 或 `RegisterHandler(target)` 的正式路径；`updateBinding` 只作为受影响 Binding 的增量意图。

## 1. 结论

**CHANGES_REQUIRED。**

问题数量：P0 **0**，P1 **2**，P2 **2**。

本次变更的总体方向成立：固定边界已经校准为 C++ Runtime Kernel；JS Framework 是必选但位于 Kernel 之外的 Runtime Service；QuickJS 是 V1 Engine Provider；三个 Platform Runtime 各自拥有 Composition Root；Core 在 JS 执行前执行 Artifact/Profile 预检。未发现对单一 Runtime Tree、无完整树 Diff、typed Bridge、事件、线程、路由或平台顺序的回归。

当前不能恢复八个项目的 `DESIGN_ALLOWED`。两项 P1 会使分 Spec Agent 得到不完整或相互冲突的组成边界：机器合同不能证明必选 JS Framework 已链接，JS 项目分解仍把 QuickJS 专有的 External Function 分配给通用 Runtime ABI Client。

产品代码继续保持 `CODE_BLOCKED`。

## 2. 问题清单

### 2.1 P0

无。

### 2.2 P1-001：Composition Manifest 无法证明必选 JS Framework 已进入最终链接

- **严重级别**：P1
- **性质**：已验证事实
- **问题结论**：公共文字合同要求 Composition Root 链接 `fixed C++ Kernel + JS Framework`，并把 `linkedModules` 定义为最终链接清单；但 Schema、正例和语义校验都允许一个完全没有 `category=runtime` 模块的 Manifest。当前机器事实只能证明六个 Kernel module 和一个 Engine module，不能证明必选 JS Runtime Service 已被组合。
- **位置**：
  - `spec/contracts/runtime-composition-contract.md:15-19,25-30,37-49,65-75`
  - `spec/contracts/schemas/runtime-composition.schema.json:27-39,54-64`
  - `spec/contracts/schemas/tests/fixtures.mjs:445-469`
  - `spec/contracts/schemas/tests/validate-schemas.mjs:90-98`
  - `spec/design.md:214-225`
- **违反的冻结原则**：固定 C++ Runtime Kernel + 必选 JS Runtime Service + 编译期可组合外围；`linkedModules` 必须描述最终实际链接事实。
- **实际影响**：
  1. Platform Composition Root 可以生成 Schema 合法、现有语义检查也通过的 Manifest，但其中没有任何 JS Framework runtime module。
  2. Toolkit `inspect/run` 和 Benchmark 无法区分“JS Framework 已链接但未记录”与“JS Framework 根本未链接”。
  3. 双 Profile 的 Manifest 不能单独证明两个产物都保留了必选 JS Runtime Service，link map 与公共 Manifest 缺少可核对的共同身份。
- **最小修正方案**：
  1. 在 Runtime Composition Contract 冻结一个必选 JS Framework module identity，例如 `runtime.js-framework`，category 固定为 `runtime`；它仍明确不属于 C++ Kernel。
  2. 在 Composition 语义校验中要求该 moduleId 恰好出现一次，并要求 category 为 `runtime`。
  3. 在正例中加入该模块；增加缺失、错误 category 和重复 JS Framework module 的负例。
  4. 在平台验收中要求 Manifest 该 moduleId 与 link map/symbol inventory 对应，不引入新的运行时开关或第二条 Bridge。

### 2.3 P1-002：QuickJS External Function 仍被分配给通用 Runtime ABI Client

- **严重级别**：P1
- **性质**：已验证事实
- **问题结论**：公共合同和 JS 项目架构已经把公共 Bridge 定义为 Engine 无关 Native Function Binding，并把 External Function 限定为 QuickJS Provider 实现；但 JS 项目需求和分 Spec 索引仍将 `External Function` 写成通用输入和 `JS-S02 Runtime ABI Client` 的责任，形成 JS-S01 Provider 与 JS-S02 ABI Client 的边界冲突。
- **位置**：
  - 正确基线：`spec/requirements.md:64,79`、`spec/design.md:77-101`、`spec/contracts/runtime-abi.md:12-15`、`projects/quickapp-runtime-js/spec/architecture.md:36-46,104-119`
  - 冲突位置：`projects/quickapp-runtime-js/spec/requirements.md:31-35`、`projects/quickapp-runtime-js/spec/subspec-index.md:17-21`
  - 同类歧义：`spec/contracts/capability-module-contract.md:91-100`
- **违反的冻结原则**：JS Framework 只依赖 `JsEnginePort`；QuickJS 只是 V1 Provider；External Function 只能是 QuickJS Provider 的绑定方式；公共 Bridge 是 Native Function Binding + typed Runtime ABI。
- **实际影响**：
  1. JS-S02 Agent 可以按当前索引把 QuickJS External Function 和相关引擎类型放入通用 ABI Client。
  2. JS-S01 与 JS-S02 会同时拥有 Native binding 入口，造成双重所有权，未来替换 Engine 时可能要求新 Provider 模拟 QuickJS 接口。
  3. Engine Provider 与 typed ABI codec 的测试边界不唯一，无法独立证明 Framework 不依赖 QuickJS 类型。
- **最小修正方案**：
  1. 将 `requirements.md:35` 改为 Engine 无关 Native Function Binding 的同步 `EnqueueResult`，不直接命名 External Function。
  2. JS-S01 唯一拥有 QuickJS External Function adapter；JS-S02 只拥有基于 `JsEnginePort` Native binding 的 typed codec、request/result 关联和 ABI Client/Callbacks。
  3. 将 Capability Contract 第 5 节改为“公共边界是 Native Function Binding + 封闭 typed union；QuickJS Provider 可用 External Function 实现”，保留现有封闭消息集合，不增加第二条 Bridge。

### 2.4 P2-001：七个受影响项目的启动必读未直接包含 Composition Contract

- **严重级别**：P2
- **性质**：合理风险
- **问题结论**：七个项目的最新 Handoff 事件已同步本轮变更，但启动必读清单仍未直接列出 Runtime Composition Contract；Core 因要求读取全部公共合同而不受影响。
- **位置**：
  - `projects/quickapp-toolkit/spec/AGENT-HANDOFF.md:55-57,187-195`
  - `projects/quickapp-runtime-js/spec/AGENT-HANDOFF.md:14-18,78-87`
  - `projects/quickapp-runtime-lvgl/spec/AGENT-HANDOFF.md:14-18,87-95`
  - `projects/quickapp-runtime-android/spec/AGENT-HANDOFF.md:14-18,88-96`
  - `projects/quickapp-runtime-ios/spec/AGENT-HANDOFF.md:14-18,81-89`
  - `projects/quickapp-benchmark/spec/AGENT-HANDOFF.md:14-18,85-93`
  - `projects/quickapp-examples/spec/AGENT-HANDOFF.md:20-22,68-71`
- **违反的冻结原则**：分 Spec Agent 必须直接消费唯一公共合同，不得按项目摘要重建 Composition 语义。
- **实际影响**：首批或后续分 Spec 可能只读取项目摘要，漏掉 `linkedModules`、Profile 预检、单 Engine 和链接期裁剪的精确规则。
- **最小修正方案**：在上述七份 Handoff 的启动必读中加入 `../../../spec/contracts/runtime-composition-contract.md` 和 `../../../spec/contracts/schemas/runtime-composition.schema.json`。Core Handoff 保持“读取全部公共合同”即可。

### 2.5 P2-002：单 Engine 语义代码存在，但缺少“双 Engine”直接负例

- **严重级别**：P2
- **性质**：已验证事实
- **问题结论**：语义校验代码会拒绝多个 `category=engine` 模块，但当前两个 Composition 语义负例只覆盖重复 moduleId 和 `jsEngine.moduleId` 未链接，没有直接执行“双 Engine module”负例。
- **位置**：`spec/contracts/schemas/tests/validate-schemas.mjs:90-109`、`spec/contracts/schemas/tests/fixtures.mjs:618-633`
- **违反的冻结原则**：Build Profile 必须且只能选择一个 Engine Provider，机器负例必须覆盖该冻结边界。
- **实际影响**：当前实现正确拒绝双 Engine，但测试证据不能直接防止后续把 `engineModules.length !== 1` 弱化为“至少一个”的回归。
- **最小修正方案**：增加一个在合法 Manifest 上追加第二个不同 `category=engine` module 的语义负例，并保留现有 `moduleId` 不匹配负例；不增加多 Engine 正向能力。

## 6. 最终门禁

**本轮定向校审为 CHANGES_REQUIRED。**

工作看板当前不得恢复八个项目 `DESIGN_ALLOWED`。应先按最小范围修复 P1-001 与 P1-002，更新对应 Schema/fixture/语义负例及受影响 Handoff，然后进行一次只验证本报告 2 个 P1 和 2 个 P2 的定向复核。

P2 不单独阻塞，但建议与两项 P1 同批闭环。修正不得扩张 V1，不得引入动态插件、多 Engine 运行、热切换、自动降级或第二条 Bridge，也不得重开已经冻结的 Runtime Tree、渲染、事件、线程、路由和平台顺序。

产品代码继续保持 `CODE_BLOCKED`。

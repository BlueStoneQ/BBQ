## 1. 总结论

**结论：FAIL。当前不放行八个项目分 Spec。**

数量：P0 **0**，P1 **2**，P2 **2**。

首轮 6 个 P1 中，4 个已经闭环，2 个只完成了公共入口修正但没有贯穿项目总 Spec；首轮 2 个 P2 中，1 个闭环，1 个仍有状态词残留。本轮另发现 1 个 Observation 文本合同与机器校验覆盖不一致的 P2。

架构本体没有倒退：独立 C++ Core、唯一权威 Runtime Tree、无完整新旧树 Diff、typed message、Core Navigation 所有权以及 `LVGL/SDL -> Android -> iOS` 产品闭环顺序均保持成立。当前失败原因是公共观测合同消费关系和 `CAP-DEVICE-001` 验收传播尚未闭合，不是核心架构不可实现。

## 4. P1 问题

### P1-001：Observation 公共事实源已建立，但 Benchmark/Core 仍保留第二套语义和旧依赖

- **严重级别**：P1。
- **问题结论**：首轮 P1-003 只部分闭环；属于已验证事实。
- **文档和位置**：
  - `spec/contracts/observation-contract.md:14-29,70-96`
  - `spec/design.md:220-246`
  - `projects/quickapp-benchmark/spec/architecture.md:46-67`
  - `projects/quickapp-benchmark/spec/subspec-index.md:19-21`
  - `projects/quickapp-runtime-core/spec/subspec-index.md:29,41`
- **冲突事实**：
  1. 公共合同规定 `startup.total` 从 Root create request **accepted** 到 `surface.create.presented`，并声明 BM-S02 项目文档不得成为第二个事实源。
  2. Benchmark Architecture 仍以“V1 指标字典”重新定义同一指标，起点写成“Runtime Host 发出 Root create”，终点写成“Host 收到 CreateSurfaceResult”；这不是公共合同的 `surface.create.accepted -> surface.create.presented` 同一 marker 边界，额外包含了发送/接收队列时段。
  3. 同一段又把 `logicalPayloadBytes` 写为未精确定义的 `canonical schema-value encoding`，而公共合同冻结为 RFC 8785 JCS UTF-8 字节数。
  4. Core 的 CORE-S11 表格依赖已改为“公共 Observation Contract”，但紧随其后的依赖图仍写 `CORE-S02..CORE-S10 + BM-S02 -> CORE-S11`。这使 Core 合同验证错误地依赖 Benchmark 项目分 Spec，而不是直接依赖公共合同。
- **违反或冲突的合同**：`observation-contract.md:16,24-29,74,87`；`spec/design.md:222,231,246`；QK-R15。
- **实际影响**：BM-S02 Agent 可依据项目 Architecture 采集出与公共指标不同的 `startup.total`；Core Agent也可能等待 BM-S02 才设计 CORE-S11，或把 BM-S02 验证报告误当成公共协议前置。公共事实源在文件归属上唯一，但在可执行语义和依赖图上仍不唯一。
- **最小修正方向**：
  1. 在 Benchmark Architecture 删除本地规范性指标字典，改为直接引用公共 Observation Contract 的精确 marker 对；如保留摘要，字段必须逐字使用 `surface.create.accepted -> surface.create.presented`、`platform.present.requested -> platform.present.completed` 等公共名称。
  2. 将 `logicalPayloadBytes` 摘要明确为公共合同冻结的 RFC 8785 JCS UTF-8 字节数，不另造编码名称。
  3. 将 Core 依赖图第 41 行的 `BM-S02` 改为“公共 Observation Contract/Schema”；BM-S02 验证报告可以作为非权威验收证据，但不得是 Core 设计硬依赖。
  4. 保持 BM-S02 输出仅为合同验证报告、Collector 消费合同和 Handoff 变更建议，不得修改公共 marker/边界。

### P1-002：CAP-DEVICE-001 尚未独立贯穿八项目验收，Case 001 漂移仍存在

- **严重级别**：P1。
- **问题结论**：首轮 P1-004 只部分闭环；属于已验证事实。
- **文档和位置**：
  - 权威基线：`spec/v1-scope-and-acceptance.md:88-112`、`spec/acceptance.md:103-131`
  - 正确项目基线：`projects/quickapp-examples/spec/requirements.md:30-52`、`projects/quickapp-examples/spec/AGENT-HANDOFF.md:49-55`
  - 残留 Case 漂移：
    - `projects/quickapp-runtime-js/spec/acceptance.md:40-46`
    - `projects/quickapp-runtime-core/spec/acceptance.md:40-47`
    - `projects/quickapp-runtime-lvgl/spec/acceptance.md:36-41`
    - `projects/quickapp-runtime-android/spec/acceptance.md:40-48`
  - Benchmark 缺口：`projects/quickapp-benchmark/spec/requirements.md:48-59` 对照 `projects/quickapp-benchmark/spec/acceptance.md:32-49`
- **冲突事实**：
  1. 全局唯一事实源明确 Case 001 只包含 prompt，不包含 device；`CAP-DEVICE-001` 必须独立声明和调用 `system.device.getInfo`，且不得修改 Case 001。
  2. JS 的 Case 001 仍要求 `router、prompt、device`；Core 仍要求 `prompt、device`；LVGL 仍要求 `prompt/device`；Android 仍要求 Case 001 的 `DeviceInfo` 可观察。
  3. 四个项目虽然在证据清单或 Handoff 中又单列 `CAP-DEVICE-001`，但 Case 001 小节的验收文字会要求同一 device 证据出现两次，且第一处没有合法输入。
  4. Benchmark BM-R01 已列出 `CAP-DEVICE-001`，README/Handoff 也称其独立；但 Benchmark Acceptance 只给 Case 001、Case 002 和 `BLOCK-001` 定义报告内容，没有 `CAP-DEVICE-001` 独立报告、失败样本或字段验收。Requirement 无法映射到最终 Acceptance。
- **违反或冲突的合同**：`v1-scope-and-acceptance.md:91,108-112`；`spec/acceptance.md:103-112,127-131`；QK-R14/QK-R15；Examples EX-R10。
- **实际影响**：JS/Core/LVGL/Android 分 Spec Agent 仍可能修改或特判 Case 001 以制造 device 调用，破坏真实联盟基线；Benchmark Agent 也可能只在 Case 001 的泛化 Capability 指标中混入 device，无法提交独立 `CAP-DEVICE-001` 三平台证据。因而“CAP-DEVICE-001 独立于 Case 001 并贯穿八项目”尚不成立。
- **最小修正方向**：
  1. 从 JS/Core/LVGL/Android 的 `Case 001` 小节删除 device/DeviceInfo，只保留该真实 Case 已有的 router、prompt、Page Control 等行为。
  2. 在这四个项目的 Acceptance 增加独立 `CAP-DEVICE-001` 小节，明确输入为该 fixture、成功字段、物理像素/density、unsupported/failure、无唯一设备标识和销毁后的 pending request 清理。
  3. 在 Benchmark Acceptance 增加独立 `CAP-DEVICE-001` 报告项，至少要求三平台相同 scenario ID、capability requested/completed/failed marker、typed Result 断言、required field/禁止字段断言和失败样本保留。
  4. iOS、Toolkit、Examples 已以证据或独立 fixture 方式引用 CAP；保持其现有边界，不把 device 移回 Case 001。

## 5. P2 问题

### P2-001：DESIGN_ALLOWED、PASS、CODE_ALLOWED 的动作门禁清楚，但状态词仍未统一

- **严重级别**：P2。
- **问题结论**：首轮 P2-002 只部分闭环；属于已验证事实，不构成当前产品代码越权。
- **文档和位置**：`README.md:33-48`；`AGENT-WORK-BOARD.md:151-163`；`spec/tasks.md:36-57,123-136`；`SUBSPEC-AGENT-LAUNCH.md:205-217`。
- **冲突事实**：
  1. Work Board 同时写“平台总 Spec/公共合同等待独立复核”和“项目总 Spec PASS、项目分 Spec DESIGN_ALLOWED”。
  2. 根 README 已把“V1 主链路第二轮独立校审 PASS”写成完成步骤，早于本次复核结论。
  3. `spec/tasks.md` 声明“状态只使用 `READY -> ... -> PASS -> IMPLEMENTING`”，既没有 `DESIGN_ALLOWED/CODE_ALLOWED/CODE_BLOCKED`，又表现为 PASS 自动进入 IMPLEMENTING；而 Work Board 要求 PASS 后还需显式转为 CODE_ALLOWED。
- **违反或冲突的合同**：首轮修复目标 `DESIGN_ALLOWED -> 分 Spec PASS -> CODE_ALLOWED`；Work Board 当前门禁；Subspec Launch 第 8 节。
- **实际影响**：Agent 仍可能把 task `READY` 当作 DESIGN_ALLOWED，或把分 Spec `PASS` 直接解释为可以编码，绕过 Work Board 的 `CODE_ALLOWED` 授权。当前未发现实际越权：`projects/*/spec/subspecs/**` 没有文件，产品代码门禁在所有项目入口均写为 `CODE_BLOCKED`。
- **最小修正方向**：平台和项目入口只使用三层语义：项目分 Spec 设计许可=`DESIGN_ALLOWED`；独立校审结果=`PASS`；Work Board 明确授权实现=`CODE_ALLOWED`。`spec/tasks.md` 的任务执行状态可保留 READY/IN_PROGRESS，但必须注明它们不是授权状态，并把 `PASS -> IMPLEMENTING` 改为 `PASS -> CODE_ALLOWED -> IMPLEMENTING`。

### P2-002：Observation 文本规则未被 Schema 或语义负例完整执行

- **严重级别**：P2。
- **问题结论**：本轮新增；属于已验证事实，但文本规则足以指导 BM-S02 设计，因此不单独阻塞分 Spec。
- **文档和位置**：`spec/contracts/observation-contract.md:48,68,85-90,98-102`；`spec/contracts/schemas/observation.schema.json:6-51`；`spec/contracts/schemas/tests/fixtures.mjs:446-462,538`。
- **冲突事实**：公共文本要求所有 `*.failed` marker 携带 `errorCode`，并要求记录 `memoryBytes` 时同时记录 `metricKind` 与 `samplingPhase`。当前 Schema 只把这些字段定义为全局可选，没有 `if/then` 或等价语义约束；测试只有一个普通 marker 正例和“未知 marker”负例。因此 `build.failed` 无 `errorCode`、`memory.sampled` 只有 `memoryBytes` 等无效消息仍会通过机器 Schema。
- **违反或冲突的合同**：Observation Contract 的失败和内存规则；`spec/README.md` 关于 Schema 是机器合同且不得被文字绕过的规则。
- **实际影响**：不同生产者可生成机器校验通过但 Collector 无法正确归类失败或内存阶段的 marker；BM-S02 若只依赖 Schema，会把合同违规样本当成合法样本。
- **最小修正方向**：在 Observation Schema 或现有语义验证器中实现至少两组规则，并增加正负例：所有 `markerName` 以 `.failed` 结尾时必需 `errorCode`；存在 `memoryBytes` 或 marker 为 `memory.sampled` 时必需 `metricKind + samplingPhase`。Collector 仍只消费该公共规则，不在 BM-S02 私建另一套字段语义。

## 8. 依赖图与越权风险

### 8.1 依赖图

- 八个项目内部的 Foundation -> 子系统 -> Integration/Verification 方向未发现环。
- Toolkit、JS、Core、Examples、三个 Platform 的设计可以并行；产品闭环顺序仍由 `LVGL/SDL -> Android -> iOS` 约束。
- 唯一错误跨项目硬边是 `CORE-S02..CORE-S10 + BM-S02 -> CORE-S11`。Core 应依赖公共 Observation Contract，不应反向依赖 Benchmark 项目分 Spec。
- BM-S02 -> BM-S03 -> 三平台 Target -> BM-S07 的 Benchmark 内部依赖无环，BM-S02 作为 Collector 设计前置是合理的。

### 8.2 提前设计/编码风险

- 当前 `projects/*/spec/subspecs/**` 没有文件，尚未实际启动分 Spec 写入。
- 各项目 README/Handoff 均声明产品代码 `CODE_BLOCKED`，对应分 Spec 独立校审 PASS 后才允许写代码。
- 代码目录检查未发现新 Runtime/Core/JS/Platform/Benchmark 产品源文件；现有 Toolkit README 和 Examples 基线属于既有输入。
- 风险来自状态文字而非已发生的越权行为，按 P2-001 修正即可。

## 10. 最终门禁建议

**当前不放行八个项目分 Spec。**

放行前只需完成两个 P1 的最小修正，不需要重做架构：

1. 删除 Benchmark 的第二套指标语义，精确引用公共 Observation marker；去掉 CORE-S11 对 BM-S02 的硬依赖。

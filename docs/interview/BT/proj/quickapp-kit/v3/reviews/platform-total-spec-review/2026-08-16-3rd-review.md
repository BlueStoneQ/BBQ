## 2. P1 闭环验证

### 2.1 Observation Contract 与 BM-S02

**结果：通过，原 P1-001 已闭环。**

证据：

1. `spec/contracts/observation-contract.md:16-29` 仍是唯一公共观测事实源，总架构维护合同与 Schema，BM-S02 只验证覆盖、边界、开销和采集可行性。
2. `projects/quickapp-benchmark/spec/architecture.md:16` 明确不建立第二套协议。
3. `projects/quickapp-benchmark/spec/architecture.md:50` 已删除本地指标字典，只引用公共 Observation Contract 第 5 节的 marker 对，并禁止用调用发送、回调接收或日志时间替代公共边界。
4. `projects/quickapp-benchmark/spec/architecture.md:54` 对 `logicalPayloadBytes` 使用公共合同冻结的 RFC 8785 JCS UTF-8 字节定义。
5. `projects/quickapp-benchmark/spec/subspec-index.md:20` 将 BM-S02 输出限制为 Observation 验证报告、Collector 消费合同和变更提议。

结论：Benchmark 只验证和消费公共 Observation Contract，不再维护第二个 marker、指标边界或字节语义事实源。

### 2.2 CORE-S11 依赖

**结果：通过，BM-S02 硬依赖已解除。**

证据：

1. `projects/quickapp-runtime-core/spec/subspec-index.md:29` 将 CORE-S11 的观测依赖写为公共 Observation Contract。
2. 同文件第 41 行的依赖图为 `CORE-S02..CORE-S10 + Public Observation Contract/Schema -> CORE-S11`，不再出现 `BM-S02 -> CORE-S11`。
3. 全文残留扫描未检出旧的 `CORE-S02..CORE-S10 + BM-S02 -> CORE-S11`。

结论：Core 验证直接依赖公共合同；BM-S02 报告不是 Core 分 Spec 的公共协议前置或硬依赖。

### 2.3 CAP-DEVICE-001 与 Case 001

**结果：通过，原 P1-002 已闭环。**

Runtime 验收证据：

| 项目 | Case 001 | 独立 CAP-DEVICE-001 |
|---|---|---|
| JS Runtime | `acceptance.md:40-46` 只含 router、prompt、Page Control，无 device | `acceptance.md:60-64` 验证 declaration、typed facade、required fields、density、禁止唯一标识、失败和销毁清理 |
| C++ Core | `acceptance.md:40-47` 只含 prompt 和 Page Control，无 device | `acceptance.md:61-65` 验证 Registry/Invoker、结果字段、错误分类、取消和晚到 Result |
| LVGL | `acceptance.md:36-41` 只含 router、prompt、Page Control，无 device | `acceptance.md:55-59` 验证独立 fixture、simulator/device、结果字段、失败和清理 |
| Android | `acceptance.md:40-48` 只含 Toast、TitleBar/Meta，无 DeviceInfo | `acceptance.md:62-66` 验证独立 fixture、结果字段、失败、JNI/pending/callback 清理 |
| iOS | `acceptance.md:39-44` 的 Case 001 未要求 device | `acceptance.md:45-46` 明确独立调用 Provider，并验证结果、失败和 Gateway 清理 |

Benchmark 验收证据：

1. `projects/quickapp-benchmark/spec/acceptance.md:49-54` 为 `CAP-DEVICE-001` 建立独立报告入口。
2. 三平台必须使用相同 scenario ID 和 fixture identity。
3. 报告必须关联 `capability.requested/completed/failed` 与 requestId，验证 typed Result required fields、物理像素/density、禁止设备唯一标识，并保留 unsupported/failed/销毁取消样本。
4. 文档明确禁止把该数据并入 Case 001 的泛化 Capability 数据。

自动段落检查确认 JS/Core/LVGL/Android 的 Case 001 小节均不含 `device`、`DeviceInfo` 或 `system.device`，五个 Runtime 与 Benchmark 均有独立 CAP 验收。

结论：Case 001 保持真实联盟输入不变；`CAP-DEVICE-001` 已独立贯穿 JS、Core、三个 Platform Runtime 和 Benchmark 验收。

## 3. P2 闭环验证

### 3.1 授权状态

**结果：通过，原 P2-001 已闭环。**

当前入口一致声明：

```text
设计授权：DESIGN_BLOCKED -> DESIGN_ALLOWED
设计任务：READY -> IN_PROGRESS -> READY_FOR_REVIEW -> PASS
编码授权：CODE_BLOCKED -> CODE_ALLOWED
实现任务：CODE_ALLOWED -> IMPLEMENTING -> VERIFIED
```

证据：

1. `README.md:38-40,63`、`spec/README.md:77`、`AGENT-WORK-BOARD.md:151-163` 当前均为等待定向复核、`DESIGN_BLOCKED + CODE_BLOCKED`。
2. `spec/tasks.md:17,125-143` 明确任务状态和授权状态分离，`READY`、`PASS` 都不自动产生授权。
3. `SUBSPEC-AGENT-LAUNCH.md:20,205-217` 明确分 Spec PASS 后仍需工作看板放行代码。
4. 八个项目 README 和 Handoff 顶部均以 `DESIGN_BLOCKED + CODE_BLOCKED` 作为当前状态；Handoff 中较早的状态属于带日期的追加历史，最新事件和文件顶部共同给出当前授权。

结论：本次复核 PASS 后，工作看板可以设置 `DESIGN_ALLOWED`；`PASS` 不等于 `CODE_ALLOWED`，不会自动进入编码。

### 3.2 Observation 条件机器规则

**结果：通过，原 P2-002 已闭环。**

`spec/contracts/schemas/observation.schema.json` 已通过 `allOf + if/then` 执行：

1. 所有公共 `*.failed` marker 必须包含非空 `errorCode`。
2. 任意消息存在 `memoryBytes` 时，必须同时包含 `metricKind` 和 `samplingPhase`。
3. `memory.sampled` 必须包含 `memoryBytes + metricKind + samplingPhase`。

`spec/contracts/schemas/tests/fixtures.mjs:512-514,539-543` 已增加：

- failed + errorCode 正例。
- memory.sampled 完整字段正例。
- failed 缺 errorCode 负例。
- memory.sampled 缺 kind/phase 负例。
- 普通 marker 携带 memoryBytes 但缺 kind/phase 负例。

这些 fixtures 由 `validate-schemas.mjs:81-87` 直接执行，不是未接入测试的静态样本。

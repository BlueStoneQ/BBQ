## 1. 总结论

**FAIL，不建议放行任何项目分 Spec。**

当前架构方向成立：v3 是唯一正式基线；Toolkit、JS Runtime、C++ Core、Platform Adapter 的一级职责没有发生反转；C++ Core 仍是唯一 Runtime Tree 和 Navigation 栈所有者；Android、LVGL、iOS 均被限定为 Host/Platform Adapter；P0-ADDR-001 的增量 Binding/Handler 主消息已统一为 Owner + Template ID，旧 `updateProp` 和 `RegisterHandler(target)` 只存在于拒绝负例。

但当前文档还不能直接驱动多个 Agent 独立写分 Spec。6 个 P0 集中在跨项目边界没有闭合：已验证 Bundle 如何进入 JS、Lifecycle/AppContext 如何经过 Runtime ABI、Surface/Navigation 销毁如何维护栈、Measure 失败如何跨 Core/Platform 表达、Handler 删除如何与 Render 回滚一致，以及冻结 Case 001 会加载未纳入 V1 的 `@system.fetch`。这些不是实现细节，而是公共输入、输出、状态或失败行为缺失。

## 3. P0 问题

### P0-01：Verified Artifact 到 JS Module Loader 的交接协议不存在

- **严重级别**：P0。
- **问题结论**：Core 独占 PackageSource、完整性校验和 Bundle 索引，JS Runtime 独占 Module Loader/QuickJS 执行，但两者之间没有定义“校验完成后的 Bundle/Bootstrap 如何交付、如何确认加载”的 typed Port 或消息。
- **文档位置**：`spec/contracts/artifact-contract.md:18`、`:47`、`:67`、`:98-118`、`:128-137`；`spec/contracts/runtime-abi.md:56-71`；`projects/quickapp-runtime-core/spec/architecture.md:46`、`:75-90`；`projects/quickapp-runtime-js/spec/requirements.md:31-35`、`:49-52`；`projects/quickapp-runtime-js/spec/architecture.md:38`。
- **违反或冲突的合同**：Artifact Contract 要求执行任何 Bundle 前完成校验；Runtime ABI 又声明为 JS/Core 唯一边界，但 ABI 没有 module load/bootstrap 输入或结果。JS-R04 要求 JS 校验 evaluator/handler export 与 Page IR 一一对应，JS 的已声明输入却没有 Page IR 或预期 ID 集合。
- **实际影响**：Core Agent 无法确定交付 bytes、Artifact handle 还是路径；JS Agent 无法在不越过 Package Loader 所有权的前提下读取 Bundle，也无法实现 JS-R04；不同 Agent 会各自发明私有 Port，破坏唯一 ABI 和“校验前不执行 JS”。
- **建议修改方向**：在公共合同中冻结 Core -> JS 的 verified module load 合同，至少明确 `requestId`、package/app identity、module kind、moduleId、immutable bundle bytes 或只读 verified handle、bootstrap metadata、dependencies、page templateId、预期 Binding/Handler ID 集合；冻结 JS -> Core 的 loaded/failed result、错误码、App/Shared/Page 缓存作用域、线程投递、bytes 所有权和“只有 Verified Package 才能发出”的顺序。若 export 一一对应校验改由别处承担，必须同时删除 JS-R04 并指定唯一替代所有者。
- **事实属性**：已验证事实。

### P0-02：Lifecycle、AppContext 与 Host 前后台信号没有进入 Runtime ABI

- **严重级别**：P0。
- **问题结论**：文字合同声明 `LifecycleDispatch -> LifecycleResult` 和 immutable `AppContext/PageContext`，但没有完整字段、判别联合、ABI entry/callback 或机器 Schema；Runtime Host -> Core 的 foreground/background/destroy 信号也没有 typed 请求和结果。
- **文档位置**：`spec/contracts/application-lifecycle-contract.md:64-76`、`:131-141`、`:143-165`；`spec/contracts/lifecycle-and-threading.md:23-30`；`spec/contracts/runtime-abi.md:15-30`、`:56-71`；`spec/contracts/schemas/README.md:13-34`；`projects/quickapp-runtime-js/spec/requirements.md:31-43`；`projects/quickapp-runtime-core/spec/subspec-index.md:21`。
- **违反或冲突的合同**：Runtime ABI Contract 第 1 节的“唯一调用边界”；Lifecycle And Threading 的 immutable typed message 规则；冻结基线中的 App/Page lifecycle 分层。
- **实际影响**：Core/JS Agent 无法一致实现 Hook sequence、App Hook 无 `surfaceId` 的关联、完成/异常 result、Context 交付和销毁取消；三个 Platform Host 也会分别定义前后台入口。`onShow/onHide/onDestroy` 的顺序虽有文字描述，却没有可对接的跨线程协议。
- **建议修改方向**：补齐并机器化 `AppContext`、`LifecycleDispatch`、`LifecycleResult` 和 Runtime Host lifecycle control。明确 scope(app/page)、hook、sequence、可选 surfaceId 约束、status/error、同一 dispatch 只完成一次、Core/JS 队列、异常与销毁时的完成行为；明确 PageContext 是否直接等价于 SurfaceContext，避免两个同义消息；把对应 entry/callback 加入 Runtime ABI catalog 和合同测试。
- **事实属性**：已验证事实。

### P0-03：Core Surface 状态与 Navigation 销毁/返回事务没有唯一状态机

- **严重级别**：P0。
- **问题结论**：Core PageContext 使用 `visible <-> hidden`，Surface schema 使用 `ready/hidden` 且没有 `visible`，Platform 使用 `visible/hidden`；同时 V1 要求页面销毁和 Core 权威 Navigation 栈，但只有 push 合同，没有销毁当前栈顶、恢复 source 或整栈 teardown 的事务语义。
- **文档位置**：`spec/contracts/application-lifecycle-contract.md:43-60`、`:104-129`；`spec/contracts/surface-control.md:53-101`；`spec/contracts/schemas/surface-control.schema.json:191-200`；`spec/contracts/platform-surface-contract.md:29-43`、`:55-90`；`spec/contracts/navigation-contract.md:41-59`；`spec/v1-scope-and-acceptance.md:67-72`；`projects/quickapp-runtime-lvgl/spec/architecture.md:60`。
- **违反或冲突的合同**：冻结基线第 12 条“Navigation 栈、Surface 状态和路由事务由 Core 统一管理”；首屏成功晚于 Present；App/Page lifecycle 的 onShow/onHide 触发条件。
- **实际影响**：Agent 无法确定 `ready` 是否等于 visible、隐藏后恢复用哪个状态、incremental Render 对哪些状态开放；销毁 push target 时可能留下隐藏 source 和包含 tombstone target 的 Core 栈。Case 001 的页面销毁也无法形成唯一可验收序列。
- **建议修改方向**：冻结一套 Core Surface 状态模型并同步文字合同与 schema；若 health 与 visibility 是正交状态，分别建字段，不能继续混用 `ready/visible`。同时明确 V1 的销毁口径：若支持返回/关闭，定义请求来源、top/non-top 校验、source reveal、Platform command、Core 栈提交点、Page Hook 顺序和失败结果；若 V1 只验收整 AppRuntime teardown，则在 V1 Scope、Examples 和 LVGL 中明确删除“返回”语义，并定义整栈销毁顺序。
- **事实属性**：已验证事实。

### P0-04：Measure Adapter 没有可实现的失败返回合同

- **严重级别**：P0。
- **问题结论**：MeasureRequest/MeasureResult 只有文字字段，未定义 method return 判别联合、adapter failure 数据、schemaVersion/kind 或机器 Schema；三个 Platform 项目都必须独立实现该 Port。
- **文档位置**：`spec/contracts/measure-adapter-contract.md:51-73`、`:75-113`；`spec/contracts/lifecycle-and-threading.md:19-21`；`spec/contracts/schemas/README.md:13-34`；`projects/quickapp-runtime-core/spec/subspec-index.md:25`；Android/LVGL/iOS `requirements.md` 的 Measure 输入输出与功能要求。
- **违反或冲突的合同**：`spec/README.md:47` 要求公共合同明确数据、所有权、线程、错误和降级；Lifecycle And Threading 要求跨层 typed message；Error Contract 要求 `MEASURE_FAILED` 可分类。
- **实际影响**：Core 和三个 Platform Agent 会分别选择异常、nullable result、boolean/out-param 或私有 error；`platformFontGeneration` 的来源与刷新消息也无入口。Fake Adapter、故障注入和跨平台合同测试无法共用。
- **建议修改方向**：冻结同步 Port 的完整签名与机器值域：Request 的所有数值单位、constraint union、contentRevision、font generation；Result 的 `measured(width,height)` / `failed(RuntimeError)` 判别联合；规定调用线程、只读输入所有权、一次同步完成、非法 metrics 到 `MEASURE_FAILED` 的映射，以及字体 generation 改变如何通知 Core。加入 catalog、正反例和三个平台共用 fixture。
- **事实属性**：已验证事实。

### P0-05：Handler 先释放、Render 后提交的顺序破坏事务失败恢复

- **严重级别**：P0。
- **问题结论**：Event Contract 要求节点/页面销毁时“先释放 JS Handler Registry”，但 RemoveBlock/解绑所在 RenderTransaction 可能在 Core 校验或 Measure 阶段被拒绝并保持旧 Runtime Tree/EventBinding。此时 Core 仍认为 Handler live，JS 已永久删除且 HandlerId 不允许复用。
- **文档位置**：`spec/contracts/event-contract.md:49-64`；`spec/contracts/render-contract.md:129-146`、`:171-177`；`spec/contracts/block-lifecycle.md:23`、`:38`；`projects/quickapp-runtime-js/spec/architecture.md:76-87`、`:113-125`。
- **违反或冲突的合同**：RenderTransaction 的提交前失败不修改权威状态；HandlerId 生命周期与晚到事件规则；事件解绑、异常、晚到消息必须闭环的验收要求。
- **实际影响**：一次 rejected RemoveBlock 即可造成 Core EventBinding 与 JS Registry 永久分叉；后续点击被路由到不存在的 JS Handler，且不能用原 HandlerId 恢复。
- **建议修改方向**：区分 Surface teardown 与可回滚 Render 删除。对 RemoveBlock/显式 Unregister，JS Registry 先进入 `retiring` 而非删除：在提交在途期间丢弃或按冻结策略处理晚到 dispatch；`presented` 或已提交的 `presentationFailed` 后永久释放；`rejected/cancelled` 后恢复 live。明确 Core commit 前后事件队列的判定点、HandlerRegistrationResult 失败时的回滚和 Trace。Surface teardown 可因 Core 已先拒绝新 input 而直接强制清理。
- **事实属性**：已验证事实。

### P0-06：冻结 Case 001 在 App bootstrap 阶段加载未纳入 V1 的 `@system.fetch`

- **严重级别**：P0。
- **问题结论**：当前 Case 001 的 `app.ux` 强制加载 `helper/apis`，其 `require.context` 加载 `ajax.js`，而 `ajax.js` import `@system.fetch`。当前 Capability Contract、Toolkit 和 JS 总 Spec 只冻结 router/prompt/device，且禁止通用 module/method Bridge。
- **文档和源码位置**：`spec/contracts/capability-module-contract.md:34-40`、`:94-105`、`:133-141`；`projects/quickapp-toolkit/spec/requirements.md:68-76`；`projects/quickapp-runtime-js/spec/requirements.md:62-64`；`quickapp-kit-ai/quickapp-examples/quickapp-code-test1/src/app.ux:6-12`；`.../src/helper/apis/index.js:4-11`；`.../src/helper/ajax.js:4`。
- **违反或冲突的合同**：V1 Scope 要求 Case 001 真实源码不修改并完成 App onCreate；Capability V1 是封闭 typed 集合；Examples 禁止为了适配实现修改 Case 001。
- **实际影响**：若 JS Module Loader 严格拒绝未知 facade，App onCreate 前启动失败；若 Agent 自行提供通用 stub，又违反 typed Capability 和禁止通用 Bridge。当前唯一纵向主链路不可运行。
- **建议修改方向**：由总架构在分 Spec 前冻结且只选择一种口径：将 `system.fetch` 作为 V1 typed module 补齐 request/result/schema/provider；或冻结一个只针对已声明但 V1 未实现模块的 typed-unavailable module resolution 规则，并明确 facade 形状与调用失败；或经产品决策更换/裁剪冻结样例并同步所有 Case 身份。不得让 Toolkit 做 Case 特判，也不得让各平台私加 fetch Bridge。
- **事实属性**：已验证事实。

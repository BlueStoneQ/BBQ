## 1. 核心原则

QuickApp Kit v2 的所有设计文档都遵循：

```text
第一性
本质抽象
学会借鉴业内优点
金字塔原理
结论先行
```

每篇文档都必须先回答：

1. 本文结论是什么？
2. 为什么要这么设计？
3. 它解决了什么本质问题？
4. 它和 QuickApp Kit v2 总架构的关系是什么？

## 2. 结构要求

每篇文档必须包含目录，并采用结论先行的结构。

推荐结构：

```text
# 标题

## 目录

## 1. 结论

## 2. 背景与问题

## 3. 本质分析

## 4. 架构设计

## 5. 关键决策

## 6. 业内借鉴

## 7. 边界与不做事项

## 8. 验收标准

## 9. 后续演进
```

## 3. 推导方式

设计文档不能只描述做法，需要说明推导过程。

每个核心设计点应按照以下顺序展开：

```text
目标
  -> 本质问题
  -> 可选方案
  -> 决策
  -> 取舍
  -> 验证方式
```

示例：

```text
目标：支持 Android / iOS / LVGL 多端渲染。
本质问题：应用运行语义和平台控件实现不能耦合。
决策：采用 One Runtime Core + Multiple Render Backends。
取舍：Core 复杂度上升，但新增平台成本下降。
验证：Android 首发链路跑通后，LVGL 复用同一 Core。
```

## 4. 借鉴方式

QuickApp Kit v2 鼓励借鉴业内成熟框架，但必须做本土化吸收。

借鉴规则：

1. 先理解对方解决的本质问题。
2. 再判断 QuickApp Kit v2 是否有同类问题。
3. 只吸收适合本项目定位的架构思想。
4. 不照搬对方术语和工程形态。

参考方向：

| 框架 | 主要借鉴点 |
|---|---|
| React Native Fabric | Shadow Tree、reconcile、commit/mount、Native 渲染管线 |
| React Native TurboModule | 模块注册、懒加载、强契约、跨语言能力调用 |
| Lynx | 高性能跨端渲染 Runtime、多端引擎化、批量更新 |
| Flutter | Engine/Framework/Embedder 分层、可观测渲染管线、平台嵌入边界 |
| QuickApp/小程序体系 | RPK/包协议、manifest、系统能力开放、轻应用生态 |

## 5. 文档模板

新设计文档可以从以下骨架开始：

```markdown
# 文档标题

## 目录

- [1. 结论](#1-结论)
- [2. 背景与问题](#2-背景与问题)
- [3. 本质分析](#3-本质分析)
- [4. 架构设计](#4-架构设计)
- [5. 关键决策](#5-关键决策)
- [6. 业内借鉴](#6-业内借鉴)
- [7. 边界与不做事项](#7-边界与不做事项)
- [8. 验收标准](#8-验收标准)
- [9. 后续演进](#9-后续演进)

## 1. 结论

先给出本文最终判断。

## 2. 背景与问题

说明为什么需要这份设计。

## 3. 本质分析

抽象出底层问题。

## 4. 架构设计

给出模块、边界、流程和接口。

## 5. 关键决策

说明关键取舍。

## 6. 业内借鉴

说明参考了谁、借鉴了什么、没有照搬什么。

## 7. 边界与不做事项

明确当前阶段不解决的问题。

## 8. 验收标准

说明如何证明设计成立。

## 9. 后续演进

说明可扩展方向。
```

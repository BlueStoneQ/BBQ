## 移动端快应用框架（类 RN 跨端框架 · Android 原生）

系统级快应用运行时，JS 驱动 Native View 渲染（非 WebView），V8 + J2V8 同步 Bridge（类 JSI）。

- 包体优化：预装包 153MB → ~60MB，DEX 44.4MB → 27MB（-39%）
- 模块裁剪与降级方案：反射解耦编译依赖 + metadata 入口控制 + 自升级兜底
- 启动内存优化：DEX 布局优化，热代码前置减少 page fault（PSS MAX 41MB → 35.8MB）
- 自动化测试：Python + pytest + uiautomator2 驱动真机采集 PSS 数据

---

## 一句话本质

这几件事不是并列的独立优化，是**同一条因果链上的一件事**，主线是：**把框架作为系统预装件集成进 ROM，要过体积和内存的合规门槛。**

所有动作都服务这一个目标：

```text
预装集成合规（要过体积 + 内存门槛）
   │
   ├─ 包体裁剪（让东西不进包）—— 主要收益
   │      └─ DEX 变小 → 启动要映射/加载的代码页天然变少
   │                     → 内存（PSS）本身就降了一大截   ← 连带结果，不是独立优化
   │
   └─ 收尾（锦上添花，边际收益）：
          ├─ R8：死代码消除，抠包体零头
          └─ DEX memory layout：热代码重排，再压启动缺页/驻留

   自动化测试：真机采样 PSS，测出优化前后的对比数据佐证
```

三个认知要点：

1. **内存降的大头，是包体降的连带结果**，不是单独做内存优化做出来的。包小了、DEX 小了，启动本来就少碰内存页，PSS 自然下来。
2. **R8 和 layout 重排是收尾**，在主体裁剪之后把剩余零头再抠一点，边际收益小。
3. **统领一切的目标是预装集成合规**——不是为了优化而优化，是为了让框架能作为系统预装件塞进 ROM，必须过体积和内存的合规线。

---

## 主线一：包体裁剪（主要收益）

**两层裁剪 + 一层运行时解耦，越早裁越干净：**

1. **Gradle 依赖裁剪（编译期，最彻底）**：定义 `isBuildForRom`，在 `dependencies` 中决定模块是否参与编译；ROM 构建不引入第三方模块，它们根本不进 APK。
2. **代码条件裁剪（编译期）**：同一个变量写入 `BuildConfig`，代码通过 `BuildConfig.IS_BUILD_FOR_ROM` 判断；Release 构建经 R8 常量折叠和死代码消除，未启用分支及其类被移除。
3. **反射解耦（斩断静态依赖链）**：如果代码不能直接引用被裁掉模块的类，就用类名/metadata + 反射在模块存在时加载；模块不存在时不触发类解析，避免编译依赖和运行时崩溃。

**为什么必须有第三层反射（关键、最易忽略）：**

前两层裁了模块，但只要代码里还有一句静态引用（如 `MapModule.init()`），编译器就把 `MapModule` 当硬依赖——为了让这句编译通过，它必须能找到这个类，于是又把整个模块拖回包里，裁了个寂寞。

反射的作用就是把这条静态引用链换成运行时字符串查找：

```java
// 静态引用：编译期就把 MapModule 焊死进包
MapModule.init();

// 反射：编译期只看到字符串，不认识 MapModule 这个类
Class<?> clazz = Class.forName("com.x.MapModule"); // 有就加载，没有走降级
clazz.getMethod("init").invoke(...);
```

两个收益：

- **避免编译依赖**：代码里没有 `MapModule` 这个类型符号，只有字符串，编译器不再把它当依赖 → 模块能被真正裁掉。
- **模块不存在时不崩**：预装包真没这个类时，静态引用会在类加载期直接 `NoClassDefFoundError` 崩掉；反射是主动 `Class.forName` 才去找，找不到抛可捕获的 `ClassNotFoundException`，catch 住就走降级（升级完整 APK 兜底），不崩。

最终结构：

```text
Gradle isBuildForRom
├── dependencies：决定哪些模块参与编译
├── BuildConfig：决定代码保留哪条分支
└── metadata + reflection：隔离可选模块的编译引用
```

本质一句话：

> 构建配置决定模块是否存在，BuildConfig 决定代码路径，反射把可选模块从静态依赖改成运行时可发现能力。

术语收敛：

> 这不是严格意义上的“源码条件编译”（不像 C/C++ `#ifdef`），而是 **Gradle 依赖选择 + BuildConfig 常量分支 + R8 后处理裁剪**。

结果：APK 153MB → ~60MB，DEX 44.4MB → 27MB（-39%）。

---

## 连带结果：内存主降

启动内存降的大头，是包体降带出来的，不是单独优化的结果。

第一性：**DEX 是按内存页（通常 4KB）加载的。** 启动只用到一部分代码，但代码所在的整页都会被读进内存。包体裁剪让 DEX 变小，启动要映射/加载的页天然变少 → 缺页（page fault）少、驻留（PSS）低。**没做任何针对内存的动作，PSS 就已经跟着降了一大截。**

---

## 收尾：R8 与 DEX 布局（锦上添花）

主体裁剪之后，再抠剩余零头，边际收益小：

- **R8**：死代码消除，把裁剪后残留的无效代码/类进一步移除，压包体零头。
- **DEX memory layout（热代码重排）**：把启动期实际执行的热方法在 DEX 里排到相邻位置，改善访问局部性 —— 启动只碰少数几页，进一步压缺页和驻留。

热代码重排的第一性和 CPU cache 的空间局部性同理：**把一起用的东西放一起。** 代码一行没改，只重排物理布局，省的是 I/O 和页驻留。哪些是热方法，靠跑一遍启动、采集 startup profile 得到。

结果：PSS MAX 41MB → 35.8MB。

## 数据佐证：自动化测试

定位：这里的自动化测试是**内存指标的测量方案**，不是功能回归。

内存优化前后要有可信的对比数字（41MB → 35.8MB），这个数字靠 Python + pytest + uiautomator2 驱动真机反复跑启动、采样 PSS 得到。

为什么必须自动化，而不是手工：

- **PSS 有波动**：单次测不准，得多轮取稳定值/峰值，手工重复几十次不现实。
- **要可复现、可对比**：优化前后必须在一致的操作路径、一致的采集时机下测，变量才可控。
- **PSS MAX 是峰值**：得在启动全过程持续采样抓峰值，靠脚本定时 `dumpsys meminfo` 采点，人工掐不准峰值时刻。

工具链分工：

- **uiautomator2**：驱动真机自动操作（拉起应用、走启动流程）。
- **pytest**：组织用例、跑多轮、断言汇总。
- **Python**：串起来，定时采集 `dumpsys meminfo` 的 PSS，算峰值、出对比数据。

## 理解参考

**一、包体(文档已写清,我只补本质)**

文档这三层总结得对。本质就一句:**在三个不同阶段做裁剪,越早裁越干净。**

- **编译期(Gradle `isBuildForRom`)**:模块压根不参与编译 → 不进包。最彻底。
- **编译期(BuildConfig + R8)**:代码进了,但常量分支为 false → R8 死代码消除,连带类一起删。
- **运行时(反射解耦)**:不能静态引用被裁的类,否则一编译就把它拖回来了 → 用反射改成"运行时按需发现",斩断静态依赖链。

**为什么必须有第三层反射**:这是关键、也是最容易忽略的点。前两层裁了模块,但只要代码里还有一句 `new SomeOptionalClass()`,编译期就会把那个类当硬依赖拉进包——裁了个寂寞。反射的作用就是**斩断这条静态引用链**,让"可选能力"从"编译期必须存在"变成"运行时有就用、没有就降级"。这一层是包体能真正瘦下来的前提。

结果:153MB → 60MB,DEX 44.4 → 27MB(-39%)。

---

**二、内存(文档空着,这是核心,讲透)**

启动内存优化的本质,一句话:**DEX 是按内存页(通常 4KB)加载的;启动只用到一小部分代码,但如果这些"热代码"散落在 DEX 各处,就会碰到很多页,每碰一个新页触发一次 page fault(缺页)、把整页读进内存 → 驻留内存(PSS)涨。把热代码集中排到一起,启动就只碰少数几页,缺页和驻留都降下来。**

第一性拆解:

1. **为什么是"页"**:代码不是想用哪行读哪行,操作系统以页为单位映射/加载 DEX。你哪怕只调用一个方法,它所在的整页(4KB)都会被读进内存。
2. **散落的代价**:假设启动要跑 100 个方法,如果它们分散在 100 个不同的页 → 碰 100 页 → 100 次 page fault → 100 页驻留。
3. **集中的收益**:把这 100 个方法在 DEX 里排到相邻位置 → 可能只占 10 页 → 10 次缺页 → 10 页驻留。**代码一行没改,只是重排了物理布局。**
4. **怎么知道哪些是热代码**:跑一遍启动,用工具(如 ART 的 profile / `dexlayout` + startup profile)采集"启动期实际执行了哪些方法",按这个把热方法前置、集中。

结果:PSS MAX 41MB → 35.8MB。

**注意这里的巧妙**:它不是"少加载代码"(代码还是那些),而是"改变代码的物理排列,让启动的访问局部性变好"。省的不是逻辑,是 I/O 和页驻留。这和 CPU cache 的空间局部性是同一个第一性原理——把一起用的东西放一起。

---

**三、自动化测试(文档空着,补本质)**

一句话:**裁剪是"减法",减法最大的风险是"减多了把功能减没了、或降级路径没兜住";自动化测试就是每次裁完自动验证"功能没坏 + 降级能兜 + 性能达标"。**

- 工具链:Python + pytest + uiautomator2 驱动真机。
- 测什么:启动跑通、被裁能力触发时降级(升级兜底)正常、性能数据(启动时间/PSS)对比不劣化。
- 为什么必要:裁剪+反射+降级这套改动面大,人工回归覆盖不全,必须自动化守住"裁了但没裁坏"。

---

**一句话收口整项**:这项是三件独立的事——**包体**靠"三层越早越好的裁剪 + 反射斩断静态依赖"让东西不进包;**内存**靠"DEX 热代码重排、改善页访问局部性"让启动少碰内存页;**测试**靠"真机自动化"守住"裁了没裁坏"。三者目标不同、机制不同,别混讲。

## QA
### 反射 从哪儿找的包名
反射方案的一个关键实现点:那个类名(包名)字符串从哪来?

结论先行:不是从 Gradle deps 配置里找的,而是编译期写进产物里的一张"能力注册表"(metadata),运行时读这张表拿到类名。 Gradle deps 决定的是"这个类在不在包里",不负责"运行时去哪查它的名字"

### 关于R8
一句话:**R8 是 Android 的编译期优化器,本质是"全程序静态分析 + 按可达性裁剪"——从入口出发算出哪些代码真正会被用到,把够不到的全删掉,再把留下的压缩重写。**

核心机制是**可达性分析(reachability)**,和 GC 标记存活对象是同一个第一性思路,只不过 GC 在运行时标对象、R8 在编译期标代码:

1. **定根(roots)**:入口点——Activity、manifest 声明的组件、`keep` 规则保留的东西。
2. **从根出发遍历调用图**:谁被根调用、谁又被它们调用……能顺着引用链够到的,标记为"可达"。
3. **删掉不可达的**:图上够不到的类/方法/字段,判定为死代码,整个删除(tree shaking)。

在这个基础上,R8 做四件事(一个工具一趟全干了,这是它和老 ProGuard+D8 分开的区别):

- **shrinking(裁剪)**:删不可达代码。← 最核心,你文档里说的"死代码消除"
- **optimization(优化)**:内联、去掉空方法、常量折叠(`BuildConfig.IS_BUILD_FOR_ROM` 为 false 的分支就是这一步被折叠掉的)、合并类等。
- **obfuscation(混淆)**:把长类名/方法名改成 `a`、`b`,既缩体积又混淆。
- **desugaring**:把新语法糖(lambda、部分新 API)降级成低版本能跑的字节码。

**关键点:R8 是"全程序、编译期、静态"的。** 

- **全程序**:它看的是整个应用的调用图,不是单文件——所以能判断"这个 public 方法全应用没人调,删"。
- **编译期**:在打包时做,产出的 DEX 就是裁剪压缩后的,运行时零开销。
- **静态**:只能分析静态可见的引用链。**这就是它和反射冲突的根源**——反射 `Class.forName("com.x.MapModule")` 里那个类名是字符串,R8 的可达性分析"看不见"这条引用,会误判它不可达而删掉。所以**反射用到的类必须写 `keep` 规则告诉 R8"别删这个",否则运行时崩**。

**扣回你的文档**:文档里 R8 出现在两处,正好是它两个能力——

- "BuildConfig 常量折叠 + 死代码消除":`IS_BUILD_FOR_ROM` 为 false 的分支被 optimization 折叠、shrinking 删除。
- 收尾"死代码消除,抠包体零头":裁剪后残留的无效类再删一遍。

一句话本质:**R8 = 编译期的全程序可达性分析器 + 压缩重写器。从入口顺着调用图标可达,够不到的死代码全删,留下的再内联/折叠/混淆压小。它和反射天然冲突——静态分析看不见字符串类名,得靠 keep 规则兜住。**

字节码。R8 的输入是 **JVM 字节码(.class)**,不是源码 AST。

理清整条编译链就看清 R8 站在哪:

```
.java 源码
  │  javac(这一步才碰 AST,产出字节码)
  ▼
.class（JVM 字节码）
  │  ← R8 在这里:吃 .class,做分析+裁剪+优化,直接吐 .dex
  ▼
.dex（Dalvik 字节码,ART 跑的）
```

几个关键点:

1. **R8 吃字节码、吐 DEX**。它同时干了老工具链两件事:ProGuard(裁剪混淆,在字节码层)+ D8(.class → .dex 转换)。合成一个工具、一趟做完,所以它的输入是 `.class` 字节码,输出直接是 `.dex`。

2. **AST 是 javac 的事,和 R8 无关**。源码 → AST → 字节码 这一段是 Java 编译器(javac)做的。R8 拿到的已经是 javac 产出的字节码,它不回头看源码,也不重建源码 AST。

3. **为什么在字节码层做,而不是源码**:
   - **语言无关**:字节码层看不出是 Java 还是 Kotlin 写的,R8 一视同仁——所以 Kotlin 项目照样用 R8。
   - **信息够且规整**:字节码里调用关系、类型引用都是显式的,做可达性分析(调用图遍历)比在源码 AST 上更直接。
   - **它本就是打包环节**:要产 DEX,输入端自然是字节码。

4. **但要说清"字节码"的粒度**:R8 内部会把字节码解析成自己的 IR(中间表示)来做分析和优化(内联、可达性、常量折叠都在 IR 上做),优化完再降成 DEX。所以严格说:**输入是字节码,内部转成 IR 分析,输出是 DEX**。它分析的载体是 IR,但源头是字节码,不是源码 AST。

一句话:**R8 分析的是字节码(经内部 IR),不是源码 AST。AST 是 javac 的中间产物;R8 站在 javac 之后,吃 .class 字节码、做全程序可达性分析和优化、直接产出 .dex。在字节码层做的好处是语言无关(Java/Kotlin 通吃)、引用关系规整、且天然就是打包环节。**

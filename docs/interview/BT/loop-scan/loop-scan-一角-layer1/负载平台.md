## 优化：大文件上传
凿原理:为什么单请求扛不住大文件(超时/内存/失败全量重传)→ MPU 把文件切片、每片独立上传可并发 → 并发调度控制 → 失败只重传那一片 → 全部完成后 CompleteMultipartUpload 合并。数字:4.4G 121s→42s(≈3x),提速来自并发打满带宽。

## 优化：大数据渲染
凿原理:为什么大数据量卡(海量点在主线程计算+渲染,阻塞 UI;且点数远超屏幕像素,画了也看不出)→ Web Worker 把数据处理挪出主线程(主线程不阻塞)→ 降采样(如 LTTB)在保持曲线形状的前提下把点数降到和像素密度匹配。

## QA
### Doris选型
先给结论,再 list,最后说业界怎么选。你说的"跨列查询多"方向对,但更准确的说法是**列存 + MPP 带来的多维聚合快 + 支持标准 SQL**。

**为什么选 Doris(list):**

1. **列存(列式存储)—— 分析型查询的地基**
   - 你的查询是"某机型过去24h 的 P95 帧率""按维度聚合内存峰值"这种——**只读少数几列、但要扫大量行做聚合**。
   - 列存只读用到的列(帧率那列),不像行存要把整行捞出来。你说的"跨列查询多"本质是这个:**分析场景每次只碰几列、要聚合海量行,列存正好只读相关列 + 高压缩比**,扫得快。

2. **MPP(大规模并行)—— 聚合快**
   - 查询拆到多节点并行算,大数据量聚合(GROUP BY、P95、COUNT)扛得住。

3. **支持标准 SQL —— 上手快、展示后端好写**
   - Go 展示后端直接写 SQL 查,不用学专有查询语言。这对"全栈一个人交付"很关键——省心智。

4. **实时写入 + 近实时查询**
   - 支持批量导入(Stream Load)后很快可查,适合"解析完落表马上能在平台看"。

5. **运维相对简单(相对 ClickHouse)**
   - 架构比一些竞品简单,单表/宽表模型好用,中小团队/一个人也 hold 得住。

**业界怎么选(同类横向对比):**

| 选项 | 定位 | 什么时候选它 |
|---|---|---|
| **Doris** | MPP 列存 OLAP,SQL 友好、运维简单 | 多维聚合分析 + 要标准 SQL + 团队小、想省运维。你的场景 |
| **ClickHouse** | 极致单表查询性能的列存 OLAP | 追求极限查询速度、日志/事件海量,但运维和 JOIN 较复杂 |
| **时序库(InfluxDB / TDengine / Prometheus)** | 专为时间序列优化 | 纯"指标随时间"的监控,但多维自由聚合、复杂 SQL 弱 |
| **数据湖(ClickHouse 之外的 Iceberg + 引擎)** | 超大规模、离线为主 | PB 级离线分析,不追求交互式实时 |
| **MySQL/PG(行存)** | OLTP 事务 | 小数据量、事务型,大数据聚合会慢 —— 你的场景不合适 |

**业界在你这类"可观测/性能分析平台"的典型选择:**

- **纯监控指标(时间序列为主)** → Prometheus / InfluxDB / TDengine。
- **多维分析、要 SQL 自由聚合、要看明细** → **Doris 或 ClickHouse**。你的平台(负载/功耗/性能/内存/流畅度多维度 + 要自由钻取)属于这类。
- **Doris vs ClickHouse 的取舍**:ClickHouse 单表查询更快、但 JOIN 弱、运维重、专有 SQL 方言;**Doris SQL 更标准、JOIN 支持好、运维简单**。你一个人全栈交付 + 要标准 SQL + 多表关联,**Doris 更省事**——这就是选它而非 ClickHouse 的关键理由。

**叙述口径(能顶追问):**

> 选 Doris 是因为平台的查询形态是"多维度聚合 + 自由钻取"(按机型/时间/场景聚合 P95 帧率、内存峰值这类),这是列存 + MPP 的主场——只读相关列、并行聚合海量行,比行存 MySQL 快一个量级。选 Doris 而非 ClickHouse,是因为它 SQL 更标准、JOIN 支持好、运维简单,适合一个人全栈交付;而没选时序库(InfluxDB),是因为我们不只是"指标随时间",还要多维自由聚合和查明细,时序库那块弱。

一句话:**选 Doris = 列存(只读相关列、聚合快)+ MPP(并行扛大数据聚合)+ 标准 SQL(好写好维护)。业界这类多维分析平台在 Doris/ClickHouse 里选;你选 Doris 而非 ClickHouse 是图 SQL 标准、JOIN 好、运维简单(适合一人全栈);没选时序库是因为要多维自由聚合而非纯时间序列。你说的"跨列查询多"本质就是列存对"少列多行聚合"的优势。**

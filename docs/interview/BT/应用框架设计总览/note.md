### 关于业界diff
1. 首先,for这种动态列表目前业界基本都是需要diff的
2. 非动态列表的场景, 基本有以下三个流派:
  - **运行时diff**: 代表就是RN, lynx, flutter
    - 展开:
      ```md
      - 通过遍历比较找到，而不是提前知道。
      - 例如 title 变了：重新 build 出包含新文字的 Widget 子树 → 从对应 Element 往下比较 → 发现 Text 的文字变了 → 更新对应渲染对象。
      - 所以，响应式绑定是“提前记住该改谁”，diff 是“更新时比较出该改谁”。
      ```
  - **运行时建立state到node的绑定**: 基于响应式+watcher+deps(观察者模式)的state更新精准触发绑定节点的, 代表是Hap(快应用联盟)这样
  - **编译阶段建立state到节点绑定关系**: 例如基于id驱动的Nyrax
    - 不过响应式是运行时收集state到节点的映射关系, 而基于ID驱动是在编译阶段就确定了state到节点的映射关系
    - nyrax会有proxy的响应式,但是没有基于watcher+deps这种观察者模式来找到state到node映射关系,而是查找编译期建立的基于id的state到node的映射关系


  ### 提前记住state<-->node的映射关系,内存会更高吗
  - **会多一份常驻的依赖关系，但不代表总内存一定更高。** diff 方案也要保存旧的 UI 描述或实例结构，更新时还会创建新描述。
  - 能确定的是：提前记住绑定，用依赖关系的存储成本，换取更新时更少的计算和比较。

### 路由模型
结论： 一个Android页面作为容器 只是里面渲染不同的RPK页面


### 页面栈注册时机
1. 页面栈注册时机 —— manifest 编译期定路由表，运行时页面进栈时"注册"

分两层：

路由表（path→页面信息）来自 manifest 的 router 配置，编译期就定好，运行时加载 rpk 时读进 RouterInfo（getPageInfoByPath 查的就是它）。
页面栈（List<Page> mPageInfos）运行时才建：应用启动，入口页 build 出来后 push 进栈（第一个元素）。之后每次跳转，新页进栈。"注册"发生在页面 push 进栈那一刻，不是启动时全量注册所有页面。

### 路由跳转
2. 路由跳转到指定 path（push）—— 查表建页 → 按 launchMode 处理 → 进栈 → 通知渲染


router.push({uri:"/pages/Detail"})
 → 转成 HybridRequest（带 path）
 → buildPageByUri：用 path 查 RouterInfo.getPageInfoByPath → 拿到 RoutableInfo
 → new 出 Page 对象
 → PageManager.push(page)：
     · 先看该页 launchMode（standard/singleTask 等）→ 决定是新压还是复用已有页
     · mPageInfos.add(page)   // 进栈(尾部)
 → PageChangedListener 通知 RootView → 加载渲染新页
关键：查表(path→RoutableInfo)在 manifest 路由表，建页+进栈在 PageManager，launchMode 决定复用还是新建。

### 路由back
3. 路由 back —— 从栈尾弹出目标之上的页 → 销毁 → 通知渲染回退


router.back() 或 back(path)
 → PageManager.back(changeIndex)：
     · 定位要回到的目标 index（back() 回上一页；back(path) 回到栈里那个 path 的页）
     · 把目标之上的页依次 mPageInfos.remove(...)   // 弹栈+销毁中间页
 → PageChangedListener 通知 RootView → 呈现回退后的栈顶页
关键：back 不只弹一页——back(path) 会把目标页之上的所有页一次性弹出销毁，回到指定 path。

三者共性收束：全走**"改 List<Page> 栈 → PageChangedListener 通知 RootView 渲染"**这一条路。JS 只发意图（push/back），栈的增删和页面生死全在 Native 的 PageManager；路由表编译期定、运行时按 path 查。push=查表建页进栈，back=弹出目标之上的页。owner 始终在 Native。

### 页面卸载和加载保活
最小代码实现：
```java
// 一页 = 一个 Page 对象，身上挂着这页的所有状态
class Page {
    String path;              // 路由路径，来自 manifest 路由表
    XVm vm;                   // JS 侧的页面 VM（响应式 data/methods）—— 常驻，从不销毁
    VDocument cachedViewTree; // 摘下来缓存的 View 树；未缓存时为 null
}

class PageManager {
    List<Page> pageStack = new ArrayList<>();  // 页面栈（动态数组当栈用）
    RootView rootView;                          // 唯一容器(FrameLayout)，同一时刻只挂一页的树

    // —— 跳转：把当前页的 View 树摘下缓存，新页进栈并挂载 ——
    void push(Page newPage) {
        Page currentPage = top();
        if (currentPage != null) {
            // 摘：从容器移除当前页 View 树，存回它自己的 Page 对象（VM 不动，仍活着）
            currentPage.cachedViewTree = rootView.currentViewTree();
            rootView.detach(currentPage.cachedViewTree);
        }
        pageStack.add(newPage);        // 进栈
        activate(newPage);             // 挂载新页
    }

    // —— back：弹出并销毁栈顶，取回上一页缓存的 View 树重新挂载 ——
    void back() {
        Page closing = pageStack.remove(pageStack.size() - 1);
        rootView.detach(rootView.currentViewTree());
        destroy(closing);             // 真正离开的页才销毁 VM + View 树

        Page revealed = top();        // 露出的上一页
        activate(revealed);           // 取回它缓存的树，挂回去
    }

    // —— 激活一页：有缓存树就复用挂回，没有(首次)就用 VM 建树 ——
    void activate(Page page) {
        VDocument viewTree = (page.cachedViewTree != null)
                ? page.cachedViewTree          // back 复现：直接复用缓存的整棵树
                : page.vm.buildViewTree();     // 首次进入：VM 建树
        rootView.attach(viewTree);             // 挂进容器 → 屏幕显示这一页
        page.vm.onShow();                      // 触发 onShow 生命周期
    }

    Page top() {
        return pageStack.isEmpty() ? null : pageStack.get(pageStack.size() - 1);
    }
}

```
解读：
- "摘下存哪里" —— 存到 currentPage.cachedViewTree，即当前页自己的 Page 对象身上。detach 只是从容器移除 View 树，树对象和 VM 都还在内存（Page 还在栈里引用着它们）。摘 ≠ 销毁。

- "怎么取出挂上激活" —— activate 里：page.cachedViewTree 有值就直接复用挂回（back 场景），没值就 vm.buildViewTree()（首次进入）。挂回靠 rootView.attach，再 onShow。关键：back 复现的是同一棵缓存树，不重建、不重跑 JS。

- 保活的根是 VM —— page.vm 从 push 到 back 全程没动过，所以 data/状态天然还在；缓存的 cachedViewTree 只是让 View 层也免于重建。VM 常驻 = 状态保持；缓存树 = 视图秒复现。

- 一句收束：Page 是承载"VM + 缓存 View 树 + 路由信息"的对象，一个在 List 栈里。push=把当前页 View 树 detach 后存回它的 cachedViewTree（VM 不动）；back=销毁真正离开的栈顶、取回下一页的 cachedViewTree 重新 attach。保活靠 VM 全程常驻，秒复现靠缓存整棵树——摘挂的是 View 树，状态的根是不销毁的 VM。

详细过程：
- **跳转时上一页不销毁，整个 Page（VM + View 子树）留在内存栈里保活，back 时直接复现。** 但我去核实一下"View 子树是留着还是移除只留数据"这个细节,别把保活的粒度说错。

- course关键证据在 `Page.getCacheDoc()` / `page.setCacheDoc()`——回答你，且比"隐藏"更精确。

- **你的直觉对，保活是真的，但机制是"缓存"不是"隐藏"：**

- **push（跳走）时**：旧页的 View 树（`VDocument`）从 RootView **detach（摘下来，`detachChildren`）**，但**不销毁**——存进 `oldPage.setCacheDoc(document)`，Page 对象仍留在 `mPageInfos` 栈里。所以是**摘下 + 缓存在 Page 对象上**，不是单纯"隐藏还挂在树上"。

- **back（回来）时**：`VDocument cacheDoc = currPage.getCacheDoc()` —— **直接取回上一页缓存的那棵 VDocument，重新 attach 回 RootView**（`mDocument = currPage.getCacheDoc()`）。不用重新加载 JS、不用重新 build 页面。

- **所以状态怎么保持/恢复：**

- **JS 状态（VM/data）**：`Page.vm`（那个 XVm）**一直活在内存里**，从没销毁——所以页面的响应式 data、变量、滚动位置对应的状态全在。这是状态保持的**根**。
- **View 树**：`VDocument` 被缓存在 `Page.cacheDoc`，back 时整棵取回复用——所以视图原样复现，连滚动位置这些 View 层状态也在（因为是同一批 View 对象)。
- **恢复动作**：back 时 detach 当前页 → 取 `currPage.getCacheDoc()` attach 回去 → 触发 `onShow` 生命周期。**不重新执行页面 JS、不重建树。**

- **修正你"只是隐藏"的措辞**：不是"隐藏但还挂在 View 树上"，是**"从 RootView 摘下来(detach)+ 缓存 VDocument + Page/VM 常驻内存"**。区别在于：隐藏=还占着 View 树（GONE），缓存=从树上摘走但对象留着。hap 是后者——**摘下但保活**，back 时重新挂回。

- **代价（顺带，这是保活方案的通病）**：栈里每页的 VM + VDocument 都常驻内存，**栈越深内存越涨**。所以有 `clearPageTask`/`clearAll`（上面代码里那些）和 launchMode 来控制——singleTask 会把目标页之上的全清掉、避免同页堆叠，就是为了压内存。

- 一句收束：**back 能恢复上一页,是因为 push 时旧页没销毁——View 树(VDocument)被 detach 后缓存在 Page.cacheDoc,JS 侧的 VM/data 一直常驻内存;back 时取回 cacheDoc 重新 attach 回 RootView + 触发 onShow,不重新加载 JS、不重建树。是"摘下并缓存 + VM 常驻"的保活,不是单纯隐藏。代价是栈深内存涨,靠 launchMode/clearTask 控制。**

### 页面栈：爆栈问题
1. 方案1: 限制深度
- 嵌入式和nyrax用的这个，在编译的时候可以指定，目前默认page stack deepth： 32
2. 方案2: launchMode
- 取值：
    - standard（默认，每次新压）/ singleTask（栈里已有则回到那页、砍其上）
    - singleTask 解读：    
        - 跳转到一个 `singleTask` 页时，push 里会做什么（基于前面读的 `push` 代码 460-450 那段）：

        - **流程（栈里已有该页 vs 没有，两种走向）：**

        ```
        push(page)  且 page.launchMode == singleTask
        → newIndex = getEldestPageIndexByPath(path)   // 在栈里找这个 path 最早的那页

        ┌─ 栈里已有(newIndex >= 0)：复用 + 回退
        │    → oldPage = mPageInfos[newIndex]          // 取栈里那个已存在的同 path 页
        │    → oldPage.params = page.params            // 用新参数覆盖它
        │    → oldPage.setShouldRefresh(true)          // 标记需刷新(用新参数重渲染)
        │    → back(newIndex - size + 1)               // 回退到那页：把它之上的页全部弹出销毁
        │    → return                                  // 不新建、不入栈
        │
        └─ 栈里没有(newIndex < 0)：当普通页
            → 走 standard 逻辑：mPageInfos.add(page)   // 正常新压一页
        ```

        - **核心动作三点：**

        1. **查重**：`getEldestPageIndexByPath` 在栈里找有没有同 path 的页。
        2. **命中则回退复用**：不新建，而是 `back` 回到已有那页，**把它上面的页全弹出销毁**——保证栈里这个页**只有一个实例**（singleTask 的本质：栈内唯一）。
        3. **传参刷新**：复用的旧页用新 `params` 覆盖 + `setShouldRefresh(true)`，让它用新参数重新渲染（不是拿旧内容）。

        - 一句收束：**跳 singleTask 页 = 先按 path 查栈；栈里已有就"回退到那页 + 弹掉其上所有页 + 用新参数刷新"(保证栈内单实例),没有就当 standard 新压一页。本质是"栈内唯一 + 复用回退",典型用于首页/主 Tab——从深层一跳回去、清掉中间历史。**


- launchMode 怎么处理栈深度

- launchMode 是页面级的入栈策略（manifest 里配，routableInfo.getLaunchMode()），本质是"push 这页时，要不要顺手清掉栈里已有的同页/其他页"。它靠在跳转时机清栈来间接压深度，不是设上限。常见两种（对标 Android）：

- standard（默认）：每次 push 都新压一页。不控深度——反复进同一页会堆叠，栈越来越深。
- clearTask / singleTask（FLAG_CLEAR_TASK）：push 这页时，把栈里到某个位置为止的页清掉（上面代码 clearPageTask：找到已有的同 path 页，把它之上/之外的页 remove）。效果是"回到那页、砍掉中间历史"——这是压深度的主力手段。
- 所以 launchMode 控深度的本质：不是"到 N 拒绝入栈",而是"特定页用 clearTask 语义,在跳转时把冗余历史清掉",让栈不无限增长。 典型场景：从深层多次跳回首页,首页配 clearTask,一跳就把中间栈全清。

- lauchMode目前是rpk在manifest配置，一个页面配置会有一个laucnhMode配置，默认都是standard


### 满栈处理
- 总结：
| 派别 | 满栈行为 | 代表 |
|---|---|---|
| **设硬上限、到顶拒绝** | 满了拒绝新 push | **nyrax(32)、微信小程序(10)** |
| **不设上限、内存兜底** | 一直压,靠业务/内存约束，交给应用开发者自己 | **hap、RN、Flutter** |

一句收束：**满栈处理分两派——(1)硬上限+拒绝:nyrax(32,嵌入式定容)、微信小程序(10,到顶 navigateTo 失败);(2)无上限+内存兜底:hap、RN(React Navigation)、Flutter,栈能一直压,控深度靠业务侧 replace/reset/popUntil,框架不主动拦。Lynx 我无可靠依据,不妄断。nyrax 选"拒绝"派,是嵌入式内存约束逼出来的,和多数手机端框架(内存兜底派)相反。**
- Nyrax
**nyrax（有代码依据）**：
`surface_controller.cpp:836` —— `navigation_stack.size() >= max_stack_depth(32)` 时**直接拒绝 push**，返回 `kNavigationFailed`/navigation busy。**满了不清、不降级，就是拒绝新入栈**——固定容量、不扩容的硬约束（嵌入式风格）。
- hap

**没有满栈概念**——`mPageInfos` 是 ArrayList，能一直 add，没有上限检查。栈深靠 launchMode（singleTask/clearTask 清栈）和内存物理上限间接约束。**"满栈"在 hap 不存在,是内存先扛不住,不是框架拒绝。**
- 业界：
**业界（诚实分层：小程序较确定，其余标注推理）**：

- **微信小程序**：**有明确硬上限——页面栈最多 10 层**（这是公开文档写死的）。到 10 层再 `navigateTo` 会**失败/报错**，得用 `redirectTo`(替换当前页,不增栈)或 `navigateBack`。所以小程序是**"设上限 + 到顶拒绝新 push"**,和 nyrax 一个思路(拒绝),只是数字是 10。

## 面试官指导大纲

### 战略层：如何驾驭 AI

1. 战略上: 
    - 挖掘本质需求(第一性 ) → 明确优先级 → 定义验收标准 + 商业成功标准
2. 方案上:
    - 多方案对比 → 资源成本对比 → ROI 分析 → 用户满意度调研 → 可行性验证(MVP) → 上线后的运维监控与运营体系构建(可观测体系+埋点+配套文档)
3. 行动上: 
    - [**风险**](#注释风险识别)识别 → 落地计划(spec.tasks.md)

### 行动层：在框架节点上

- 对 AI 的输出进行**批判(质疑)**
- **补充**遗漏
- **抓关键**信息
- 提供**方案**
- 提出**创新**

## 我的策略

### 框架：[ISO](#注释ISO)（Anker 官方框架）= Spec 模式

### 阶段:两段式
- 阶段1: 快速覆盖: spec三段式 + 覆盖到面试官要求的所有要素 + 产出交付

- 阶段2:  持续加分: 不断打磨, 例如多维度的可观测, 小版本前进, 挖掘潜在需求, 更长期规划等
### 整体思路

**[Spec 模式](#注释spec三段式)（架构师 + PM 视角）** — 不是让 AI 写完代码就完事，而是：

```
1. 需求分析（10min）：拆解场景 → 明确核心功能 → 定义验收标准
2. 方案设计（15min）：架构选型 → 技术方案 → 对比 trade-off → 选最优
3. 实现（2h）：拆 task → AI 执行 → 我 review + 纠错 + 补充
4. 验证（20min）：跑通核心流程 → 自测 → 总结产出
```

## 铁律

1. `/model` 切 opus
2. 边做边交（每阶段产出文件）
3. 每 3-5 轮[高价值质疑](#注释高价值质疑)一次
4. 对话 ≥ 30 轮
5. ⚠️ **只能提交一次** — 80min 时确认所有文件就位，最后 10min 一次性压缩提交
6. 不熟的领域不慌 — 让 AI 先科普，你抓本质(第一性)后再做决策
7. [常用命令速查](#注释常用命令)

## Phase 1：Spec 流程（20min）

⚠️ **20min 必须有 MVP 在跑，超了就危险**

产出三件套：
1. `docs/requirements.md` — 需求拆解
2. `docs/tech-design.md` — 技术设计（含 Top3 方案对比）
3. `docs/tasks.md` — 开发任务拆解（按版本分：MVP / V1 / V2 / V3）

**注意点**：
- requirements：**主动加题目没说但应该做的**（错误处理、空状态、加载态）← 加分
- tech-design：**必须有[方案对比](#注释方案对比)**，不要直接给一个方案。对比 = 决策能力
- tasks：**按版本切**，让评分者看到你有节奏感

### @PM 需求拆解（5min）
```
@PM 读完以下题目，帮我：
1. 拆解核心功能模块
2. 每个模块定义验收标准
3. 标注优先级 P0/P1/P2/P3
4. 定义商业成功标准（上线后用什么指标衡量成功）
5. 输出到 docs/requirements.md
```
→ 质疑 Top3：
- "你没考虑错误状态（网络失败/空数据）的 UI 展示"
- "删除操作没有确认弹窗，用户误删怎么办？"
- "权限边界没定义 — 谁能看/谁能改/谁能删？"

### @Arch 技术方案（8min）
```
@Arch 基于 requirements.md，给出：
1. 数据库表结构设计
2. API 设计（路径 + 请求/响应）
3. 前端路由 + 组件结构
4. 给 Top3 方案对比，推荐一个并说明理由
输出到 docs/tech-design.md
```
- [接口设计考量](#注释接口设计)
-  质疑 Top3：
    - "为什么选 JWT 不选 Session？内部系统用户少，Session 不是更简单？"
    - "SQLite 并发写入有限制，多人同时操作怎么处理？"
    - "你的表结构没有软删除字段，误删数据不可恢复"

### @Arch 任务拆解（5min）
```
@Arch 基于 tech-design.md，拆解开发任务到 docs/tasks.md：
- MVP：最小跑通（1个接口 + 1个页面能渲染）
- V1：P0 功能完整 CRUD, 必做核心功能
- V2：模块关联 + 状态流转: P1功能实现: 次核心模块
- V3：看板/可视化 + 打磨: P2功能实现: 外围模块
- V4: 可观测 + 性能体验优化 + 视野升维: P3优先级: 锦上添花
每个版本列出具体 task 和预估耗时
```

### MVP 跑通（2min）
```
@Dev 按 tasks.md 的 MVP 部分，快速搭骨架跑通最小链路
```

## Phase 2：迭代（40min）

**注意点**：
- 每个版本完成后发一条小结："V1 完成，实现了 XX，接下来进 V2"
- 质疑集中在这个阶段（"代码没处理 null" / "API 格式不统一"）
- **不追求完美** — V3 做到 80% 比 V1 做到 100% 但后面没时间强
- 派活 → 验收 → [质疑](#注释质疑角度) → 下一个
- 速查：[前端考量](#注释前端考量) · [后端考量](#注释后端考量) · [PM考量](#注释PM考量)

### V1 核心 CRUD（15min）
```
@Dev 实现 P0 功能的完整 CRUD：
- [具体模块1]
- [具体模块2]
先后端再前端，每完成一个模块告诉我
```
→ 质疑 Top3：
- "密码存明文了，必须 bcrypt 加盐"
- "API 响应没有统一格式，加 { code, data, message } 包装"
- "列表接口没分页，数据多了前端会卡死"

### V2 关联功能（15min）
```
@Dev 实现模块间的关联逻辑：
- [关联操作]
- [状态流转]
```
→ 质疑："这段代码没有错误处理" / "密码存明文了"

### V3 看板/可视化（10min）
```
@Dev 实现数据看板页面：
- 用 Chart.js 画 [具体图表]
- 数据从后端 API 获取
```

**⚡️ 60min 时检查：demo 是否能跑。能跑就继续，不能跑立即修。**

## Phase 3：打磨（20min）

**注意点**：
- 代码审核让 AI 做，**你的角色是读审核结果后追问**（"你说有 XSS 风险，具体哪一行？修一下"）
- 运维/商业维度 = **主动加分** — 题目没要求但你做了 = 求极致

### @QA 代码审核
```
@QA 你是极其严格的代码审查员。审核 backend/ 和 frontend/ 代码：
1. 安全问题
2. 性能问题
3. 改进建议
输出到 docs/code-review.md
```

### @QA 测试报告
```
@QA 为系统写测试用例：
- 正常流程
- 异常流程
- 边界条件
输出到 docs/test-report.md
```

### 加分维度：升维思考（SSP 决胜点）

不只是交付代码，而是展示**全局视野**：

```
@Arch 我们已经完成了技术实现。现在请你从以下维度做一个项目总结，输出到 docs/summary.md：

0. 需求场景覆盖度
1. 产品维度：这个系统解决了什么核心痛点？用户体验还有哪些可优化？
2. 商业维度：上线后预计为团队节省多少人力？ROI 怎么算？
3. 成本维度：当前方案的开发/运维成本，vs 继续用 Excel 的隐性成本
4. 风险维度：上线后最大的 3 个风险是什么？如何应对？
5. 演进维度：V2 阶段应该做什么？（权限细化 / 审计日志 / 自动化告警）
```

→ 这 1 轮对话直接把你从"开发者"提升到"产品负责人"视角。

```
"你这个方案没有考虑 XX 场景，补充一下"
"为什么选 A 不选 B？给我理由"
"这段代码有安全问题，用 XX 方式重写"
```

## 得分公式

```
SSP = 过程深度（质疑+角色+拆解） × 产出完整度（能跑+文档全）
只有过程没产出 = 合格
只有产出没过程 = 合格
两手都硬 = SSP
```

# 注释

<a id="注释高价值质疑"></a>
### 高价值质疑

本质上质疑 = 你不接受第一版答案就直接用。形式可以是：

你知道的领域 → 直接指出问题
你不熟的领域 → 让 AI 自查 → 你追问它自查出的薄弱点

公式：**具体场景 + 指出问题 + 你的判断/方向**

| 类型 | ✅ 高价值 | ❌ 低价值 |
|------|----------|----------|
| 选型 | "为什么选 JWT？内部系统 Session 不是更简单？" | "能换个方案吗？" |
| 遗漏 | "没处理管理员删除自己的情况，会锁死系统" | "还有别的场景吗？" |
| 安全 | "密码存明文了，必须 bcrypt。这个 SQL 拼接有注入风险" | "代码安全吗？" |
| 性能 | "SQLite 不支持并发写入，10 人同时操作怎么办？" | "性能够吗？" |
| 数据 | "删设备时关联记录怎么处理？级联删还是软删除？" | "删除怎么办？" |
| 体验 | "列表没分页，1000 条时页面卡死" | "体验好吗？" |

核心区别：你**指出了具体问题并给方向** vs 让 AI 自己去猜。

<a id="注释方案对比"></a>
### 方案对比维度

| 维度 | 问什么 |
|------|--------|
| 实现复杂度 | 多久能做出来？MVP 成本？ |
| 性能 | 并发量？响应时间？ |
| 可扩展性 | 需求变了好不好改？ |
| 安全性 | 有什么安全风险？ |
| 运维成本 | 部署难度？依赖多不多？ |
| 团队适配 | 当前团队熟不熟这个栈？ |

prompt 模板：
```
@Arch 给出 Top3 方案，按以下维度对比：
实现复杂度 / 性能 / 可扩展性 / 安全性 / 运维成本
用表格输出，最后推荐一个并说明理由。
```

<a id="注释质疑角度"></a>
### 质疑角度（开发阶段每次验收后挑 1-2 个问）

| 角度 | 示例 |
|------|------|
| 边界 | "如果 email 不存在呢？返回什么？" |
| 安全 | "密码怎么存的？有没有加密？" |
| 错误处理 | "数据库挂了返回什么？有统一错误格式吗？" |
| 一致性 | "这个接口的响应格式和前面统一吗？" |
| 性能 | "数据量到 1 万条，这个查询会不会慢？" |
| 遗漏 | "删除时关联数据怎么处理？" |

<a id="注释风险识别"></a>
### 风险识别 Top5

| 类型 | 示例 |
|------|------|
| 技术风险 | "SQLite 并发写入可能丢数据" |
| 时间风险 | "功能太多做不完 → 砍到 P0" |
| 安全风险 | "没鉴权任何人都能改数据" |
| 数据风险 | "没备份，误删不可恢复" |
| 依赖风险 | "npm install 失败 → 备选 CDN" |

在 tech-design.md 里提一句："当前方案 Top3 风险：XX / YY / ZZ"即可。

<a id="注释spec三件套"></a>
### Spec 三件套 prompt 模板

**1. requirements.md**
```
@PM 读完题目，输出 docs/requirements.md，包含：
1. 需求背景（一句话痛点）
2. 核心功能模块拆解（每个模块列子功能）
3. 每个功能的验收标准（怎么算做完）
4. 优先级（P0 必做 / P1 尽量 / P2 可不做）
5. 商业成功标准（上线后用什么指标衡量成功）
6. 题目没提但应该考虑的（错误处理/空状态/权限边界）
```

**2. tech-design.md**
```
@Arch 基于 requirements.md，输出 docs/tech-design.md，包含：
1. 技术栈选型
2. Top3 方案对比表（实现成本/性能/可扩展性/安全/运维）
3. 推荐方案 + 选型理由
4. 数据库表结构
5. API 设计（路径 + 方法 + 请求/响应）
6. 前端页面结构（路由 + 组件）
7. Top3 风险点 + 应对
```

**3. tasks.md**
```
@Arch 基于 tech-design.md，输出 docs/tasks.md：
- MVP：最小跑通 task 列表
- V1：P0 功能完整 task 列表
- V2：关联 + 状态 task 列表
- V3：可视化 + 打磨 task 列表
每个 task 标注角色（前端/后端）+ 预估时间
```

<a id="注释接口设计"></a>
### 接口设计考量 Top5

| 方面 | 具体 |
|------|------|
| RESTful 规范 | GET/POST/PUT/DELETE 对应 CRUD，路径用名词复数 |
| 统一响应格式 | `{ code, data, message }` 每个接口一致 |
| 错误处理 | 4xx/5xx 状态码 + 错误信息 |
| 鉴权 | 哪些接口需要 token，中间件统一拦截 |
| 分页 | 列表接口带 `page` + `pageSize` 参数 |

<a id="注释ISO"></a>
### ISO 框架（Anker 官方）

| 阶段 | 含义 | 你做什么 | 对应 Spec |
|------|------|---------|-----------|
| **I — Insight（洞察）** | 分析问题本质，挖掘关键信息 | 读题 → 拆解需求 → 发现痛点 → 定义成功标准 | requirements.md |
| **S — Strategy（策略）** | 把洞察转化为行动方案 | 技术选型 → 方案对比 → 风险识别 → 任务拆解 | tech-design.md + tasks.md |
| **O — Operation（执行）** | 把策略落地为可交付产物 | 编码 → 迭代 → 测试 → 打磨 → 提交 | 代码 + 文档 + demo |

Phase 1 = I + S / Phase 2+3 = O

- /model：可以切换AI模型，如需识别PDF文件请切换至Haiku模型。
-  /run ：运行自动生成的代码（执行任务）
- /todos：查看当前正在处理的任务清单
- /status：检查当前状态（是否联网、是否执行完毕）
- /rewind：回到上一步（撤销或重做）
- /rename：为当前会话命名，方便在历史列表中识别
- /resume：在交互式会话中切换到另一个历史会话
- /export<文件名>：将当前完整对话导出为Markdown文件保存
如果需要恢复历史会话，建议直接使用【终端】CLI命令
- /claude-c：继续最近的一次会话
- /claude-r：从历史会话列表中选择一个来恢复

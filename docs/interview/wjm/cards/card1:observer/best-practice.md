## 一、优先级排序

```
P0 稳定性（不能崩）> P1 性能（不能慢）> P2 内存（不能涨）> P3 包体（不能大）
```

| 优先级 | 领域 | 为什么 | 目标 |
|--------|------|--------|------|
| **P0** | 稳定性 | Crash/ANR 直接影响留存和商店评分 | Crash 率 < 0.5%，ANR 率 < 0.47% |
| **P1** | 性能 | 启动慢/卡顿影响用户体验和转化 | 冷启动 < 2s，FPS > 55 |
| **P2** | 内存 | OOM 导致 Crash，后台被 kill 影响留存 | PSS 不超标，无泄漏增长 |
| **P3** | 包体 | 影响下载转化（每增 6MB 下载率降 1%） | APK < 50MB，IPA < 80MB |

## 二、快速搭建路径（2 周走通全链路）

### Week 1：接入 + 看到数据

```
Day 1-2：Sentry 接入（三端）
  ├── RN：@sentry/react-native（Crash + JS Error + Performance）
  ├── Android：sentry-android（Native Crash + ANR）
  └── iOS：sentry-cocoa（Native Crash + Watchdog）

Day 3：基础配置
  ├── Source Map 上传（CI 中自动）→ 错误堆栈可读
  ├── Release / Dist 标记 → 按版本筛选
  └── Environment 区分（staging / production）

Day 4-5：性能 Tracing
  ├── App Start span（Native 启动 → JS 加载 → 首屏渲染）
  ├── 自定义 Transaction（关键页面加载）
  └── HTTP 请求自动 Instrumentation

Day 6-7：看板 + 告警
  ├── Sentry Dashboard：Crash 率 / Error 率 / P95 启动时长
  ├── 告警规则：Crash 率 > 1% → Slack/飞书通知
  └── 与灰度发布关联：新版本 error spike → 自动通知
```

### Week 2：补齐短板 + 建立流程

```
Day 8-9：ANR / Watchdog 检测
  ├── Android：Sentry ANR 检测（自带） + 自定义 Looper 监控
  └── iOS：MetricKit（iOS 14+） + 自定义 Watchdog

Day 10-11：内存基线
  ├── 启动后 PSS 基线记录
  ├── 页面切换内存 diff 采集
  └── CI 中跑内存基准测试（可选，P2 阶段再做）

Day 12-13：包体监控
  ├── CI 产物大小记录（APK/IPA/JS Bundle）
  ├── bundlesize 配置阈值 → 超标阻断 PR
  └── 历史趋势图（简单用 CI artifact + 脚本）

Day 14：流程文档 + 团队对齐
  ├── 错误治理 SOP（发现→分配→修复→验证）
  ├── 值班 oncall 机制
  └── 防退化规则（启动时长/Crash 率/包体 不允许退化）
```

## 三、工具链统一化

### 选型原则

| 原则 | 说明 |
|------|------|
| **一套工具覆盖三端** | 减少维护成本，统一看板 |
| **SaaS 优先** | 30 人团队不自建后端，用云服务 |
| **开箱即用** | 最小配置量，快速出数据 |
| **可扩展** | 后续可以加自定义指标 |

### 推荐工具链

```
┌──────────────────────────────────────────────────────────────┐
│ 可观测工具栈（海外团队推荐）                                    │
├──────────────────────────────────────────────────────────────┤
│                                                                │
│ 错误监控：Sentry（统一三端）                                    │
│   - RN / Android / iOS Crash                                   │
│   - JS Error + Source Map                                      │
│   - Performance Tracing                                        │
│   - ANR 检测（Android 原生支持）                                │
│                                                                │
│ 性能监控：Sentry Performance + Firebase Performance             │
│   - 启动时长 / 页面加载 / HTTP 耗时                             │
│   - Firebase 补充：网络质量 / 屏幕渲染                          │
│                                                                │
│ 用户行为：Firebase Analytics / Amplitude                       │
│   - 页面访问 / 功能使用 / 漏斗转化                              │
│                                                                │
│ 包体监控：CI 内置（bundlesize + 自定义脚本）                    │
│   - PR 级别包体 diff                                            │
│   - 历史趋势                                                    │
│                                                                │
│ 告警通道：Sentry Alerts → Slack / 飞书 Webhook                 │
│                                                                │
└──────────────────────────────────────────────────────────────┘
```

### 国内替代方案

| 海外方案 | 国内替代 | 说明 |
|---------|---------|------|
| Sentry (SaaS) | Sentry 自部署 / Bugly | Bugly 免费但功能弱 |
| Firebase Performance | 听云 / 阿里 ARMS | 国内 APM |
| Firebase Analytics | 友盟 / GrowingIO | 国内埋点 |

## 四、开发流程治理

### 可观测驱动的开发流程

```
┌─────────────────────────────────────────────────────────────┐
│ 开发 → 提 PR → CI 门禁 → 合并 → 灰度 → 全量 → 监控         │
│         │         │                │              │          │
│         │    ┌────┴────┐     ┌────┴────┐    ┌───┴───┐     │
│         │    │包体检查  │     │观测灰度  │    │持续监控│     │
│         │    │启动基准  │     │错误率   │    │防退化  │     │
│         │    │lint+test │     │性能指标  │    │告警   │     │
│         │    └─────────┘     └─────────┘    └───────┘     │
└─────────────────────────────────────────────────────────────┘
```

### CI 门禁卡点

| 卡点 | 工具 | 阈值 | 阻断级别 |
|------|------|------|---------|
| 包体大小 | bundlesize | APK +2MB / Bundle +500KB | ⚠️ Warning（P3 阶段改为 Block） |
| TypeScript 类型 | tsc --noEmit | 0 errors | 🚫 Block |
| ESLint | eslint | 0 errors | 🚫 Block |
| 单元测试 | jest | 通过率 100% | 🚫 Block |
| 构建验证 | metro bundle | 能编译 | 🚫 Block |

### 灰度阶段观测

```
发布灰度 1%
  → 观测 1h：
    - Sentry error count（对比上一版本同时段）
    - Crash 率（不能高于基线 0.5%）
    - 启动 P95（不能比上版本慢 500ms+）
  → 无异常 → 扩大到 10%
  → 观测 4h → 无异常 → 100%
  → 有异常 → 自动回滚 + 告警 oncall
```

### 错误治理 SOP

```
1. 发现：Sentry 告警 / 用户反馈 / QA 发现
2. 分级：
   - P0（Crash 率 > 1% / 核心流程不可用）→ 立即修复 + 热更新
   - P1（非核心 Crash / 性能退化明显）→ 24h 内修复
   - P2（低频错误 / 体验问题）→ 下个版本修复
3. 定位：Sentry 堆栈 + 版本对比 + 设备分布
4. 修复：热更新（JS 层）/ 发版（Native 层）
5. 验证：灰度观测指标恢复
6. 复盘：根因分析 → 加防退化规则 / 补自动化测试
```

## 六、面试叙述

> "我的做法是分优先级快速建立可观测体系：第一周接入 Sentry 覆盖三端 Crash 和性能，第二周补 ANR 检测和包体监控，两周内走通'采集→上报→看板→告警'全链路。同时把可观测能力嵌入开发流程——CI 卡包体和启动基准，灰度阶段自动对比错误率，异常自动回滚。本质不是工具选型问题，是建立一个'测量→定位→修复→验证→防退化'的闭环流程。"

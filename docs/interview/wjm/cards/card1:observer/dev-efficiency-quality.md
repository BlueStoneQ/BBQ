## 一、研发效率指标 Top 3

### 1. 需求交付周期（Lead Time）

```
定义：从需求提出到生产环境上线的平均时间

计算：
需求交付周期 = 需求上线时间 - 需求创建时间

分层：
├── 需求评审到开发启动：评估产品/设计效率
├── 开发启动到代码提交：评估开发效率
├── 代码提交到生产上线：评估CI/CD效率
└── 整体周期：评估全流程效率

目标：7天（小需求）/ 30天（大需求）
```

### 2. 部署频率（Deployment Frequency）

```
定义：单位时间内生产环境部署次数

计算：
部署频率 = 部署次数 / 时间周期（天/周）

分层：
├── 个人：每人每天提交次数
├── 团队：每周发布次数
└── 公司：每天生产部署次数

目标：每天多次（持续交付）/ 每周至少1次（敏捷）
```

### 3. 恢复时间（MTTR, Mean Time To Recovery）

```
定义：故障发生到恢复的平均时间

计算：
MTTR = 故障恢复时间 - 故障发现时间

分层：
├── P0故障：1小时内恢复
├── P1故障：4小时内恢复
└── P2故障：24小时内恢复

目标：P0 < 30分钟
```

## 二、研发质量指标 Top 3

### 1. [缺陷逃逸率](#注释缺陷逃逸率)（Defect Escape Rate）

```
定义：生产环境发现的缺陷 / 总缺陷数

计算：
缺陷逃逸率 = 线上缺陷数 / (线上缺陷数 + 测试发现缺陷数)

分层：
├── 严重缺陷逃逸率：P0/P1缺陷占比
├── 一般缺陷逃逸率：P2/P3缺陷占比
└── 趋势：逐版本对比

目标：< 5%（严重缺陷逃逸率）
```

### 2. 变更失败率（Change Failure Rate）

```
定义：导致故障或回滚的部署 / 总部署次数

计算：
变更失败率 = 失败部署次数 / 总部署次数

分层：
├── 代码变更失败：提交后构建失败
├── 部署失败：上线后回滚
└── 业务失败：上线后功能异常

目标：< 15%（精英团队 < 5%）
```

### 3. 代码覆盖率（Code Coverage）

```
定义：自动化测试覆盖的代码比例

计算：
代码覆盖率 = 被测试覆盖的代码行数 / 总代码行数

分层：
├── 单元测试覆盖率：核心逻辑
├── 集成测试覆盖率：API接口
└── E2E测试覆盖率：关键路径

目标：> 80%（单元）/ > 60%（集成）
```

## 三、DORA 框架对照

```
Google DORA（DevOps Research and Assessment）：

效率指标：
├── 部署频率（Deployment Frequency）
├── 变更前置时间（Lead Time for Changes）
└── 恢复时间（Time to Restore Service）

质量指标：
├── 变更失败率（Change Failure Rate）
└── 可靠性（Reliability）

对应关系：
├── 部署频率 → 部署频率
├── 变更前置时间 → 需求交付周期
├── 恢复时间 → MTTR
└── 变更失败率 → 变更失败率
```

## 四、可观测体系设计

```
数据采集：
├── 研发工具链：GitLab/Jira/Jenkins → API采集
├── 监控平台：Prometheus/Grafana → 指标采集
├── 日志系统：ELK/Loki → 日志分析
└── 人工反馈：故障复盘/Retro → 定性补充

数据展示：
├── 研发效能仪表盘（Grafana）
├── 团队排名/趋势对比
└── 个人效能报告（可选，敏感）

持续改进：
├── 每周效能Review
├── 瓶颈识别（最长等待环节）
└── 实验优化（A/B流程改进）
```

## 五、关键陷阱

| 陷阱 | 说明 |
|------|------|
| 唯指标论 | 指标是手段，不是目的；避免数据造假 |
| 忽视质量换效率 | 压缩测试时间 → 缺陷逃逸率上升 |
| 局部优化 | 开发快但部署慢 → 全流程未改善 |
| 团队差异 | 基础设施团队 vs 业务团队指标不同 |

# 注释

<a id="注释缺陷逃逸率"></a>
### 缺陷逃逸率统计周期

按**版本/迭代**统计，不是按固定时间。一个发版周期内（Sprint 2 周或一个版本生命周期），统计该版本上线后发现的 bug 占总 bug 的比例。实际操作：按月汇总看趋势（月度质量报告），或按版本回顾。
